# T-0274 — Research javascript text editor with syntax highlighting for markdown.

For the detail editor, Research javascript text editor with syntax highlighting.

Monaco, and Ace are editors are two I have used in the past. A few options should be compared, a light weight option is important also a non-restrictive license is important.

## Current constraints

- The UI is server-rendered and progressively enhanced. Static assets are embedded in the Go binary and must work offline under `script-src 'self'`.
- The existing editor is a native textarea named `detail`; save, conflict detection, and revision checks already depend on that submitted raw Markdown value.
- T-0272 selected `markdown-it` for rendered preview. The editor only needs source highlighting and editing behavior; it should not introduce a second Markdown-to-HTML renderer.
- The editor must survive htmx panel replacement, preserve unsaved source while switching to preview, and cleanly destroy its event handlers when the panel is replaced.
- Mobile usability, keyboard access, screen-reader behavior, soft wrapping, undo, selection, paste, and IME input matter more than IDE features.

## Options

### 1. CodeMirror 6 — recommended

[CodeMirror](https://codemirror.net/) is MIT licensed and its current architecture is modular. The official packages provide editor state/view primitives and Markdown language support, so a build can include the editor, the Markdown parser/highlighter, history, search, wrapping, and only the keymaps actually wanted. The official documentation notes that CodeMirror 6 packages require a bundler or module loader in the browser.

Strengths:

- Best balance of mature editing behavior, Markdown-aware highlighting, accessibility work, and configurable bundle scope.
- State and view are explicit objects, which suits htmx lifecycle cleanup and preserving selection/scroll between Edit and Preview.
- Extensions can be kept narrow. No autocomplete, linting, language server, minimap, worker, or multi-file machinery is needed.
- A hidden textarea can remain the form's submission source, synchronized on document changes, which preserves the server contract and no-JavaScript fallback.

Costs and risks:

- Requires a small deterministic JavaScript bundling step; the repository currently vendors ready-made classic scripts instead.
- CodeMirror is a graph of packages rather than one file. Versions must be locked together, and the generated bundle plus license metadata should be checked in.
- Its DOM/editor behavior needs real-browser accessibility and IME testing in addition to jsdom tests.

Suggested minimal bundle: `@codemirror/state`, `@codemirror/view`, `@codemirror/commands`, `@codemirror/lang-markdown`, `@codemirror/language`, and only the selected search/keymap support. Build one self-contained `codemirror-markdown.min.js`; do not ship npm modules to the runtime.

### 2. Ace — best no-new-bundler fallback

[Ace](https://github.com/ajaxorg/ace) is MIT licensed, mature, and ships prebuilt browser artifacts. Its official embedding guidance supports copying packaged builds locally, and Markdown mode is a separate module. It offers robust editing, search, undo, wrapping, folding, multiple selections, and familiar editor APIs.

Strengths:

- Lowest integration uncertainty for a full editor: vendor `ace.js`, Markdown mode, and one theme; configure their local URLs; no new production build pipeline.
- Mature API and editing behavior, including explicit session state for selection and scrolling.
- The team already has experience with it.

Costs and risks:

- Heavier and less modular for this narrow use case; dynamic module loading needs careful local `basePath` configuration under the existing CSP.
- Brings many code-editor concepts that task details do not need.
- Styling Ace to match the existing design/theme tokens is less direct than styling CodeMirror extensions.

Choose Ace if avoiding a JS bundling step is more important than minimizing the embedded asset and feature surface.

### 3. Monaco — capable but not a fit

[Monaco Editor](https://github.com/microsoft/monaco-editor) is MIT licensed and provides the editing core of VS Code. It is excellent for IDE-like language tooling, large source files, diagnostics, commands, and complex multi-model workflows.

Why not here:

- Its own documentation says mobile browsers are unsupported.
- The ESM build expects a bundler and commonly uses workers; the legacy AMD path is deprecated.
- Even aggressively reduced Markdown configurations have historically produced bundles around 1.5 MB. That cost buys IDE machinery this detail editor does not need.
- Worker/static-path setup increases complexity in an otherwise single-script, embedded-asset UI.

### 4. CodeJar plus Prism — smallest, but higher ownership risk

[CodeJar](https://github.com/antonmedv/codejar) is MIT licensed, dependency-free, and advertises a roughly 2.45 kB core. It turns a `contenteditable` element into an editor and delegates highlighting to a library such as [Prism](https://github.com/PrismJS/prism), also MIT licensed and lightweight.

Strengths:

- By far the smallest editor core.
- Easy to vendor as classic scripts with no bundler.
- Enough for basic indentation, bracket pairing, undo/redo, and highlighting.

Costs and risks:

- It is not a complete Markdown editor by itself; Prism and a Markdown grammar are additional dependencies.
- Re-highlighting `contenteditable` content while preserving selection, IME composition, paste fidelity, undo history, screen-reader semantics, and mobile behavior is the hard part of editor engineering. CodeJar reduces but does not eliminate that ownership.
- Synchronizing a contenteditable surface back to the canonical textarea adds another state boundary.
- Prism v1 currently accepts only security fixes while v2 is under development, increasing upgrade uncertainty.

This is attractive only if the smallest possible download outweighs mature accessibility and editing behavior.

### 5. Native textarea with a highlighted overlay — smallest dependency surface

Keep the textarea as the actual editor and mirror its escaped text into a non-interactive highlighted `<pre>` behind it, synchronizing font metrics, wrapping, and scroll positions. Prism could supply tokenization, or a very small purpose-built Markdown tokenizer could highlight only punctuation.

This preserves native editing and form behavior, but correct overlay alignment across proportional metrics, wrapping, zoom, platform scrollbars, composition, and long lines is deceptively expensive. A home-grown tokenizer also becomes a second Markdown interpretation beside `markdown-it`. It is a reasonable progressive experiment, not the preferred production path.

## Vim keybinding support

### CodeMirror 6: yes, through a maintained extension

[`@replit/codemirror-vim`](https://github.com/replit/codemirror-vim) provides Vim keybindings for CodeMirror 6. It is a separate MIT-licensed dependency maintained by Replit rather than part of CodeMirror core. The package supplies normal, insert, visual, and command-line behavior plus Vim motions, operators, registers, search, mappings, and Ex-command integration.

This is the best Vim option among the lightweight candidates, but it changes the proposed minimal bundle:

- Add the extension only when Vim mode is enabled; if practical, produce a separate optional bundle or dynamically load the locally hosted extension.
- Provide a visible mode/status element (`NORMAL`, `INSERT`, `VISUAL`, command input) and announce mode changes accessibly.
- Preserve the ordinary CodeMirror keymap as the default. Vim mode must be explicit and persistent per user, never silently enabled from content.
- Define how application shortcuts such as Save, Preview, Escape/close, and search interact with Vim interception, and test those collisions.
- Destroy Vim state with the editor view during htmx cleanup.

### Ace: yes, first-party packaged module

Ace ships a `keybinding-vim.js` module in its prebuilt distribution and enables it through `editor.setKeyboardHandler("ace/keyboard/vim")`. This is the simplest Vim integration operationally: vendor the module beside Ace core and Markdown mode, configure the same local base path, and toggle the handler.

Ace therefore becomes more attractive if Vim support is a first-release requirement and avoiding another third-party extension matters more than total bundle weight. It still carries the broader Ace core and remains the no-bundler fallback rather than the overall lightweight recommendation.

### Monaco: yes, third-party

[`monaco-vim`](https://www.npmjs.com/package/monaco-vim) adds Vim behavior and a status bar to Monaco. It is MIT licensed and currently published, but it is not part of Monaco. Its documentation notes that it depends on Monaco internals, requires bundling or the deprecated AMD loading path, and may have gaps in commands that require extra input, including some Ex/search behavior.

Vim availability does not alter the Monaco rejection: the editor remains disproportionately large, its browser integration is the most complex, and Monaco itself does not support mobile browsers.

### CodeJar plus Prism: no maintained built-in Vim mode

CodeJar exposes keyboard events but provides no maintained Vim emulation. Adding Vim would mean adopting another editor-agnostic Vim engine or implementing modes, motions, operators, counts, registers, text objects, search, repeat, mappings, and command state locally. That eliminates its simplicity and greatly increases input/accessibility risk. Treat this option as not supporting Vim for planning purposes.

### Native textarea/highlight overlay: no practical Vim mode

A textarea can intercept keys, but it has no Vim state machine. A credible implementation would require the same large custom surface as CodeJar and would fight native browser editing shortcuts. Treat this option as not supporting Vim.

| Option | Vim support | Ownership | Effect on recommendation |
|---|---|---|---|
| CodeMirror 6 | Yes: `@replit/codemirror-vim` | Maintained third-party, MIT | Still recommended |
| Ace | Yes: `ace/keyboard/vim` | Packaged with Ace | Strongest no-bundler/Vim fallback |
| Monaco | Yes: `monaco-vim` | Third-party, MIT | Still rejected on weight/integration |
| CodeJar + Prism | No built-in option | Would become app-owned or another dependency | Reject if Vim is required |
| Textarea overlay | No | Would be app-owned | Reject if Vim is required |

## Recommendation

Use CodeMirror 6 with a deliberately minimal, version-locked Markdown bundle checked into `internal/web/static/`. Keep the native textarea in the form as the canonical raw value and no-JavaScript fallback; enhance it into CodeMirror only in Edit mode and synchronize every document change back to that textarea.

This recommendation optimizes for total product cost rather than the smallest byte count alone. It avoids Monaco's IDE-sized payload, provides substantially stronger editing and accessibility behavior than CodeJar or an overlay, and can be narrower than Ace when bundled for this one language and feature set.

If Vim bindings are included, add `@replit/codemirror-vim` as an optional user-selected mode. Its additional bundle size should be measured separately. Vim support does not require changing the editor recommendation; if the project rejects third-party keybinding extensions or rejects bundling, choose Ace instead.

## Integration outline

1. Add a reproducible asset-build directory with a lockfile and a single entry module. Pin all CodeMirror package versions; check in the minified bundle, source/version manifest, checksum, and MIT notices.
2. Load the bundle locally before `mm.js`; make it expose a tiny application-specific factory rather than the full package API.
3. Keep `textarea[data-testid="item-field-detail"]` in the DOM and in form submission. Hide it only after enhancement succeeds.
4. Initialize CodeMirror only when entering Edit mode. Seed it from the textarea, synchronize changes back, and expose methods for value, focus, selection, scroll state, and destroy.
5. Before Preview, synchronize the latest source and hand that exact string to the T-0272 `markdown-it` renderer. Returning to Edit must reuse or restore editor state without changing text.
6. On htmx `beforeCleanupElement`, destroy the editor view; after a new panel settles, initialize only if that panel is in Edit mode. Never retain a detached editor or listener.
7. Use soft wrapping, Markdown mode, history, search, bracket matching, and accessible default keymaps. Omit autocomplete, linting, gutters/line numbers by default, folding, workers, and IDE services unless user testing justifies them.
8. Map colors, borders, focus rings, selection, and typography to existing `--mm-*` tokens and verify all shipped themes.

## Acceptance and evaluation

- Raw Markdown remains byte-for-byte authoritative; preview HTML is never submitted.
- Without JavaScript, the textarea remains visible and fully usable.
- Edit/Preview switching preserves text, undo history where practical, selection, and scroll position.
- Saving, validation errors, concurrent-edit conflicts, SSE/htmx replacement, and panel close do not lose edits or leak editor instances.
- Keyboard-only editing, screen-reader labeling, focus indication, IME composition, paste, mobile/touch input, zoom, high contrast, and reduced motion are tested in real browsers.
- A large but bounded detail remains responsive; bundle size is measured and recorded rather than guessed.
- Vendored files have an auditable version, checksum, license, and repeatable rebuild/update command.

## Open questions before implementation

- Is introducing a small deterministic JS asset build acceptable, or is “no bundler” a hard project constraint? If it is hard, choose Ace.
- Should the initial editor show line numbers? Recommendation: no; they consume scarce panel width and are less useful for prose.
- Which non-basic controls are required initially: search, Markdown key bindings, spellcheck, or Vim/Emacs mappings? Recommendation: search and browser spellcheck only.
- Should Vim mode be a global UI preference, a per-board preference, or session-only? Recommendation: a global user preference, because keybinding choice belongs to the user rather than board data.
- Is Vim mode required in the initial editor release or acceptable as a follow-up? Making it optional keeps the default bundle and first implementation smaller.
- What maximum detail size should trigger a plain-textarea fallback to protect rendering and editing responsiveness?

## Conclusion

Proceed with CodeMirror 6 if a checked-in deterministic bundle is acceptable. Otherwise use locally vendored Ace with only core, Markdown mode, and one theme. Do not use Monaco for this feature, and treat CodeJar/overlay approaches as prototypes that must prove accessibility and input correctness before adoption.
