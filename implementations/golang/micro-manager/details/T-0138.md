# T-0138 — Morph leaks an htmx poll chain per externally-targeted board swap

A regression introduced by T-0129 and found while measuring T-0131. It is on
`main` as of b2d4bb3.

## Symptom

Every swap that targets the board **from another element** leaves an extra
`every 30s` poll chain running. The chains never stop, so a session's idle
board traffic is `(1 + number of mutations) x 120 fetches/hour` and grows
without bound for as long as the tab stays open.

Reproduced in a real browser on a board page:

- fresh load, no mutations — board fetches at t=18, 49, 79, 109 s (one chain,
  correct), status at t=18, 48, 78, 108 s;
- after a single `htmx.ajax('GET', board, {swap:'morph'})` — board fetches at
  t=1, 13, 31, 43, 61, 73, 91, 103, 121, 133, 151, 163 s: **two** independent
  30 s chains, while status still runs one.

## Cause

htmx has no de-duplication on polling. `ct()` (the polling scheduler in the
vendored `htmx.min.js`) stores its handle on the element's internal data and
reschedules itself:

```js
function ct(e,t,n){ const r=oe(e);
  r.timeout = setTimeout(function(){
    if (se(e) && r.cancelled !== true) { ...request...; ct(e,t,n) }
  }, n.pollInterval) }
```

A second call overwrites `r.timeout` **without clearing the previous timer**.
Nothing sets `cancelled`, so the only thing that stops the orphaned chain is
`se(e)` — `bodyContains(e)` — going false.

That is exactly the invariant morph breaks. Under `outerHTML` the swapped-out
element left the DOM, `se(e)` went false, and the old chain died on its next
tick. Under `morph` the element is **preserved**, so `se(e)` stays true and
both chains run forever. Verified: the extra `setTimeout(…, 30000)` is
scheduled during the swap, from `ct` called by `St` (the trigger-handler
registrar).

Self-triggered refreshes do **not** compound — a poll or `sse:board` that
refreshes the board through its own `hx-get` keeps one chain. Only a swap
aimed at the board *from somewhere else* re-registers the trigger. In this
codebase that is every mutation:

- `static/mm.js` — the two `htmx.ajax(..., swap:'morph')` calls (card-menu
  operations, drag commit);
- `templates/partials/dialogs.html` — block / finish / confirm-remove forms;
- `templates/partials/item-panel.html` — the item form, the action buttons,
  the note form.

`app-status` carries the same `every 30s` + morph pairing and is swapped OOB
by every mutation, so it should be checked for the same leak.

## Fix — decide between

1. **Keep morph only where it is safe.** Revert the *mutation* swaps to
   `outerHTML` (dialogs, item-panel, the two `mm.js` calls) and keep morph on
   the self-refresh triggers, which are proven not to compound and are where
   the flicker actually was. Smallest, and T-0130 already suppresses the
   mutation echo that morph was meant to hide.
2. **Cancel before re-registering.** Have `mm.js` mark the poll cancelled and
   let htmx re-register — relies on htmx internals, so it would need a test
   pinned to the vendored build.
3. **Move the trigger off the morphed element** so the polling element is
   never the swap target. Largest change; touches the DOM contract.

Option 1 is the recommendation: it restores correctness now and keeps the
measured win (morph is *faster* than `outerHTML` at the default `doneLimit`,
6.7 ms vs 11.9 ms median — see T-0131).

## Regression test

A Go test cannot see this: it is htmx timer behaviour in a live browser. Note
it against T-0111 (the drag/JS test-runner gap), which is the item that would
give this a home.
