# T-0164 — Tickler service

Spike. Define a way for a task to be placed into 'someday' with a date in the
future when a service will move it to the ready column. Also define a way for
repeatable items to be created that are a prototype that create a task in the
ready column. Spike this out first with a proposed spec.

**Status: spike done, proposal below. Adoption is filed as [[T-0169]]–[[T-0173]].**

---

# Proposed spec — the tickler

## 1. The model in one paragraph

A someday item MAY carry a `tickler:` field holding a machine-built schedule
expression (`2026-09-01`, `mon@08:00`, `first-mon@08:00`, `15@08:00`,
`last@08:00`). A process that runs the library's `Store.tick(now)` — from the
`mm` CLI on a cron timer, or from an optional goroutine inside the UI service —
evaluates every someday item with a `tickler`, and each due item fires:

- **One-shot** (`tickler:2026-09-01`): the item moves to `## Ready`, its
  `tickler:` field is dropped, and `tickled:2026-09-01` is stamped on it. It is
  now an ordinary ready item; the schedule is consumed.
- **Recurring** (`tickler:mon@08:00`, `tickler:first-mon@08:00`,
  `tickler:15@08:00`): the item is a **prototype**. The service creates a new
  item in `## Ready` — a fresh ID, the prototype's title/prio/tags, `created`
  set to the firing date — stamps `tickled:<date>` on the prototype, and the
  prototype STAYS in Someday with its `tickler` intact, ready to fire again.

Firing is idempotent across overlapping processes (a cron entry and a running
UI at once): each fire is one transaction, and the `tickled` stamp makes a
second process see the schedule's next fire as not-yet-due. See §5.

Times are wall-clock in the process's own zone; the data files stay
date-granular (§7). The checker validates the schedule's *shape*, never its
meaning — no clock enters the format.

## 2. On-disk representation

Two new registered fields (§6 of the format spec; both optional):

| Key | Value | Required | Valid in | Notes |
|---|---|---|---|---|
| `tickler` | `SCHEDULE` | no | `## Someday` only | Fires when `Store.tick` runs at/after the due instant. |
| `tickled` | `DATE` | no | all | Date the tickler last fired. Audit trail; harmless after a manual move. |

Placement rules, added to §5.1's Someday bullet and enforced in I7:

- An item carrying `tickler` MUST sit in `## Someday` (nowhere else — a
  tickler on a ready item is a contradiction).
- An item carrying `tickler` MUST also carry `created`. The service anchors a
  never-fired recurring schedule on `created`; without it a freshly written
  `mon@08:00` on a Tuesday would be judged overdue against the epoch and fire
  for last Monday.

### 2.1 The SCHEDULE grammar

Built by UI controls, not typed free text. Three shapes, `@HH:MM` always
optional (absent time = `00:00`):

```
SCHEDULE      = one-shot / weekday-spec / monthday-spec
one-shot      = DATE [ "@" TIME ]
DATE          = 4DIGIT "-" 2DIGIT "-" 2DIGIT     ; a real calendar date (§3.3.1)
TIME          = 2DIGIT ":" 2DIGIT                ; 00:00–23:59, wall-clock
weekday-spec  = [ ordinal "-" ] weekday [ "@" TIME ]
ordinal       = "first" / "second" / "third" / "fourth" / "last"
weekday       = "mon" / "tue" / "wed" / "thu" / "fri" / "sat" / "sun"
monthday-spec = ( monthday / "last" ) [ "@" TIME ]
monthday      = 0[1-9] / [12][0-9] / 3[01]       ; 1..31
```

Examples:

| Value | Meaning |
|---|---|
| `2026-09-01` | Move to Ready at 00:00 local on 2026-09-01 (once). |
| `2026-09-01@08:00` | Same, at 08:00 local. |
| `mon@08:00` | Every Monday 08:00 (prototype; spawns each Monday). |
| `first-mon@08:00` | First Monday of each month 08:00. |
| `last-mon@08:00` | Last Monday of each month 08:00. |
| `15@08:00` | The 15th of each month 08:00. |
| `last@08:00` | The last day of each month 08:00. |

Semantics that must be pinned down once, in the library:

- `first-mon` = the Monday in the first seven days of the month; `last-mon` =
  the Monday in the last seven days. `last` = the final day of the month.
- A monthday of `31` fires only in months that have a 31st; the next fire skips
  short months (`next` returns the next month with a 31st). Same for `30` vs
  February. This is the one place the calendar algorithm must be tested hard.
- `@` (not `T`) separates time: `T` already means an ISO timestamp in §3.3.1,
  and timestamps carry seconds and an offset the schedule must not.

Extensions deliberately not in v1, named so a later revision can add them
without breaking the grammar: daily schedules (`daily@08:00`), weekday lists
(`mon,fri@08:00`), and a per-item timezone. None are needed for the two use
cases in the task.

## 3. Fire semantics

`Store.tick(now)` walks `## Someday`, and for each item with a `tickler`:

1. Parse the schedule (a malformed value is an error reported for that item —
   hand-edited garbage must not abort the run).
2. Compute due: see §4.
3. If due, fire in ONE transaction (§7 of spec-tools: read, modify, validate,
   write; the write is a line splice, never a re-render):
   - **one-shot**: remove the `tickler:` field, set `tickled:<today>`, move the
     line from `## Someday` to `## Ready` (appended — Ready order is the user's
     own prioritisation; a tickled item is not automatically important).
   - **recurring**: set `tickled:<today>` on the prototype; add a new item to
     `## Ready` with a fresh ID (`next_id` bumps, I2), the prototype's title,
     prio, and tags, and `created:<today>`.
4. Report every fire (item, kind, new ID for spawns) and every error.

**Spawns do not copy `detail`, `blocked`, `tickler`, or `tickled`.** The
detail trap is the sharp one: I9 says every detail file is claimed exactly
once. A spawned copy carrying the prototype's `detail:` would point two items
at one file and the transaction would abort on validation. A spawned copy gets
no `detail:` at all; the prototype keeps its own.

**Both fire kinds live entirely in `backlog.md`** — Someday and Ready are the
same file, so a fire is a single-file transaction, the simplest shape the
envelope has. Nothing in a fire touches working files, `done.md`, or `next_id`
(except the spawn's bump). Manual intervention mid-fire is impossible in a way
a two-file op never is.

**The move out of Someday clears `tickler`.** One-shot fires do this by
removing the field; the library's `Move` operation, when it moves an item out
of `## Someday`, must also drop a `tickler:` field (keeping `tickled` — it is
historical). Without this, dragging a scheduled someday item to Ready would
leave a field the checker rejects, and the move would die with
`InvariantViolation` for no visible reason. The fire's own move reuses this
rule, so the one-shot path is: move + set `tickled`.

## 4. Due test

Let `last = tickled` (absent for a never-fired item). With the `created`
requirement of §2, due is:

- **one-shot**: due iff `fire-date > last` (absent `last` → the date has
  arrived). A backdated one-shot — written down after its date — fires on the
  next run: "overdue, fire now" is the least surprising reading.
- **recurring**: due iff `next(last ?? created) <= now`, where `next(after)`
  is the smallest fire instant **strictly after** `after`. A `mon@08:00`
  prototype written on a Tuesday fires the following Monday 08:00, never for
  the Monday that already passed.

A service that missed a run (down Monday, back Tuesday) still fires — the
strictly-after rule makes `next(last) <= now` stay true across the gap.

## 5. Concurrency, idempotency, cadence

Two processes can run `tick` on one board (a UI service and a cron entry).
Three layers make that safe:

1. **The `tickled` stamp is the primary guard.** After a fire, the parent's
   `tickled` is today, so `next(tickled)` is in the future and the schedule is
   not due again. All v1 periods are >= 1 day, so this is at-most-once-per-day
   per tickler, which is at-most-once-per-period. A minute-cadence UI and an
   hourly cron cannot double-spawn in the same day.
2. **Transaction rule 5 (`Concurrent`)** covers the process that read the
   parent *before* the winner wrote: its read is stale, its write aborts, and
   `tick` reports the error and continues with the other due items. A failing
   item never aborts the run.
3. **One-shot consumption.** A consumed one-shot has no `tickler` left to
   re-evaluate; the only failure mode is two processes moving the same line,
   which rule 5 resolves.

Cadence is free: any interval works, and a missed run catches up. The
effective firing granularity is the cadence of the least frequent runner, not
a property of the data.

## 6. Library API

The library is the single surface; the CLI and the UI are thin callers
(spec-tools §2.6 — the library moves data, a front end decides *when*).

```
Schedule  — value type, immutable
  parse(string)        -> Schedule      # InvalidArgument on a bad SCHEDULE
  String()             -> string        # canonical form
  next(after DATE)     -> DATE | null   # smallest fire strictly after; null for
                                        # a one-shot that will never fire again
  isOneShot() -> bool, fireDate() -> DATE | null
  isRecurring() -> bool

Store.ticklers() -> [Tickler]
  Tickler { id ID, schedule string, last DATE | null, next DATE | null }
                       # read-only; next is computed from Schedule.next(created
                       # or last) against the caller's idea of "now", which the
                       # caller passes: next(after)

Store.tick(now DATE, dryRun bool) -> TickResult
  TickResult {
    fired  [FiredTickler]    # fired[].id, kind move|spawn,
                             #   spawned ID | null, tickled DATE
    errors [TickError]       # per-item: id, error — never fatal
  }
```

`tick(now)` is date-granular like every other operation in the format — the
service passes "today". A schedule's `@HH:MM` is evaluated *inside* the
library's calendar math (next Monday 08:00 is a real instant in the process's
zone), but a caller that can only express dates (a daily cron) still gets the
right answer: `tick` takes the current date and fires anything whose due
instant falls on or before it, which is exactly "the next fire after `last`
is today-or-sooner". A UI service with a minute clock can pass its timezone's
today; nothing in the data needs the clock.

## 7. Why the format does not need a clock

The format spec §3.3.1 records dates, never times, and §10.1 defends the
choice (a clock in a hand-edited file is a field people get wrong). The
tickler keeps that discipline:

- The data files record **dates only**: `tickler`'s schedule expression and
  the `tickled` stamp. The checker (I7) validates the *shape* of the
  expression — a real calendar date, a known weekday, a legal time — and never
  evaluates it. A schedule cannot make a directory invalid because a clock
  disagrees.
- The `@HH:MM` time lives only inside the expression, and only the evaluating
  process reads it, in its own zone. Two processes with different zones see
  the same data; their *judgement* of "due" can differ by an hour, which is
  exactly the wall-clock behaviour a "Monday at 8am" promise implies.

## 8. Triggers — the flexibility the task asks for

`Store.tick` is library code with no scheduling of its own. Three ways to run
it, any subset at once (§5 makes overlap safe):

1. **CLI, once** — spec-tools §5.3 gains an optional operation:

   | Switch | Behavior |
   |---|---|
   | `--tick [--dry-run]` | Run the tickler once: fire every due someday item. MUST report what fired and what errored. Default: manual, like every other operation. |

   This is the cron/systemd surface:

   ```
   # /etc/systemd/system/mm-tickler.timer
   [Unit]
   Description=run the micro-manager tickler every minute
   [Timer]
   OnCalendar=minutely
   Persistent=true            # a missed run fires on boot
   [Install]
   WantedBy=timers.target

   # /etc/systemd/system/mm-tickler.service
   [Service]
   ExecStart=/usr/local/bin/mm --tick --dir /srv/boards/todos
   ```

2. **UI service, continuously** — spec-gui §2 gains a subsection: the UI
   service MAY run `Store.tick` on a configurable interval (config key
   `tickler.interval`, e.g. `1m`, default **off**). Opt-in because a process
   that mutates the board on its own initiative should not start quietly
   (same principle as §5.3.1's "nothing archives on its own initiative").
   When it fires something, the client learns on the next SSE refresh; a
   dedicated SSE event is a MAY.
3. **Library callers** — anything else embedding the library calls `tick` on
   its own schedule.

The UI service serves several boards; it runs `tick` per directory it holds.

## 9. The UI (spec-gui changes, filed as T-0171)

- **Controls, not free text.** The new-item panel (§5.6), when the section
  selector says Someday, shows a "Wake up" group (testids `tickler-kind`,
  `tickler-date`, `tickler-weekday`, `tickler-ordinal`, `tickler-monthday`,
  `tickler-time`): kind select (never / one-time / weekly / monthly), the
  matching date/weekday/ordinal/monthday input, and an optional time input.
  The form POSTs the control values and the **server composes** the
  `tickler:` value — the grammar lives in one place, the library validates on
  write, and the checker would catch any leak. A recurring schedule carries
  the copy: "This item stays in Someday and creates a new Ready item each time
  it fires."
- **The item panel** (edit form) shows the same group for a someday item that
  carries `tickler`, pre-filled from the parsed schedule; clearing it removes
  the field. One partial serves both panels.
- **Next-fire on the board.** A someday card with a `tickler` carries
  `data-tickler="<schedule>"` and a text badge (testid `item-<ID>-tickler`)
  like "next Mon 08:00" or "next 2026-09-01", computed server-side with
  `Schedule.next(today)` on every board render — §11 rule 2: never a
  colour-only or tooltip-only affordance.
- **TUI** (spec-tui): a someday listing MAY show the next fire beside the
  item. No normative requirement; noted, not tasked.

## 11. Open questions the proposal answers

- **Times in the data?** No — inside the expression only, wall-clock in the
  evaluator's zone (§7). The format keeps its date granularity.
- **One-shot vs recurring is a property of the value**, not a separate flag:
  a bare date is one-shot; a weekday/monthday spec recurs. The prototype case
  needs no marker beyond a recurring `tickler`.
- **Two runners at once?** Safe, by the `tickled` guard + rule 5 (§5).
- **A scheduled item dragged to Ready?** Legal; the move clears `tickler` (§3).
- **A spawned copy's detail?** None — I9 forbids sharing the prototype's file
  (§3). The prototype's detail is its own; the spawned copy starts bare.
- **Backdated one-shot?** Fires on the next run (overdue semantics, §4).
- **`created` required?** Yes, on tickler items, so a never-fired recurring
  schedule has an anchor (§2).
