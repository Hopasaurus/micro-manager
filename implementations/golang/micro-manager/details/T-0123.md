# T-0123 — Library: `mm fix` — repair of I1 duplicate / I2 ceiling

Implementation task following the T-0101 spike (decision 4 of
`implementations/golang/project/plan-git-support.md`). The repair targets
exactly the two findings a git merge manufactures — the I1 duplicate and the
I2 ceiling — nothing else. **Gated on T-0122**: the repair refuses to run
while conflict markers remain, which needs the marker rule to exist first.

## Why

Reproduced in T-0101: two branches both `mm add` against the same committed
`next_id`, both allocate `T-0043`, git auto-merges with no conflict markers,
and the directory ends up with two `T-0043` items. `next_id` merged cleanly
(both sides made the same change); the validator is the only detector. The
collision cannot be prevented without a lock, which the format's no-server
promise forbids — so the repair is the answer, and it doubles as the repair
for a hand-edited directory that broke I1/I2.

## Semantics (from the plan, decision 4)

1. **Refuse to run while the directory is not loadable** — markers now make it
   unloadable (T-0122); the caller must resolve git conflicts first.
2. **`next_id` becomes `max(current next_id, max ID in use + 1)`** — never
   lowered, so I2's monotonicity holds by construction.
3. **For each ID that appears more than once** (in one file or across files,
   which is I1): keep the item in the most advanced home — `done.md` beats a
   working file, which beats `backlog.md` — and among equal homes the earliest
   `created`; renumber the losers to fresh IDs drawn from `next_id`, bumping
   it as it goes.
4. **A renumber updates the item line *and* renames `details/<old>.md` to
   `details/<new>.md` in the same transaction** — the I9 coupling, the
   sharpest rule in the format and the easiest to break. A loser with no
   detail file needs only its item line.
5. **Ties (same home, same `created`) refuse with both items named** rather
   than guessing — the repair must never invent an answer a human should give.
6. **Dry-run prints the exact splices**; the real run goes through the
   transaction envelope — read, modify, validate, write atomically. Running
   twice is a no-op. The repair is not git-aware and must not be: the same
   command fixes a hand-broken directory.

## What to build

- A new library operation (mirroring how `Add`/`Move`/`SetWipLimit` are built),
  exposed through the CLI as `mm fix` (probably with `--dry-run`; follow the
  CLI conventions T-0030–T-0034 established). The library package stays
  third-party-free and print-free; rendering is the CLI's job.
- The transaction baseline rule applies: capture state at begin, validate
  before commit.

## Verify

- Build the 3.1 reproduction as a fixture: a board with two `T-0043` items
  (one with a detail file, one without), `next_id: T-0044`. `mm fix --dry-run`
  matches the real run byte for byte; after the run check.sh is green, the
  kept item still has its ID, the loser is renumbered to a fresh ID, its
  detail file (if any) is renamed in the same commit, and `next_id` is bumped
  exactly once to cover the new high ID.
- A second fixture: the same ID in two homes (e.g., `backlog.md` and
  `working.01.md`) — the keep rule picks the working file; and a tie case that
  must refuse with both items named.
- The reading battery and the rest of the suite stay green; `go test ./...`,
  `go vet ./...`, and `./check.sh --all` pass.
