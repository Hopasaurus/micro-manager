# T-0111 — Close the drag-behaviour test gap: non-displacing placeholder and/or a JS test runner (T-0110 follow-up)

Follow-up to **T-0110**, whose fix shipped with a weak guard.

The drag bug was a feedback loop: `hoverTarget` inserts the drop placeholder
between cards, displacing every card below it, and the next `dragover` measured
`getBoundingClientRect` while it was still there. The index stayed pinned and
dragging down became a no-op.

The fix (clear placeholders before measuring) is correct, but the regression
guard in `dragdrop_test.go` is a **source-shape assertion**: it checks that the
clear appears before the measure in `mm.js`. It catches a literal reordering of
those two statements and nothing else. A different reintroduction of the same
feedback loop — a second placeholder, a CSS change that gives some other
inserted node height, a rewrite of the handler — passes it.

Two ways to close that gap. They are different in kind, and the interesting
question is which to reach for next time.

## Option A — make the placeholder non-displacing

Take the placeholder out of layout flow (`position: absolute`, or render it as a
border/outline on the card it precedes) so inserting it cannot move anything.
The feedback loop stops being a bug you avoid and becomes one that cannot exist.

**For**

- Removes the whole bug class, permanently. No ordering discipline to remember.
- Cheap: CSS plus a small change in `hoverTarget`. No new tooling, no CI cost.
- Keeps the measurement code simple — geometry is stable for the whole drag.

**Against**

- The placeholder currently communicates the insertion point *by occupying the
  gap*. Absolute positioning has to reproduce that affordance, and inside a
  scrolling column with variable card heights that is fiddlier than it sounds.
- Buys nothing for any other client behaviour.
- Still leaves zero behavioural coverage: the fix would be verified by eye once
  and then trusted forever, exactly as before.

## Option B — add a JS test runner

Real coverage for `mm.js`: drag and drop, the keyboard move mode of §7.4, the
card menus, toasts, the SSE wiring.

**For**

- Would have caught T-0105 and T-0106 outright — both were "the handler does
  nothing", which needs no layout to detect.
- `mm.js` is the largest untested surface in the service. Everything else has
  tests; the client script has source-shape greps.
- Makes future client work verifiable instead of browser-checked by hand.

**Against**

- New toolchain in a Go repo. Weigh against the guest rules in `AGENTS.md`
  before committing to it.
- **jsdom would not have caught T-0110.** jsdom does no layout:
  `getBoundingClientRect` returns zeroes, so every midpoint comparison collapses
  and the bug is invisible. Catching a layout-dependent bug needs a real engine —
  Playwright or similar — which is a heavier dependency and a slower CI.
- Synthetic drag events are their own trap. During T-0110 the browser tool's
  `left_click_drag` fired a single `dragover` at an intermediate point and often
  no `drop` at all; it neither confirmed nor refuted the bug. What settled it was
  dispatching `DragEvent`s in sequence and reading `data-drop-index` back. Any
  drag test has to drive events explicitly and assert on the attributes §7.3
  already fixes — which is precisely why those attributes are normative.

## Doing both

Yes, and they are complementary rather than redundant.

A removes this bug class now, cheaply, and reduces what B has to be able to
express. B covers the rest of `mm.js`, most of which does not depend on layout
and so is testable with the lighter runner.

Recommended order: **A first, then B.** A is small and makes the failure
impossible; B is a standing investment that should not block it. Doing B first
means building layout-capable browser testing to protect a line of code that A
would delete the need for.

## Which to reach for next time

The deciding question is **whether the behaviour depends on real layout**.

- **Wiring bugs** — a handler that does nothing, a missing attribute, an
  operation posting an empty body (T-0105, T-0106) — need no layout. A light
  runner catches them, and they are worth testing because they are invisible to
  Go tests and cheap to assert.
- **Layout-coupled bugs** — anything comparing coordinates, measuring elements,
  or mutating the DOM it is about to measure (T-0110) — cannot be caught by
  jsdom at all. Prefer the structural fix that removes the coupling. Reach for a
  real browser only when the behaviour genuinely cannot be made layout-independent.
- **When a bug is a feedback loop** — the code mutates the thing it measures —
  treat the structural fix as the primary work and the test as secondary. A test
  pins one instance; removing the coupling removes all of them.
- **Source-shape assertions** (the current guard, and the ones in
  `dragdrop_test.go`) are honest only when the invariant is genuinely textual: a
  testid that must not be renamed, a key binding that must stay bound. Using one
  to protect a *behaviour* is a placeholder for a real test, and should be
  labelled as such where it sits.
