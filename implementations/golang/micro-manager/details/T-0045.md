# T-0045 — Implement stats: throughput, cycle time, WIP over time

## As built

`mm/op_stats.go` — `Store.Stats(Period, StatsOptions, today) (StatsResult,
error)` — and `mm --stats`, the third optional operation of `spec-tools.md` §5.3
to be wired. Four measures, all derived from the three dates the format records:

| Measure | Definition |
|---|---|
| throughput | items closed per bucket, plus the split by outcome |
| cycle time | `done` − `started` in whole days: mean, median, p90, range |
| in flight | items between `started` and `done`, per day: peak, the day, mean |
| tags | closed items distributed over their tags, untagged counted apart |

`--bucket day|week|month` sets the resolution of the series; a week is the
default, being the unit `--report` is built around.

## What the numbers can and cannot mean

This is the whole design problem, and it is a data problem rather than a code
one. `spec-file-format.md` §10.1 makes every date date-granular, and §5.2 resets
a slot on pause, so:

- **"WIP over time" cannot mean slots occupied.** A pause leaves no trace, so an
  item paused for a month still reads as in flight for that month; and intra-day
  concurrency is not recoverable at all, so a board that starts and finishes ten
  items in one day reads as ten in flight that day. On this repository's own
  board that is a peak of 33 against a WIP limit of 4 — a number that would be
  nonsense if it claimed to be WIP. It is therefore called **in flight**
  everywhere the user can see it, and a CLI test asserts the word "WIP" does not
  appear in the output. §10.7 is the same point from the other side: the limit is
  not recorded historically either.
- **An item with no `started` has no cycle time**, and is counted as unmeasurable
  rather than assumed to have started when it was created. Same for `done`
  before `started`: neither date is invalid on its own so I7 says nothing, and
  averaging it in would hide it.
- **A same-day item has a cycle time of 0 and one day of flight.** Both follow
  from the granularity; neither is a rounding choice made here.

## Decisions

**The period defaults to ALL of history**, where `--report` defaults to last
week. Throughput and cycle time over seven days are a sample; the question
`--stats` answers is usually about the trend. An unbounded period has no start
to cut buckets from, so it takes one from the data: the earliest date the
directory holds, through today.

**`MM_REPORT_PERIOD` does not apply.** It is documented as the default `--report`
period, and stats is not a report — a variable set for one operation must not
silently narrow another. `resolvePeriod` was split for this: `periodFromSwitches`
holds steps 1–3 of §5.1.11, which both operations share, and each supplies its
own default and decides whether the environment step applies.

**Rendering stays in the CLI**, unlike `Report.Markdown()`. That renderer is in
the library because spec-gui.md §5.7 requires the GUI to put the same bytes on
the clipboard. Nothing requires that of stats, and a layout is not a rule.

**The human output shows the top ten tags**, with `+N more`; `--json` and
`--porcelain` carry all of them. Forty tags on one wrapped line is not a
distribution anyone reads.

## Verification

- `mm/op_stats_test.go`: a four-item fixture where every number is checkable by
  hand — throughput per week, outcomes in fixed order, cycle time (mean 3,
  median 2, p90 6 by interpolation, one unmeasurable), the daily flight series
  (peak 2 on the 2nd, mean 12/13), an open item still counted, tags with a
  two-tag item counted twice, all three bucket sizes, an unbounded period taking
  its range from the data, an empty directory producing no series rather than a
  panic, and archives in and out with the warning either way.
- `internal/cli/stats_test.go`: the four measures end to end, the "in flight"
  wording, the period default and that `MM_REPORT_PERIOD` cannot narrow it, JSON
  and porcelain, two bad arguments, and the archive warning.
- Run against this repository's own board: 140 closed, mean cycle 0.0d, flight
  peaking at 33 on 2026-07-31 — the number that named the measure.
