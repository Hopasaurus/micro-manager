# T-0251 — Give Working an add control, WIP badge and dimmed-when-full state

Reported live: Working has no "+" for adding tasks, and should — dimmed once
the stage's WIP limit is reached. Also requested: any stage carrying a WIP
cap should show its used/limit count just to the left of the "+", in the
stage's own theme color normally, switching to an alert color once full.

## Library fix first

`--add --stage working` was already legal per `spec-tools.md` §5.1.2 ("SLUG
MUST be a member of the directory's declared stages" — no working
exception), but nobody had exercised it end to end: `addV2`/`addManyV2` had
no WIP-limit check at all (unlike `moveV2`, which already refuses a full
destination), and `buildNewItemV2` never stamped `started:`, which I7
requires of any `working` item — so a direct add would have failed
transaction validation the moment someone tried it.

- New `checkStageWipLimit(b, stage)` in `mm/board_ops.go`, generalized to any
  `wip.<slug>` cap (not hardcoded to working), called from both `addV2` and
  `addManyV2` right after the request is validated and before an ID is
  allocated — so a full stage fails before anything is written, and
  `AddMany`'s existing all-or-nothing guarantee covers it for free.
- `buildNewItemV2` now stamps `Started: today` when `stage == "working"`,
  mirroring `moveV2`'s own `--move --stage working` stamp.

## GUI

Generalized past the literal "Working" example to any WIP-capped stage,
consistent with this codebase's stance elsewhere (custom stages get the same
treatment as the built-in four):

- `internal/web/board.go`: v1's working columnData now also carries
  `WipCapped`/`WipUsed`/`WipLimit` (structural: v1's cap is always
  `len(Slots)`), so v1 gets the visible badge even though it still has no
  add control (v1 has no `--add --stage working` at all — a v1 item only
  reaches working via `--start`, so this fix is v2-only for the add link,
  same as before). v2's per-stage loop already carried these fields for
  every capped stage; only the stale comment claiming working never gets an
  add link was removed.
- `internal/web/templates/partials/board.html`: the add-control gate changed
  from "never on working" to "never on working *unless it's a v2 column*"
  (`$c.Stage` is only ever set there). A capped column now renders a
  `board-column-<slug>-wip` badge (`used/limit`) immediately before the add
  control, colored with the same `color.state.<slug>` token the column
  border already reads (falling back to `accent.base`), switching to the
  required `feedback.danger` token once `used >= limit`. When full, the add
  control itself renders as a disabled `<button data-reason="WipLimitReached">`
  instead of the normal `<a>` — the same present-but-disabled convention the
  item action menu already uses, rather than hiding it.
- `internal/web/static/mm.css`: `.mm-column__wip` takes over the `+`'s old
  `margin-left: auto` (with `.mm-column__wip + .mm-column__add { margin-left:
  0 }` so the two stay adjacent when both are present), plus a disabled-state
  rule for `.mm-column__add` mirroring `.mm-item__action[disabled]`.

## Spec

- `spec-tools.md` §5.1.2: documented that `--stage` accepts `working` with
  no exception, that its WIP cap is pre-commit-validated the same way
  `--start`/`--move` already enforce it, that `--add --stage working` stamps
  `started:` (mirroring §5.1.7's existing note for `--move`), and added
  `WipLimitReached` to the Errors list.
- `spec-gui.md` Appendix A: added `-wip` to the column child list; the old
  "board-column-working does not [carry -add]" parenthetical was replaced
  with the real v1/v2 split. §5.5 gained a paragraph describing the visible
  badge (colors, capped-only) and the disabled-when-full add control.
