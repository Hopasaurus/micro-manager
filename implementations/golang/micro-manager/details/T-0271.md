# T-0271 — Research markdown parsing and presentation in the UI

Research markdown parsing and presentation in the UI

This will be used to show the detail in formatted html instead of raw markdown.  It will also be used to expose the structure.md document.

Find a few options that can be used in the front end, probably JS only options.

## Current UI constraints

- The UI is server-rendered with Go templates and progressively enhanced by htmx and `mm.js`.
- Static assets are embedded into the Go binary. The application works as one self-contained executable without a package manager or CDN at runtime.
- Content Security Policy uses `script-src 'self'`, so a CDN import would be rejected and would weaken the existing deployment model.
- Detail and `structure.md` content is editable local data and must be treated as untrusted markup. Markdown rendering must not make embedded HTML, event handlers, or unsafe URL protocols executable.
- The existing JavaScript behavioral suite runs the real scripts under Node and jsdom, so a vendored classic browser build is the lowest-friction test integration.

## Options

### 1. markdown-it — recommended

[markdown-it](https://github.com/markdown-it/markdown-it) is MIT licensed, supports CommonMark, has a browser build, and is extensible through plugins. Its documented defaults disable source HTML (`html:false`), URL auto-linking, and typographic substitutions. That default is a particularly good security and fidelity fit here: Markdown constructs render, while literal HTML remains inert text.

Fit:

- Vendor the minified browser build under `internal/web/static/`, exactly like htmx and Idiomorph.
- Load it before `mm.js`; no build pipeline or runtime network request is required.
- Use one deliberately small configuration: `html:false`, `linkify:false`, `typographer:false`, and the normal CommonMark renderer.
- Direct rendering API and token API leave room for later link rewriting or heading IDs.

Tradeoffs:

- Larger than the smallest parser.
- Plugins expand both behavior and security surface, so add none until a concrete requirement exists.
- Although disabling HTML prevents the primary injection path, rendered links still need tests for unsafe protocols and external-link policy.

### 2. micromark — strongest safe-by-default alternative

[micromark](https://github.com/micromark/micromark) is MIT licensed, fully CommonMark compliant, small, heavily tested, and explicitly safe by default: embedded HTML is encoded and dangerous link/image protocols are dropped unless dangerous options are enabled.

Fit:

- Best option if exact CommonMark behavior and parser-level safe defaults outweigh integration simplicity.
- Its extension ecosystem can add GFM features later.

Tradeoffs:

- It is ESM-only. Official browser examples use an external ESM bundling service, which conflicts with the self-hosted CSP and offline single-binary model.
- Adopting it cleanly means introducing a small asset build/bundle step and deciding how generated vendor artifacts are updated and verified.
- Its syntax-tree ecosystem is powerful but unnecessary for the initial render-only use case.

### 3. Marked plus DOMPurify — easy API, two-library security boundary

[Marked](https://marked.js.org/) is MIT licensed, fast, extensible, and provides both UMD and ESM browser builds. Its own documentation explicitly warns that it does **not** sanitize generated HTML and recommends filtering output with a sanitizer such as [DOMPurify](https://github.com/cure53/DOMPurify).

Fit:

- Very simple `parse(markdown)` integration and easy browser vendoring.
- DOMPurify is mature, browser-native, and can return sanitized HTML or a DOM fragment.

Tradeoffs:

- Requires two vendored libraries and makes correct configuration/order a security invariant: parse first, sanitize second, then insert.
- DOMPurify's broad default HTML/SVG/MathML profile is more permissive than this feature needs; it should be restricted to an HTML-only allowlist with style, SVG, MathML, forms, media, and active attributes excluded.
- More update and security-advisory maintenance than a parser that safely escapes source HTML by default.

## Recommendation

Use a vendored, version-pinned `markdown-it` browser build with source HTML disabled. It is the smallest architectural change, preserves the single embedded binary and current CSP, and provides enough CommonMark support for task details and `structure.md` without introducing a JavaScript bundler or a second sanitizer dependency.

Do not allow raw HTML in the first implementation. The source files are meant to remain portable Markdown, and neither current use case needs arbitrary HTML. If raw HTML becomes a real requirement later, add DOMPurify as an explicit second layer and test a narrow allowlist; do not enable `html:true` alone.

## Suggested implementation shape

1. Vendor a pinned `markdown-it` browser artifact plus its license in `internal/web/static/`; record the upstream version and checksum/update procedure.
2. Add a small renderer in `mm.js` that finds escaped Markdown source, calls one shared configured parser, and replaces only the designated preview container.
3. Keep the Markdown source HTML-escaped in a hidden `textarea` or inert template. Read it with `.value`/`.textContent`; never interpolate raw file text into a script literal.
4. Render detail preview in the item panel while retaining the raw Markdown textarea for editing. Re-run enhancement after htmx swaps.
5. Add a read-only `structure.md` route/view using the same renderer and stylesheet. Missing `structure.md` should produce the existing not-found presentation, not a blank document.
6. Add scoped `.mm-markdown` styles for headings, paragraphs, lists, task lists, blockquotes, links, inline code, fenced code, tables, and horizontal rules.
7. Test ordinary Markdown, HTML/event-handler payloads, `javascript:` links, malformed nesting, empty/missing files, htmx replacement, keyboard/focus behavior, and very large input. Cap rendered source size to avoid freezing the browser.

## Open product questions for implementation

- Should detail panels open in rendered preview mode with an explicit Edit action, or continue opening directly in the textarea with a preview alongside it?
- Where should `structure.md` be linked: project navigation, an About/help surface, or both?
- Is CommonMark sufficient initially, or are GFM tables, strikethrough, and task-list presentation required? The current files use tables and task-list syntax, so enabling only the specific GFM features actually encountered may be worthwhile.

## Conclusion

No production code change is needed for this research task. A follow-up implementation should choose `markdown-it`, keep raw HTML disabled, vendor the asset locally, and use one shared rendering path for details and `structure.md`.
