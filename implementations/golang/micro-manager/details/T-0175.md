# T-0175 — Plugin skeleton and install: directory extension, package.json, mm-on-PATH check

From [[project/spec-pi-mm-plugin.md]]. Build the directory-form extension per spec §2, §3.1: index.ts factory, helper modules, typebox + pi packages only. Verify mm on PATH at session start and degrade loudly but gracefully when absent (tools error, no context injection, name what to install). Source dir in this repo must NOT be named micro-manager (check.sh treats it as a todo directory); the installed copy in pi's extension dir is named micro-manager.

## As built

`plugins/pi-mm/` — the directory-form extension, loadable by pi today:

```
plugins/pi-mm/
  package.json        pi.extensions -> ./src/index.ts; deps: typebox only
  tsconfig.json       types only; pi runs the TypeScript through jiti
  README.md           install, requirements, why the directory is not named micro-manager
  src/index.ts        the factory: lifecycle, the health gate
  src/presence.ts     the mm-on-PATH probe
  src/*.test.ts       node --test, no framework, no build step
```

- **`src/index.ts`** registers `session_start` (probe, then either a status line
  naming the build it will drive, or one `warning` notification saying what to
  install) and `session_shutdown` (nothing to release — the handler exists so
  that stays a statement rather than an omission). It registers no tools and no
  command: those are T-0178 onward, and half a tool would be worse than none.
- **`src/presence.ts`** is the whole "is `mm` usable" question — one probe,
  cached for the session, three distinguishable failures (`not-found`,
  `failed`, `timeout`) because they need different words, and one message that
  names the remedy. Nothing else in the plugin spawns `mm`; that is the
  runner's job (T-0176).
- **`health()`** in index.ts is the gate every later tool calls first. It lives
  above the probe so that later gates — a board that will not resolve, an `mm`
  too old for an operation — join it in one place a caller checks once.

## Decisions

**The source lives at `plugins/pi-mm/`, not in `implementations/typescript/`.**
The spec's §3.1 named the latter as "a natural home", written when that
directory was an empty placeholder. It is now a whole TypeScript implementation
of the format — library, CLI, service, web client, with its own solution build,
its own vitest, and an AGENTS.md whose rules ("the library is a guest, no
`console.*`") are about a different deliverable. The plugin is an agent-side
companion that drives the **Go** `mm`; enrolling it in that workspace's `tsc -b`
would couple two unrelated things. **The spec was updated in the same session**
to name the real location and say why, rather than leaving a doc that points
somewhere the code is not.

**Node's own test runner, no framework.** Node 26 strips types natively, so
`node --test src/*.test.ts` runs TypeScript with zero devDependencies of its
own. The tests spawn **real shims** — a `#!/bin/sh` file in a temp directory —
rather than faking `spawn`, because what is being tested is precisely what a
fake would paper over: ENOENT, a non-zero exit, a process that hangs. A stub
that "returns not-found" proves nothing about not being found.

**typebox is pinned to 1.1.38, the version pi itself ships.** A floating range
would resolve a second copy of the schema library into a process that already
has one.

**§8.1's conformance smoke test, from the first commit.** The spec suggests
grepping the source for board filenames. A filename grep alone is both too weak
(a path can be assembled) and too strong (prose describing a board is not a file
access), so the test does two things: **no plugin module imports `node:fs` at
all** — you cannot read or write a board without it, and the plugin's one way
out to the world is spawning `mm` — and no board filename appears **inside a
string literal**. It also asserts it scanned at least two modules, because a
smoke test that silently covered nothing is the failure mode this file cannot
afford.

That test earned its place immediately: it failed on the first run against
index.ts's own header comment, which is what sent the rule to "string literals,
not prose".

## Verification

- `npm test` — 14 cases: the probe's six shapes (version on stdout, version on
  stderr, multi-line, ENOENT, non-zero exit, hang), the message naming the
  remedy for all three failures, the once-per-session cache, and the factory's
  registration, both degradation paths, `health()`, and §8.1.
- `npm run typecheck` clean under `strict` + `noUncheckedIndexedAccess` +
  `exactOptionalPropertyTypes` + `erasableSyntaxOnly`.
- `pi --list-models -e ./src/index.ts` loads the module through pi's own jiti
  loader without error — the real check that the entry point is loadable.
  Driving a full `session_start` inside pi needs a model turn, so that path is
  covered by the unit tests instead of by spending the user's tokens.
- `./find.sh` does not match `plugins/pi-mm`, and `./check.sh --all` still
  reports 8 clean directories — the naming rule that §3.1 is about.

## Not done

Everything else in the spec, on purpose: the runner and exit-code mapping
(**T-0176**), board resolution and the pin (**T-0177**), the read/write/workflow
tools (**T-0178**–**T-0181**), `/mm` (**T-0182**), context injection
(**T-0183**), and the conformance suite (**T-0185**).
