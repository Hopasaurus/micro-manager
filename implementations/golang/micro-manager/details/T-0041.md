# T-0041 — Implement theme and config loading for the UI service

## Context

Written as a low-priority blocked item while the library was being built,
because nothing consumed it. `spec-gui.md` is now being implemented, so it is
unblocked and on the critical path: the app shell cannot render without resolved
tokens, and the settings views cannot write without a merge rule.

It lives in the library, `mm/config.go`, not in `internal/web`, because the TUI
reads the same files with the same precedence and must agree byte for byte
(`spec-gui.md` §8.5, §13).

## Requirements

**Config** (`spec-gui.md` §9)

1. Two locations: `$XDG_CONFIG_HOME/micro-manager/config.json` (system) and
   `<micro-manager dir>/config.json` (project). Both optional; missing is an
   empty object. `XDG_CONFIG_HOME` defaults to `$HOME/.config` when unset or not
   absolute — and the **path arrives as a parameter**, because the library must
   not read the environment (`spec-tools.md` §2.2).
2. Merge is built-in defaults, then system, then project, **per leaf key, not
   per object**: a project overriding `ui.density` must not discard the system's
   `ui.defaultView`.
3. System-scoped keys are never overridable. A project config setting
   `ui.recentCount`, `ui.favoritesCount`, `ui.recentMaxStored` or anything under
   `server` is a **validation warning naming the key** — present-but-ignored is
   explicitly not acceptable (§9.3).
4. A project `config.json` is outside the file-format spec and MUST be ignored by
   format readers and the checker. It never participates in I1–I10.
5. The `tui` object is reserved for the terminal front end. The GUI ignores it
   and **preserves it on write** (§9.3).

**Theme** (`spec-gui.md` §8)

6. Resolution order, first hit wins: project `theme.json`; the theme named by
   project config `theme.id` from the library; system `theme.json`; the theme
   named by system config `theme.id`; the built-in default.
7. Missing tokens fall through to the built-in default **per token, not per
   file** — a project theme setting only `accent.base` and `brand` is valid and
   common (§8.7).
8. The full `color` and `gui` token sets of §8.3 exist as a built-in default that
   passes the §11 contrast requirement. Values are `#rrggbb` or `#rrggbbaa`;
   validation reports each bad token **by path**.
9. `appearance` is `light`, `dark` or `auto`; `auto` requires both `color` and
   `colorDark`.

**Shared to both**

10. **Unknown keys are preserved on read-modify-write**, everywhere, in config
    and theme alike. Two front ends over one set of files will otherwise strip
    each other's settings on alternate runs, each correctly writing back only
    what it knows (§9.4). A round-trip test over a file containing keys this
    implementation has never heard of is the acceptance criterion.
11. Writes are atomic and target **one scope explicitly**. There is no "write to
    whichever file it came from".
12. Every date and timestamp is ISO 8601 extended, timestamps with a `Z`
    designator (§8.2). Never a locale form, never epoch seconds.
13. No `server.*` value may be settable through anything the UI can reach
    (§9.6 rule 4) — the loader may read it, and the settings writer must refuse
    it.

## As built

`mm/config.go` and `mm/theme.go`.

**The raw document is the source of truth.** `ConfigFile` and `Theme` both keep
the decoded JSON they were read from and apply changes to *that*, so a key this
implementation has never heard of survives a write because it was never dropped.
Decoding into a struct and re-encoding is precisely the mistake §9.4 exists to
prevent, and the tests prove it with a file carrying `tui`, an unknown key inside
a known object, and an unknown top-level object.

**Typed view for reading, raw document for writing.** `MergeConfig` folds
defaults, then system, then project onto a `Config`, leaf by leaf. A malformed
value is a warning and falls back to the layer below rather than failing the
load: a front end that will not start because of one bad value is worse than one
that starts and says which value it ignored.

**System-scoped keys are refused twice.** `MergeConfig` ignores them in a
project file and names each one; `ConfigFile.Set` refuses to write them there at
all. `SettableFromUI` is a third gate for §9.6 rule 4 — nothing under `server`
may be written by any settings screen, in either scope — and it lives in the
library so the GUI and the TUI cannot disagree about it.

**Resolution is per token, and a dark-only theme supplies both renderings.** A
theme declaring `appearance: dark` with one `color` set would otherwise render
the built-in *light* palette in dark mode, because `colorDark` was empty. Its own
palette is used for both.

**Contrast is measured, not assumed.** `ContrastRatio` is WCAG 2.1 relative
luminance, and a test asserts the built-in passes AA on both required pairs in
both appearances. The editor will warn and must never block saving (§11 rule 7).

## Open question for the spec

`spec-gui.md` §8.4 says **every** `color` and `gui` token is exposed as a custom
property, and §8.3 lists `density.{compact,normal,comfortable}` under `gui` — but
Appendix B does not list `--mm-density-*`. This implementation emits them, since
§8.4 is the normative sentence and the appendix is an index. Appendix B is
probably the thing to correct, but it is a spec edit and has not been made.

`TestCSSPropertyNamesMatchTheSpecIndex` parses Appendix B out of the spec file
itself and asserts every name in it is emitted. It is deliberately a subset
check, which is what lets the two coexist until the spec is settled.
