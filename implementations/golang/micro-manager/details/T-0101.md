# T-0101 — Explore how this could interoperate with git, consider how merge conflicts with overlapping task IDs could be solved.

Plan only, save the plan to project/plan-git-support.md

## Update (post-ship)

The plan is written to `project/plan-git-support.md` (status: proposed). It
measures, rather than assumes, what git does to the format:

- **The headline finding is a real, reproduced merge**: two branches, one
  base, both `mm add` against the same `next_id` — git auto-merges with no
  conflict markers and the directory ends up with two `T-0043` items. The
  validator is the only detector; the `next_id` line merged cleanly because
  both sides made the same change.
- **A latent hole found by probe**: conflict-marker lines (`<<<<<<<`,
  `=======`, `>>>>>>>`) are *legal prose* under spec §5.1, so both validators
  silently absorb a half-resolved merge — when the two sides carry different
  IDs, it passes with zero findings.
- **Decisions**: git is transport, never part of the format contract;
  collisions are solved by detection plus a deterministic `mm fix` repair
  (never by locks, per-branch prefixes, or custom merge drivers); markers
  become a format violation; `mm` never auto-commits.
- **Proposed follow-ups**: T-0121 (spec: marker carve-out in §5.1), T-0122
  (both validators reject markers, corpus fixture, oracle lockstep), T-0123
  (`mm fix` with dry-run and the I9 detail-rename coupling, tested against the
  reproduced merge and a hand-broken I1/I2 directory), plus a SKILL.md
  git-workflow section. None are registered in the backlog yet — the spike is
  plan-only by its detail.
