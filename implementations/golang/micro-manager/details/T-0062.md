# T-0062 — Render home and the projects list with favorites

## Context

These are the two views that make the service navigable. Until this item a
project could only be reached by typing its id into the URL: `/` and `/projects`
both 404ed, and the project switcher in the header rendered empty because
nothing wrote the recent list.

## As built

`internal/web/home.go`, `templates/home.html`, `templates/projects.html`,
`templates/partials/project-card.html`.

**One card template.** Home and `/projects` render the same
`project-card-<projectId>`, so a project looks and locates identically wherever
it is listed.

**Opening a board records it** (§10 rule 1) — the gap this item closed.
`registry.touch` existed and was tested since T-0048 but nothing called it.
It is called on a **full page load only**: an htmx fragment refresh or a poll is
not an "open", and a window left sitting on a board would otherwise rewrite the
recent list forever. A failure to write is logged and swallowed, because not
being able to write a convenience list is not a reason to refuse to show
somebody their board.

**Empty lists render their container** with `data-count="0"` and
`data-state="empty"` (§5.4). A suite has to be able to tell "no favorites" from
"the view forgot to render favorites".

**A missing project is rendered, not dropped** (§10 rule 5) — `data-missing`,
a visible "not reachable", and removal left as an explicit choice.

**One route toggles a favorite**, because the control is one button whose
`aria-pressed` says which way it will go. Two routes would let the client and
the server disagree about the current state.

**A truncated scan says so** (§5.3): `data-partial="true"` plus prose naming the
two limits to raise. A silently truncated list is indistinguishable from a
missing project.

## A spec inconsistency, not acted on

There are **three exclude lists** and they disagree:

| Source | Excludes |
|---|---|
| `find.sh`, the reference tool | `.git .hg .svn .claude node_modules vendor target dist build .venv venv` |
| `mm.DefaultDiscoveryOptions` | the same eleven |
| `spec-gui.md` §9.2 `scan.excludes` | `node_modules .git target vendor .venv dist` — six |

The config default omits `.claude`, `.hg`, `.svn`, `build` and `venv`. This
implementation follows §9.2, because that is the sentence that binds the config
file — and the visible result is that `/projects` lists
`.claude/skills/micro-manager`, the *skill* directory, as a project, while
`mm --find` does not list it.

The two front ends therefore disagree about which projects exist, which is
exactly what §9.5 exists to prevent. The one-line fix is to bring §9.2's
`excludes` into line with `find.sh`. **Not made:** it is a spec edit, and the
standing rule is to surface these rather than guess.

## The browser found the cosmetic one

The scan-root heading was uppercased by CSS. That heading is a filesystem path,
and paths are case-sensitive on most systems this runs on, so shouting one at
the user misrepresents it. Uppercasing stays on the Home list titles, which are
words.
