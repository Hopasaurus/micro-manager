# T-0241 — Decide and implement --init's version-2 story (spec-tools.md §5.1.1 already describes v2 output)

Raised and deferred three times during the v1→v2 migration
([T-0230.md](T-0230.md), [T-0234.md](T-0234.md), [T-0235.md](T-0235.md), all
"--init still only creates version-1 directories; M2/M3 will want to decide
whether --init needs a direct-to-v2 path or whether --init-then-migrate is
the permanent story") but never turned into its own task, and quietly
absent from T-0230's own closing summary despite being named there. Surfaced
again in conversation on 2026-08-21 when asked directly whether `--init`
creates a v2 board — it does not.

## What's actually in the spec today

`spec-tools.md` §5.1.1 describes `--init` **unconditionally in version-2
terms**, with no version modifier of any kind:

> Creates a micro-manager directory: `board.md` with `next_id: T-0001` and
> the default `stages: someday,ready,blocked,working` (format spec §5.1.1),
> `done.md` with no month groups, and `details/` containing `_template.md`.

There is no `--version`/`--to` flag on `--init` anywhere in the spec, and no
mention of a version-1 output ever being a legitimate `--init` result. Read
plainly, this isn't an open design question the spec left for later — the
spec already settled on "init creates v2, always." What's missing is that
`mm/init.go` was never updated to match: it still writes `version: 1`
`backlog.md`/`working.NN.md`/`done.md` unconditionally
(`InitRequest` in `mm/init.go` has no version field at all), and
`internal/web/api/projects.go`'s `POST /api/v1/projects` route inherits the
same behavior since it calls the same `mm.Init()`.

Before implementing, it's still worth confirming there was no real reason
the three deferrals treated this as open rather than obvious — e.g. whether
anything in the migration-chain machinery (`Store.MigrateVersion`,
`spec-tools.md`'s version-history table) assumes every board was *born* at
version 1 and passed through an explicit migrate step. Nothing found so far
suggests it does, but this task should check rather than assume.

## Related gaps found while researching this (2026-08-21)

`--init`'s modifier surface hasn't been updated to the spec's own renamed
vocabulary either, which matters for the same implementation:

- The spec's `--wip-limit N` (§5.1.1) replaced version 1's `--slots N`
  (see the "Corrected" note in that same section) — v2's default is
  **uncapped** when absent, unlike v1's "one working file, effectively
  `--wip-limit 1`". The CLI (`internal/cli/run.go`'s `runInit`) still reads
  `--slots`/`--slot-width` only, and still requires `n >= 1` — v1's
  validation, not v2's "absent means uncapped" semantic. `mm/init.go`'s
  `InitRequest.Wip`/`SlotWidth` fields are named for the old v1 file-count
  concept too.
- `--description TEXT` (§5.1.1: seeds `structure.md`'s first paragraph) does
  not exist anywhere — not in `InitRequest`, not in the CLI, not in the web
  init route. This isn't a version-1-vs-2 issue by itself, just a flag the
  spec documents that was never implemented at all; worth folding in here
  since it's the same function being touched.

## Shape of the decision + work

1. Confirm (per the note above) there's no hidden reason to keep
   init-then-migrate as the permanent story; if none turns up, this
   converges on: `Init()` writes `board.md`/`done.md` at version 2 directly,
   using `DefaultStageConfig()`'s stages.
2. `mm/init.go`: `InitRequest` gains whatever v2 needs (a `WipLimit *int` or
   similar, matching "absent means uncapped" — `Wip int` with a zero-means-
   default sentinel won't express "uncapped" cleanly since 0 already means
   something for v1's slot count); write `board.md` directly instead of
   `backlog.md`+`working.NN.md`. Decide whether the v1 code path stays
   reachable at all (e.g. for `sample-data/`'s deliberately-v1 fixtures,
   built by hand or by `check.sh`'s own test corpus, never via `--init`) or
   whether `Init` drops v1 output entirely now that no spec text describes
   it.
3. `internal/cli/run.go`'s `runInit`: rename `--slots`/`--slot-width` to
   `--wip-limit` (matching §5.1.1's own correction note about the
   `--wip`/`--slots` naming collision), add `--description`, drop the
   `n >= 1` validation in favor of v2's "absent/omitted means uncapped."
4. `internal/web/api/projects.go`'s `initProject`/`initRequest`: same field
   additions, JSON shape parity with the CLI.
5. Tests: `mm/init_test.go`, `internal/cli`'s init tests, and
   `internal/web/api`'s init test all currently assert v1 output — this is
   a bigger test-shape change than T-0236's mutation-guard work, since it's
   the CREATION path itself changing, not a guard added around existing
   v1 logic. `sample-data/`'s own fixtures were NOT built via `mm --init`
   (they predate the v2 redesign entirely, per T-0230's cross-directory
   decision to leave them as-is) so they are unaffected either way.
6. Update `spec-file-format.md`/`spec-tools.md` only if the implementation
   uncovers a real gap in the already-written §5.1.1 text — the spec itself
   looks complete and doesn't need drafting, only reading carefully before
   the Go side is rewritten to match it.

## Notes

**2026-08-21** — Confirmed via `AskUserQuestion` before starting: went with
the full flip (option 1 of 3 offered), since the blast radius question
("internal/cli calls the real `--init` 37 times directly expecting version
1") had a real, contained answer rather than an open-ended one.

**`mm/init.go`**: `Init()` now always writes `board.md`/`done.md` at version
2 (`renderInitBoard`, `renderInitStructureV2`, `validateInitV2`), matching
`migrateOneToTwo`'s own rendering conventions (no `stages:`/`wip.working:`
key when the default applies, same "declares nothing stays byte-identical
to the default" rule version 1's grammar keys already followed). The prior
implementation survives verbatim as the unexported `initV1`
(`validateInitV1`, unchanged), reachable only from this package's own
tests — the same extract-to-sibling shape T-0236 used for the seven guarded
mutation methods, applied here to creation instead. `InitRequest` gained
`Description string` (seeds `structure.md`'s first paragraph, overriding
`NoStructure` since spec-tools.md §5.1.1 says supplying it "makes the
SHOULD a MUST"); `Wip`'s zero-meaning flips per version - `initV1` still
defaults absent to one slot, `Init` treats absent OR explicit zero as
uncapped, matching `SetStageWipLimit`'s own existing "0 clears the cap"
convention (`op_wip.go`) rather than inventing a new one.

**A real, closely-related bug found and fixed along the way**:
`mm/discover.go`'s `IsBoardDirectory` (the Appendix B emptiness test) only
ever checked `backlog.md`/`done.md` - the exact same class of bug T-0236
found and fixed in `fingerprint.go`'s `isOwnedFile`, and spec-file-format.md
Appendix B has *already* documented the three-file check
(`board.md`/`backlog.md`/`done.md`) correctly all along, so this was pure
code/spec drift, not a spec gap. A version-2 board that lost its `done.md`
was undiscoverable (only findable via `backlog.md`, which a v2 board never
has), exactly the "half-deleted board disappears at the moment it needs
attention" failure Appendix B calls out by name. Found because
`mkProject`-built fixtures in `discover_test.go` are version 2 now, and
`TestDiscoverFindsABoardMissingOneFile` broke revealingly rather than
quietly. Fixed by adding `board.md` to the checked list; regression
coverage added for both versions (`mkProjectV1`, a new test-only v1
constructor mirroring `initV1`, alongside the existing v2 `mkProject`).

**`internal/cli`**: `runInit` gained `--wip-limit`/`--description`, dropped
`--slots`/`--slot-width` entirely (version 2 has no working files to size or
pad) along with the old `n < 1` validation trap - `--wip-limit 0` is now a
legitimate, accepted request (uncapped), not a guarded-against accident.
`usage.go` updated to match. The CLI's own test suite calls the real
`--init` 37 times directly (`newProject`) expecting version-1 output, plus
39 more through a wrapper that migrates afterward (`v2Project`) - since
version 1 remains fully supported on directories that already exist and
still needs real CLI-level coverage, `newProject` now hand-writes a
version-1 skeleton directly (mirroring `initV1`'s exact shape) instead of
shelling out to `--init`, which no longer produces one. `v2Project`
(`newProject` then `--migrate`) needed no changes at all - a version-1
fixture migrated to version 2 is still a perfectly valid, and arguably more
honest, way to build one. The one real behavior change this surfaced:
`TestInitRejectsBadGrammarFlags`'s `--slots 0`/`--slot-width 0` cases tested
a version-1-only trap that no longer exists; replaced with
`TestInitWipLimitZeroMeansUncapped` asserting the new, opposite-intent
behavior.

**`internal/web/api/projects.go`**: `initRequest`/`initProject` gained
`description`, dropped `slotWidth` (dead weight once the public `Init` never
reads it) for the same reason the CLI dropped its flag.
`TestGrammarAPIInit`'s own comment had explicitly documented the old
assumption ("--init ... still only creates version-1 directories") and
called `MigrateVersion` afterward defensively; removed that now-unnecessary
call rather than leaving a defensive no-op error path in a passing test.

Verified live against the real CLI binary and the real web API route (not
just unit tests): `mm --init --wip-limit 2 --description "..."` produces a
valid `board.md` with `wip.working: 2` and the description seeded into
`structure.md`, passes `mm --check`, and `--add`/`--start` work immediately
against it with no migrate step; the same round-trip through
`POST /api/v1/projects` produces byte-identical `board.md` content. One
minor, pre-existing, unrelated cosmetic gap noticed while checking the web
route's JSON response: `toJSONDirectory`'s echoed `wipLimit`/`wipUsed`
fields are the version-1-only flat ones (always 0 for a version-2 board,
whose real cap lives in `StageCfg.WipLimits`) - not something this task
introduced or needed to fix, noted here rather than silently ignored.

`go build`, `go vet`, `gofmt -l`, and the full `go test ./...` (mm,
internal/cli, internal/web including the `jstest` node suite) are all
green. Nothing in `mm/` outside `init.go`/`discover.go` changed; no spec
text needed updating - §5.1.1 and Appendix B were already correct.

mm --init now creates version-2 directories directly, matching spec-tools.md §5.1.1's already-written text; CLI/web gained wip-limit/description flags, dropped v1-only slots/slot-width. Also found and fixed a real, closely-related bug: discover.go's IsBoardDirectory never checked board.md, so a v2 board missing done.md was undiscoverable. See details/T-0241.md for the full breakdown.
