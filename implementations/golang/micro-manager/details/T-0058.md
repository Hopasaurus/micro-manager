# T-0058 — Wire every mutating operation with its dialogs and toasts

## Context

The board renders; this is what makes it a tool. Every operation of
`spec-gui.md` §6.1 that changes a file goes through here: start, pause, finish,
block, unblock, move, note, edit, remove, and add.

Two things make this more than a row of buttons. First, two operations need
input before they can be issued — blocking needs a reason, finishing needs an
outcome — and cancelling that input must abort the operation, including when it
was initiated by a drag (§7.2). Second, a mutation invalidates more of the page
than the fragment it returns: column counts, the WIP indicator, the status bar
and the check count are all stale afterwards.

## Requirements

1. Routes are the POST endpoints of §4.2, served for both htmx and JSON. Each
   calls exactly one `mm.Store` method and re-renders from the returned item and
   `[]Change` rather than re-reading (`spec-tools.md` §6.2).
2. **Out-of-band swaps** carry the collateral: `app-status` (`status-wip`,
   `status-counts`, `status-check` with `data-violations`), the affected column
   headers and counts, and every card whose `data-position` moved. §5.5 requires
   `data-position` to stay accurate after every reorder — it is how the suite
   asserts ordering without reading text.
3. `item-action-remove` carries `data-guarded="true"` and opens
   `dialog-confirm-remove`. It **MUST NOT be satisfiable by a single click**
   (§5.6), and the DELETE route requires `force=true` (§4.2, `spec-tools.md`
   §5.1.6).
4. Prompts: `--block` prompts for a reason, `--finish` prompts for an outcome
   defaulting to `shipped`. Both are dialogs in `dialog-root`; cancelling issues
   no request at all.
5. The item menu on a card contains **one entry per legal operation**, testid
   `item-<ID>-action-<operation>`. Illegal ones are present and `disabled` with
   `data-reason` naming the error code — hidden is wrong, because a test asserts
   *why* an action is unavailable (§5.5).
6. Deciding that set is server-side. The handler asks the library what the item
   is and what the WIP state is, and computes the enable/disable set once, in
   one function shared by the card menu and `item-actions` in the panel. Two
   copies of that rule will diverge.
7. Toasts: `toast-<n>` in `toast-region` with `data-severity`, success on the
   happy path, `danger` carrying the error code on rejection (§5.10, §7.5).
8. Every failure path is a first-class outcome, not an exception: WIP full,
   concurrent modification, invariant violation. They arrive as the fragments of
   the error-mapping item, and the board must be correct afterwards without a
   reload.

## As built

`internal/web/item.go` (the operations), `internal/web/dialogs.go`,
`templates/partials/dialogs.html`, `static/mm.js`.

**Every operation is one library call**, with the response built from the return
value rather than a re-read — `spec-tools.md` §6.2 returns the resulting state
precisely so a UI does not have to ask again.

**A mutation returns the whole board plus its collateral.** Column counts, the
WIP indicator, the status bar, the validation count and every card whose
`data-position` moved are all invalidated by one change. Re-rendering the board
and swapping the status bar out of band is the honest answer, and on loopback
for a single user it is also the cheap one.

**The toast lives on the shell, not on the board's data.** Both renderings need
it: an htmx swap sends it out of band, and a plain form post gets a whole page
that must still say what happened. One `toast-body` template serves both, so the
two forms cannot drift.

**Three operations prompt first** (§7.2): remove, block and finish each fetch a
dialog, and cancelling issues no request at all. The prompt is a fetched
fragment rather than an optimistic field precisely so that cancelling is free.

**Remove is guarded twice.** `data-guarded="true"` opens
`dialog-confirm-remove`, and the DELETE route independently requires
`force=true` — so the guard is not something a client can forget its way past.

**Disabled actions issue no request.** The server would refuse them with the
same code the button already carries in `data-reason`; making the refusal slower
would not make it clearer.

**Every mutation test asserts the directory still validates afterwards.** The
library validates before every commit, and this proves the UI cannot route
around that.

## What the tests caught

`project()` returned `(nil, nil)` when the not-found view rendered successfully,
so the handler read "no error, carry on" and dereferenced a nil store. Callers
now check the **store**, not the error. The panic is the reason the harness item
came before the view items.
