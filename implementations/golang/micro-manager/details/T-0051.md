# T-0051 — Build the template renderer with page and fragment parity

## Context

Two rules from `spec-gui.md` §4.1 and `project/architecture.md` §4.3 decide the
whole design:

1. Every reachable view state is addressable, and loading a URI directly
   produces the same state as navigating to it. So every route htmx swaps a
   fragment from must also serve a whole page.
2. A partial rendered on its own must be byte-identical to the same partial
   rendered inside its page — otherwise the external suite breaks in a way that
   only shows up after an interaction.

## As built

`internal/web/render.go`, `templates/layout.html`, and the template funcs.

**One template set per page**, each carrying the layout, that page, and every
shared partial. A single set for everything cannot work: two pages both define
`content`, and that collision is exactly what a layout needs to be allowed.

**Parity is structural, not asserted.** The fragment render executes the *same
definition* the page render reaches, so the two cannot drift. The test asserts
containment — the standalone fragment appears verbatim inside the page — which
is the strongest form the property can take when the page adds a shell around
it. It checks a nested partial too, because that is where a per-context tweak
would sneak in.

**Rendering goes to a buffer first.** A template failing halfway would otherwise
have written a 200 and half a document, leaving the error handler able only to
append a message to a broken page.

**Parse is eager and a parse failure is a startup failure.** A broken template
is not a 500 the first time someone opens the view it belongs to, and the error
names the template.

**`HX-History-Restore-Request` gets the whole page.** htmx sets `HX-Request` on
it as well, so the obvious check alone would hand htmx a fragment while it is
rebuilding a page from history — leaving the user on a document with no shell.

## Template funcs

`attr` renders a `data-*` attribute only when it has a value, so an absent value
never becomes `data-thing=""` and changes what a test sees. It returns
`template.HTMLAttr`, which `html/template` trusts **only inside a tag** — using
it in text context escapes the quotes, which is what the first version of its
test discovered.

`pad` renders slot numbers as the zero-padded form the DOM contract uses
(`board-column-slot-01`), and `yesno` renders the `true`/`false` strings the
`data-*` attributes use.

## Not done here

The real pages. `templates/` holds only `layout.html`; every view arrives with
its own item, and a page registered before its handler exists would be a route
that looks implemented and is not.
