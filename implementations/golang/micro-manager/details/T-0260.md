# T-0260 — Vet declared-stage transition support and silent edit behavior

## Context

The usage notes report that `mm --edit ID --stage review` returns success without moving the item, while custom declared stages such as `review` are otherwise unreachable except by hand-editing `board.md`.

## Investigation

- Reproduce and characterize the silent-success behavior against version 2 boards.
- Determine whether `--edit --stage` should perform a move, reject the modifier, or delegate to a general stage-transition operation.
- Evaluate a general interface such as `--move-to ID STAGE`, including declared-stage validation, reason requirements, working-slot/WIP semantics, tickler behavior, audit records, and dry-run/JSON/porcelain output.
- Reconcile the result with existing `--start`, `--pause`, `--finish`, `--block`, and `--unblock` semantics and the specs.

## Done when

Record the reproduced behavior, preferred transition model and CLI contract, compatibility risks, spec changes, and scoped follow-up implementation tasks. Split the silent-success bug into an immediate fix if warranted.

## Findings (2026-09-05)

### Decision

No product decision or clarification is needed. The normative operation model
already resolves the question:

- `--edit` changes fields in place and MUST NOT change position or stage
  (`project/spec-tools.md` §5.1.5).
- `--move ID --stage SLUG` is the general operation for moving onto any declared
  stage (§5.1.7).
- A separate `--move-to` spelling would duplicate an existing operation without
  adding semantics.

The correct behavior is therefore for `--edit --stage` to fail loudly and point
to `--move`, not to perform an implicit move.

### Reproduction

Before the fix, this command returned success while leaving the item on
`working`:

```sh
mm --edit T-0260 --stage review --dry-run --json
```

The result still reported `"stage":"working"`. In the pre-T-0259 binary it
also emitted an `updated` change whose before and after lines were identical.
The parser accepted the global `--stage` modifier, but `runEdit` never consumed
it, producing the silent success.

The supported command already worked:

```sh
mm --move T-0260 --stage review --dry-run --json
```

It reported a move from `working` to `review`.

### Existing transition semantics verified

The library's version-2 move implementation already covers the proposed general
stage-transition requirements:

- Destination stages must appear in the board's declared `stages` list.
- Moving into a WIP-capped stage enforces its limit.
- Moving into `working` stamps `started:` when missing.
- Moving into a `needs_reason` stage requires an existing or supplied reason.
- Moving out of a tickler source drops `tickler:` and `tickler_dest:` while
  preserving historical `tickled:`.
- Position selectors operate within the destination stage.
- Done items cannot be moved; `--finish` remains the transition to `done.md`.
- Dry-run, JSON, porcelain, and human output share the same library operation.
- Audit logging records the stage change and coupled field changes such as
  `started:` or `reason:`.
- `--start`, `--pause`, `--block`, and `--unblock` remain convenience operations
  for common transitions; they do not limit the general `--move --stage` path.

The spec's examples already show a custom review stage:

```sh
mm --move T-0042 --stage review
```

### Implementation

`runEdit` now rejects a supplied `--stage` before calling the library and names
the exact supported command, including the item and requested destination:

```text
--stage does not apply to --edit; move the item with
--move T-0260 --stage review
```

A CLI regression test proves that the command returns the usage exit code,
points to `--move`, and leaves the item on its original stage.

### Compatibility and help follow-up

The change only affects a previously ignored combination. Scripts using
`--edit --stage` were not moving their items, so failing them exposes an existing
mistake rather than removing working behavior.

The operation-specific help already says that state changes belong to the move
operations, but it would be useful for T-0263 to make the rejection and the
custom-stage example explicit. That wording is intentionally not changed here
so help improvements remain collected in T-0263.

### Verification

```text
go build ./...                    pass
go test ./...                     pass
go vet ./...                      pass
```

The freshly built CLI was exercised against this board: `--edit --stage review`
returned an error with no changes, while `--move --stage review --dry-run`
reported the expected transition.
