# T-0125 — Spec: `board` slug and `refs` link field

Spec change task following the T-0104 spike. The spike's findings and
decisions are in `implementations/golang/project/plan-board-links.md`; this
task lands the normative changes it proposes. **The format spec is normative:
the validators (T-0126) cannot accept or reject `board`/`refs` until this task
defines the rules.**

## Why

An item in one board needs to reference an item in another board in a form a
machine can read and that survives a change in file hierarchy. Measured in
T-0104: every identity the system already has except one is location-derived —
`projectId` is `sha256(canonicalPath)`, so a moved board gets a new id
(`0b53479ae264` → `8031b21be7bf`), and `project` is unconstrained free text
(§10 limitation 8). The only handle that survives a hierarchy change is a
content-declared one, so the spec gains one: the `board` slug.

## What lands

- **§5.1 `backlog.md` frontmatter gains `board`**: optional; value a slug of
  shape `[a-z][a-z0-9-]{0,15}` — one to sixteen lowercase ASCII characters
  starting with a letter. Lowercase keeps the slug namespace disjoint from the
  ID-prefix namespace by construction (§3.3.2 rule 2, case-exact matching:
  every prefix is uppercase). Absent means the board is not a link target.
  Human-chosen, human-stable: moving or renaming the directory never touches
  it; changing it is a deliberate, findable edit (`grep -rn 'board:'`,
  `grep -rn 'refs:'`).
- **§6 field registry gains `refs`**: a `LINKLIST` — comma-separated, no
  spaces, the identical lexical rule to `tags`' TAGLIST (§10.3) — of elements
  `SLUG:ID`, where SLUG is a board slug and ID the target item's ID in the
  generic form `[A-Z]{1,4}-[0-9]{1,15}` (the intersection of every declared
  grammar, §3.3.2). The generic form lets a local reader check the *shape*
  without knowing the target board's declared grammar. Canonical field order
  (§6.1): immediately after `tags`, both being lists.
- **§9 extensibility gains the advisory-links sentence**: link resolution is
  never validation. A per-directory checker cannot see other boards, so a
  stale or ambiguous link never invalidates a directory; resolution is the
  GUI's job, where a tree-wide view exists. A slug that resolves to nothing
  renders missing; one that matches two known boards refuses to resolve,
  naming both.
- **§10 known limitations gains the two owned gaps**: slug uniqueness is not
  enforced (no server, no global view — even a tree-wide sweep cannot see
  other repos), and `mm fix` in the target board can dangle a ref (the repair
  is directory-local by design, T-0123), which renders as a missing target.
- **SKILL.md** gains a "linking boards" note: the post-move ritual — move the
  directory, `grep -rn 'refs:'` for every link to it, update the one slug if
  it changed.

## Verify

`./check.sh --all` and `go test ./...` stay green (the spec change is
normative text; the validators land the behaviour in T-0126). The plan's
decision 1 is visible as a sentence: links never contain paths.
