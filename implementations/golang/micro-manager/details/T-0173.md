# T-0173 — mm --tick and the UI tickler service goroutine

Wire the front ends per [[T-0164]] §8 and T-0171: mm --tick [--dry-run] reporting what fired/errored, and an opt-in UI service goroutine (tickler.interval, default off) calling Store.tick per held board. The panel partial (controls, server-side composition) and the someday-card badge land here too.

## As built

Four pieces, all four in place:

- **`mm --tick [--dry-run]`** (`internal/cli`): the operation, its `--json` and
  `--porcelain` shapes (`id outcome spawned tickled message`, one record per
  fire AND per error, because "what errored" is data rather than prose), and a
  help page. `--add --tickler SCHEDULE` carries the field in.
- **The service goroutine** (`internal/web/tickler.go`): `Store.Tick` over every
  held board on `tickler.interval`, started from `Server.Start` only when the
  system config sets one — off by default, the §2.4 rule that a process which
  mutates boards on its own initiative must not start quietly. Each fire is one
  Info line with item, kind and spawned ID: the §2.4 audit trail.
- **The Wake-up group** (`templates/partials/tickler.html`, both panels): the
  controls, the server-side composition of the `tickler:` value from them, and
  the reverse parse that pre-fills them. The grammar stays in the library —
  the server composes, the library validates on write (§4.2).
- **The someday-card badge**: computed with `Schedule.Next(today)` on every
  render, `data-next` absent when the schedule is already due, and the badge
  then reads `due`.

## What this session added

The Go side was already green when I picked it up. What was missing:

**`jstest/mm.test.js` had no cases for the new mm.js.** The client gained ~50
lines — the kind select choosing the shape, the section selector revealing the
group, and an afterSettle reconcile for a swapped-in form — with nothing but
the line-count ceiling watching it. Four cases now cover both rules and the
"no group on this page" path; three of them fail against the pre-T-0173 script,
which is the check that they test the code rather than the fixture.

**Neither SKILL.md mentioned the tickler at all.** `--tick` is a user-facing
operation and `tickler:`/`tickled:` are user-facing fields; both docs now carry
them, and `project/SKILL.md`'s status list said the UI service was "not built",
which stopped being true several tasks ago.

## Verified in a browser

Against a scratch copy, tickler service off (the Go test already proves the
loop; a background mutation while clicking around proves nothing):

- both visibility rules behave exactly as the jsdom cases say;
- filling the group and saving composed `tickler:first-mon@08:00` — the
  library accepted it, `check.sh` stayed clean, and the card came back reading
  `next Mon 08:00` with `data-next="2026-09-07"`, the first Monday after the
  one already past;
- an armed schedule whose time has gone by renders `due` with no `data-next`.

## Found, not fixed

`last@08:00` is unreachable from the UI: §5.6's table says the monthly control
takes `1`–`31` **or `last`**, and the same section's DOM sketch makes it
`type="number"`. The server composes and pre-fills `last` correctly; only the
control cannot produce one. Shipping the sketch verbatim rather than inventing
DOM the contract does not have — **T-0197** carries the spec decision.
