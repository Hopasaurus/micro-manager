# T-0028 — Cross-check the validator against check.sh on every fixture

## Context

`check.sh` at the repository root is a working reference implementation of
I1–I10. Two independent implementations of ten invariants will diverge; this
test finds the divergence for almost no effort.

## Requirements

- For every fixture, run the Go validator and `../../../../check.sh <dir>` against
  the same directory and assert the two agree.
- Compare **violation sets, not messages**: match on file and line. The wording
  differs and should be allowed to.
- Also run it over directories the Go implementation itself produced, not only
  static fixtures. A mutation that writes an invalid directory is exactly what
  this is meant to catch.
- Skip the test with a clear message when `bash` is unavailable, rather than
  failing. It must not block CI on a minimal container.
- The sample directories under `sample-data/` are a free additional corpus.
  (They were at the repository root when this item was written.)

## Resolved: how file-level findings compare

The open question was how to compare findings that `check.sh` reports with no
line number. **A finding with no line is a claim about the whole file, and it
matches any finding in that file.**

That is not slack in the comparison — it is the honest reading of two tools with
different precision. For an I9 title drift, `check.sh` reports the detail file;
this implementation names the exact frontmatter line. Both are right about the
same problem, and demanding identical line numbers would force the better answer
down to the coarser one. What is *not* tolerated is a problem one side reports
and the other misses, in either direction; `TestFindingComparisonIsNotTooForgiving`
pins that down so the cross-check cannot pass by being permissive rather than by
the validators agreeing.

Note also that **`check.sh` emits no invariant identifiers at all** — it prints
`path[:line]: message` — so matching on "invariant identity", as the requirement
above asks for, is not possible against this reference. File and line is the
whole of the shared vocabulary.

## What it caught immediately

A real bug, on the first run: findings about an **absent** frontmatter key
(I7 no project, I2 no next_id) pointed at **line 1**, which is the `---`
delimiter. `Frontmatter.Line` returns 1 for an unknown key so that a diagnostic
always has somewhere to point, and that default leaked into two violations where
the right answer is "no line at all". Both now report at file level, which is
what `check.sh` does too.

## Known difference that is not a violation

`check.sh` does not apply format spec §4.1 rule 5 to `project`: it prints a
trailing ` #comment` as part of the value where a conforming reader strips it.
See [T-0026](T-0026.md). Both agree the directory is valid, so it does not
affect this cross-check.
