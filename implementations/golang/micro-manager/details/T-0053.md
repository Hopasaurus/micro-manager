# T-0053 — Map library errors to HTTP status, JSON and HTML fragments

## Context

`spec-gui.md` §4.3 fixes the mapping from the library's error taxonomy to HTTP
status codes, and requires the error `code` verbatim in the body so a client
branches on the name rather than the status — which matters because three
distinct errors all map to 409.

This is the UI's equivalent of `internal/cli/exit.go`, and it must be written
the same way: one table, one place, no `if errors.Is` scattered through
handlers.

## Requirements

1. One Echo `HTTPErrorHandler` and one mapping function:

   | Library error | HTTP |
   |---|---|
   | `ErrNotFound` | 404 |
   | `ErrAmbiguous` | 409, body lists candidates |
   | `ErrInvalidArgument` | 400 |
   | `ErrConflict` | 409 |
   | `ErrWipLimitReached` | 409, body carries `wipUsed`, `wipLimit`, occupants |
   | `ErrPreconditionFailed` | 412 |
   | `ErrInvariantViolation` | 422, body carries the violation list |
   | `ErrConcurrent` | 409 |
   | `ErrIO` | 500 |

2. Three body forms from one decision point, chosen by the request:
   - `/api/v1/*` → the JSON envelope of §4.3, `{"ok":false,"errors":[…]}`;
   - an htmx request (`HX-Request`) → an HTML fragment: a toast, or for
     `WipLimitReached` the `dialog-wip-limit` fragment;
   - anything else → a full error page.
3. `code` is the spec's name — `WipLimitReached`, not `wip limit reached` and
   not the Go sentinel's text. A test asserts the string for every error, since
   the external suite branches on it.
4. `mm.AsWipLimitError` already carries the limit and the occupants; the dialog
   lists them as `dialog-wip-limit-slot-NN` and offers finish, pause and
   raise-limit — the same three remedies the CLI names (§5.10).
5. `ErrConcurrent` renders `dialog-conflict`, which offers reload and **MUST NOT
   offer a blind overwrite** (§5.10).
6. `ErrInvariantViolation` carries `[]Violation` into the body with `invariant`,
   `file` and `line`, matching the shape the check view renders.
7. A panic in a handler is a 500 through Echo's recover middleware and must not
   take the process down — the service is long-lived and a user's next request
   should still work.

## As built

`internal/web/errors.go`, installed as Echo's single `HTTPErrorHandler`.

**v5's router errors are an unexported type.** `errors.As(err, &echo.HTTPError{})`
does not see them, so a 404 for an unrouted path silently became a 500 —
`echo.StatusCode(err)` is the API that covers both the framework's own
`*HTTPError` and its internal `httpError`. The scaffold's "unknown route is a
404" test is what caught it, which is the argument for having written that test
before there were interesting routes.

**Three errors are 409 and each carries a distinct code.** A test asserts they
are all 409 and that no code repeats, because the status alone cannot tell a
client which of the three happened — which is the whole reason §4.3 puts the
code in the body.

**The message drops the sentinel's own prefix.** A body reads
`T-0042 is not in this directory`, not `not found: T-0042 is not in this
directory`; the code already says which error it is.

**Guard refusals get codes too** — `HostNotAllowed`, `OriginNotAllowed` — so a
client branches on a name for those as well rather than on 421 versus 403.

**The htmx path falls back to a bare fragment.** The dialogs of §5.10 arrive
with the items that own them; until then the handler emits a minimal element
carrying `data-severity` and the code, because a client behaving correctly
matters more than how the error looks. `dialog-wip-limit` and `dialog-conflict`
are already selected by code, so those items only have to add the templates.

**A committed response is left alone.** Appending an error to a half-written
response corrupts it; the truncated body plus a logged error is the least bad
outcome available.
