# T-0047 — Derive projectId from the canonical directory path

## Context

`spec-gui.md` §3.1 addresses a directory in every URI by a derived id, never by
a path, and fixes the algorithm so that a fixture computes the same id against
every implementation:

```
projectId = lowercase(hex(sha256(canonicalPath)))[0:12]
```

`canonicalPath` is the absolute path with symlinks resolved, no trailing
separator, encoded UTF-8 in NFC.

## Requirements

1. `mm.ProjectID(path string) (string, error)` in the library, not in
   `internal/web` — the TUI's recent and favorites files carry the same ids
   (`spec-gui.md` §10) and both front ends must agree byte for byte.
2. Canonicalisation: `filepath.Abs`, then `filepath.EvalSymlinks`, then strip a
   trailing separator. `discover.go` already has a `canonical` helper; reuse it
   rather than growing a second one, and make discovery emit the id so
   `/projects` does not recompute per row.
3. **NFC normalisation is the part that will be got wrong.** macOS hands back
   decomposed (NFD) filenames, so a directory containing `é` produces a
   different sha256 on macOS than on Linux unless it is normalised first. The
   stdlib has no NFC, and the library was required to have zero third-party
   dependencies.

   **Decided: take `golang.org/x/text/unicode/norm`.** The dependency rule was
   local policy — `architecture.md` §3 and `AGENTS.md`, not any spec — and it
   was relaxed rather than worked around, because hand-rolling Unicode
   normalisation inside a todo tool puts a correctness-critical implementation
   in the one place the whole cross-implementation identifier rests on.
   `architecture.md` §3 now records the licence alongside every dependency and
   says what the higher bar on `mm/` actually means.
4. A rejection path: the id is derived, never parsed. Nothing accepts an id and
   reconstructs a path from it; resolution is a lookup against the registry
   (see the project-registry item), and an unknown id is a 404, never a
   redirect (`spec-gui.md` §4.1 rule 4).
5. Test vectors go in the fixture corpus so the future Python, TypeScript and
   Erlang implementations can assert against the same table.

## As built

`mm/projectid.go`: `ProjectID(path)`, `CanonicalPath(path)`, `ProjectIDLength`,
and an unexported `projectIDOf(canonicalPath)` that hashes a string and touches
no filesystem — which is what lets the vector table assert on paths that do not
exist on the machine running the test.

Three things worth knowing before changing any of it:

- **Normalisation applies to the hash input only.** `CanonicalPath` returns the
  path exactly as the filesystem reported it, because on a byte-exact filesystem
  a normalised path may not open the file it names. Only the bytes fed to
  sha256 are NFC.
- **`canonical()` in `discover.go` had an ordering bug**, found by the
  relative-path test: it called `EvalSymlinks` *before* `filepath.Abs`, so a
  relative path had nothing to resolve and then picked a symlinked prefix back
  up from the working directory — `/var` → `/private/var` on macOS gave one
  directory two canonical forms and therefore two ids. Now absolute first, then
  resolve. This also affected discovery's deduplication.
- **`Directory` carries `ProjectID`**, filled by `Store.Directory()` and by
  `describe()` in discovery — including for a matched directory that could not
  be read, which is precisely the one a user most needs to open. `mm --find
  --json` emits it, so a script gets the ids the UI service serves without
  reimplementing §3.1.

`testdata/projectid-vectors.json` is the portable half: nine canonical paths and
their ids, including one written twice — `café` composed and decomposed — which
must produce a single id. It is plain JSON with no fixture directories, so the
Python, TypeScript and Erlang implementations can assert against it directly.
