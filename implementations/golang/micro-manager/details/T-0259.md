# T-0259 — Vet arbitrary custom-field mutation support

## Context

The usage notes in `xfer/working-with-mm.md` report that unregistered fields
such as `parent:T-0006` are legal and preserved, but cannot be set through the
CLI. The note was written from experience with an installed `mm 0.2.0`; that
binary may have been older than the source and binary in this checkout.

## Executive summary

The requested capability already exists in the current specification, library,
CLI source, built binary, and tests. The working commands are:

```sh
mm --edit T-0007 --set parent=T-0006
mm --edit T-0007 --unset parent
```

Both switches repeat. Existing unknown fields are updated in place, new unknown
fields are appended after registered fields, and unrelated unknown fields
survive edits and moves.

The feature does not need a new operation or spelling. It does have two
correctness gaps, and the current help page is accurate but too terse to explain
the behavior well. The decision is therefore whether to accept the existing
feature as-is or approve a small hardening and help-text pass.

## What is already specified

`project/spec-tools.md` §5.1.5 specifies repeated `--set KEY=VALUE` and
`--unset KEY` modifiers. It explicitly requires them to reach unregistered
fields and validate registered fields. The library API exposes the same
capability through `UpdateRequest.Set` and `UpdateRequest.Unset`.

`project/spec-file-format.md` §4.2 defines a field key as one or more ASCII
letters, digits, underscores, or hyphens. Section 9 makes unregistered fields the
format's extension point and reserves several names from being redefined by an
extension.

No new `--field` alias is advisable: it would duplicate `--set`, and `--field`
already means a search-field filter on `--search`.

## What is already implemented

- `mm.UpdateRequest` has `Set []Field` and `Unset []string`.
- `Store.Update` edits in one transaction, reparses and validates pending bytes
  before commit, uses atomic writes, and detects concurrent modification.
- Registered keys route through field-specific validation. Unknown keys route
  through `setExtra` and `removeExtra`.
- Updating an existing extra preserves its position; adding one appends it.
- `stage` is deliberately refused through `--set` because changing it is a move
  with WIP, timestamp, and tickler semantics. The error points to
  `--move --stage`.
- Human, JSON, porcelain, and dry-run paths use the same library operation.
  JSON exposes unknown fields under `extra`.
- With audit logging enabled, a changed custom field is derived from the
  before/after lines and appended to the audit.

## Help-text assessment

Current `mm --help --edit` output says:

```text
mm --edit ID [--title T] [--prio P] [--tag T]... [--untag T]...
               [--set KEY=VALUE]... [--unset KEY]... [--blocked REASON]
               [--created DATE] [--started DATE]

Changes fields in place. Position is --move; state is --start/--pause/--finish.
--set and --unset reach any key, including ones this tool does not know.
```

This is enough to discover the switches if the operation-specific page is
opened, but it does not describe them well enough:

- There is no example using the motivating custom-field workflow.
- Repetition is conveyed only by compact `...` notation.
- Registered-field validation versus unknown-field preservation is unexplained.
- The item-field key grammar and need for shell quoting are not explained.
- The special `--set stage=...` refusal is not mentioned.
- Set/unset overlap is unspecified.
- It lists older `--blocked` wording but omits the version-2
  `--reason`/`--tickler-dest` modifiers present in the normative syntax.
- Top-level help only says “change an item's fields,” so users must guess that
  the operation page contains the custom-field escape hatch.

Suggested help content:

```text
--set KEY=VALUE            set or replace a registered or custom item field;
                           repeats; registered values are validated
--unset KEY                remove a field; repeats; required fields cannot be
                           removed

Examples:
  mm --edit T-0007 --set parent=T-0006
  mm --edit T-0007 --set owner=dana --set estimate=3d
  mm --edit T-0007 --unset parent

Changing stage is a move: use mm --move T-0007 --stage review.
Quote values according to your shell when they contain spaces or shell syntax.
```

The shell-safety wording should be coordinated with T-0263. Help-output tests
ensure every operation has a page, but there is no focused assertion that the
edit page documents custom-field use.

## Correctness gaps found

### 1. Custom key grammar is not enforced

`setAnyField` rejects an empty key and a value containing `|`, but does not
enforce the §4.2 key grammar. This currently succeeds in dry-run mode:

```sh
mm --edit T-0259 --set 'bad key=value' --dry-run
```

It proposes `bad key:value`, although spaces are forbidden in keys. The parser
also accepts the malformed key when reparsing, so pre-commit validation does not
catch it. This is a writer-conformance bug.

Suggested hardening: introduce one shared `validFieldKey` check used by
item-line parsing, `--set`, `--unset`, bulk-add parsing, and every writer. Test
spaces, tabs, punctuation, non-ASCII, empty keys, and valid `_`/`-` forms.

### 2. Reserved extension names are settable as unknown fields

This also succeeds in dry-run mode:

```sh
mm --edit T-0259 --set id=oops --dry-run
```

It proposes an `id:oops` item-line field. Format §9 reserves `id`, `status`,
`next_id`, `doc`, `version`, `id_prefix`, `id_width`, `board`, `stage`, `stages`,
`stage_labels`, `tickler_stages`, `needs_reason`, and the `wip.` prefix from
extension use. `stage` has a special refusal, but the others do not.

Suggested hardening: reject reserved keys consistently when they would
otherwise enter `Extra`. Decide whether readers should reject pre-existing
misuse or preserve it; refusing new writes is the minimum safe change.

## Lower-severity semantics to decide

### No-op reporting

`--unset absent` and `--set parent=T-0006 --unset parent` do not write a file,
but return an `updated` change whose before and after lines are identical. The
transaction correctly reports no changed files, and audit logging emits no
field entry. Machine consumers may nevertheless interpret the change as real.

Possible rule: omit item-level `Change` records when `Before == After`, while
retaining successful no-op status. This should be decided globally.

### Set/unset overlap

All sets are applied first and all unsets second, regardless of argv order. A
key named by both is therefore absent. This is deterministic but undocumented.
Possible policies are to document “unset wins,” reject overlap as ambiguous, or
preserve argv order. Rejecting overlap is simplest and least surprising.

## Options for the owner

1. **Accept as already shipped.** Close this task and create no new work. This
   accepts the malformed/reserved-key and help gaps for now.
2. **Accept with focused hardening.** Treat the capability as shipped, then
   create a correctness task for key grammar and reserved names and a help task
   for discoverability. Optionally include the lower-severity semantics.
3. **No-go / remove generic mutation.** Remove `--set`/`--unset`. This conflicts
   with the extension model; this investigation found no evidence favoring it.

Selected optio: Accept with focused hardening.

## Questions for the owner

1. Should this be marked shipped, with separate hardening and help-text tasks? No, do the work as part of this task.
2. Should pre-existing malformed/reserved extras remain readable and
   preservable, while only new writes are refused? Yes
3. When one invocation sets and unsets the same key, should that be rejected or
   should “unset wins” be documented? Document "unset wins"
4. Should successful no-op edits return zero `Change` records? Yes
5. Should the help improvement be folded into T-0263 or tracked separately? Fold it in.

## Proposed implementation scope if approved

- Add a shared field-key validator matching format §4.2.
- Add a shared reserved-extension-key predicate matching format §9.
- Apply both at parse/write boundaries under the chosen legacy-read policy.
- Improve `mm --help --edit` with examples, repetition and validation semantics,
  stage guidance, current version-2 modifiers, and shell-safe quoting guidance.
- Add library and CLI tests for valid, malformed, and reserved keys and focused
  help-output coverage.
- Resolve overlap/no-op semantics only if included in the approved scope.

## Implementation outcome (2026-09-05)

Approved behavior has been implemented while leaving this task in Working for
owner review.

- New and replacement fields now require the §4.2 key grammar.
- Reserved extension keys are rejected by `--set`, direct `AddRequest.Extra`,
  and `--add-many` custom fields.
- Readers still accept and preserve legacy malformed or reserved extras during
  unrelated edits.
- `--unset` can remove those legacy extras. For `id` and `title`, it removes an
  extra with that key when present but still refuses to remove the structural
  item ID or title.
- Byte-identical updates now return zero `Change` records as well as writing no
  files.
- `project/spec-tools.md` now makes “unset wins” normative when a key appears in
  both switch groups.
- `project/spec-file-format.md` now records the approved tolerant-reader,
  strict-writer legacy policy.
- Help changes were intentionally left to T-0263, which can collect this and
  the broader shell-interpolation guidance together.
