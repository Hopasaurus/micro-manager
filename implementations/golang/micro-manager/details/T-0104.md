# T-0104 — Explore how micro-manager could link between boards.

Make sure the links would be able to survive a change in file heirarchy.

## Update (post-ship)

Plan written to `project/plan-board-links.md` (status: proposed). The spike
measured, rather than assumed, what identity is in this system:

- **The requirement decides the design.** A link must survive a change in
  file hierarchy. Measured: `projectId` is `sha256(canonicalPath)` — a moved
  board gets a new id (`0b53479ae264` → `8031b21be7bf`) — and `project` is
  unconstrained free text (§10 limitation 8). The one handle that survives a
  hierarchy change is a **content-declared** one, so the plan proposes the
  `board` slug in `backlog.md` frontmatter: lowercase `[a-z][a-z0-9-]{0,15}`,
  disjoint from the uppercase ID-prefix namespace by case.
- **The link form** is `refs`, a comma-separated LINKLIST of `SLUG:ID`
  elements (the same lexical rule as `tags`), reusing the §9 extension point:
  unregistered fields already survive every move verbatim, and
  `mm --edit --set refs:…` already works — no CLI change needed.
- **Links are advisory, never load-bearing**: check.sh validates shape only;
  resolution is the GUI's (tree-wide view), with the §10 rule 5 missing
  treatment for dead targets and the `mm fix` tie discipline for ambiguous
  slugs. A stale link never invalidates a board.
- **Proposed follow-ups, registered in Ready**: T-0125 (spec: `board` +
  `refs`), T-0126 (validators: shape rules, broken/clean fixtures, oracle
  lockstep), T-0127 (GUI: clickable links, missing/ambiguous rendering).
  `next_id` bumped T-0124 → T-0128.
