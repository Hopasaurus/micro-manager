# T-0098 — Themes listing/export: sample-one-dark serves the builtin; don't advertise ids the library lacks (F4)

Finding **F4** of `project/code-review-006.md` (CONFIRMED).

## The bug

`internal/web/api/files.go:557`:

```go
switch themeID {
case "micro-manager", "sample-one-dark":
    return mm.BuiltinTheme()
}
```

`mm/theme.go:552` shows `BuiltinTheme()` is `ID: "mm-default"`,
`Name: "micro-manager"`, `Appearance: auto`. There is no `sample-one-dark`
theme anywhere in `mm` — grep finds the string only in a `theme_test`
id-validation list.

Consequences on the public API surface:

- `GET /api/v1/themes` (line 406) advertises `sample-one-dark` as a distinct
  dark theme.
- `GET /api/v1/themes/sample-one-dark/export` then serves the default auto
  theme under the filename `sample-one-dark.mm-theme.json`.
- The same listing advertises id `micro-manager` while the document it yields
  carries id `mm-default` — a listing/export id mismatch.

`theme.go`'s pre-existing `resolveExportTheme` has the same shape; the new API
surface inherits it rather than introducing it, but it ships the bug on a new
public endpoint.

## Fix direction

Make the advertised ids match what the library actually has. Either drop
`sample-one-dark` from the listing/export switch, or — if a dark sample theme
is genuinely wanted — add it to `mm` and serve it by its real id. The
`micro-manager` vs `mm-default` mismatch must be resolved one way: the listing
should advertise the id the exported document carries.

## Verify

- Every id in `GET /api/v1/themes` exports a document whose `id` field is
  that id.
- No endpoint serves the builtin under a name the library does not define.

## Notes

**2026-07-31** — Went deeper than the finding. Three parts: (1) dropped sample-one-dark from both listings, the export switch and the settings picker - it is the EXAMPLE document of spec-gui.md 8.6, not a theme mm has, and 8.7 defines exactly one builtin. (2) BuiltinTheme().ID was mm-default, referenced nowhere else in the tree while every consumer advertised micro-manager; changed the definition rather than the four consumers. All listings now derive ID/Name/Appearance FROM BuiltinTheme() so they cannot drift again. (3) The real defect the review missed: Theme.Bytes marshalled raw alone while Save folded the parsed fields in first, so a theme built in Go had empty raw and exported as {}. Exporting the builtin had always downloaded an empty document. Extracted Theme.document() and routed both Save and Bytes through it.

3 tests added: listing offers only real themes, every advertised id exports a document carrying that id, and the builtin survives export/re-import with every token intact. All verified to fail against the old code.
