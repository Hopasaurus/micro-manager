# T-0048 — Implement the recent and favorites list files

## Context

`spec-gui.md` §10. Two files under `$XDG_CONFIG_HOME/micro-manager/`, separate
so that the high-frequency writes of one cannot clobber the other, shared with
the TUI byte for byte (§13). Home, the project switcher and the favorites toggle
all read them.

## As built

`mm/list.go`. One `ProjectList` type covering both files, with `ListKind`
selecting the differences — favorites carry `order` and an optional `label`,
recent does not.

**`Timestamp` is new.** `lastOpened` is a TIMESTAMP, not a DATE: ISO 8601
extended, UTC designator, second granularity. Unlike `Date` it *does* carry a
zone and the zone is always `Z`, because these files are synchronised between
machines and a local offset would make two machines disagree about the order of
one list. An offset such as `+02:00` is rejected rather than converted — the
files are compared as text, so accepting a second spelling would mean one front
end rewriting what another wrote.

**Retention and display are different numbers.** `maxStored` trims the list;
`Display(count)` only limits what is returned. §9.2 is explicit that shrinking
the display count must not discard stored history, and keeping them in two
methods is how that stops being something to remember.

**Missing is a question, never a cleanup.** `ListEntry.Missing()` stats the
path; nothing acts on it. §10 rule 5: a project on an unmounted drive is not a
deleted project, so the entry is rendered with `data-missing="true"` and removal
is the user's explicit choice.

**`UpdateProjectList` re-reads before writing.** That is how "tolerate
concurrent writers" is honoured at this granularity: two front ends may both be
running, and the loser of a race should lose one edit rather than the whole
file. A caller holding a stale list and calling `Save` would take the file back
in time; the helper exists so nothing has to.

**Per-entry unknown keys survive too**, not just top-level ones — `Extra` on
each entry — because a newer front end's per-project field is exactly what a
naive rewrite would strip.

A malformed `lastOpened` costs the ordering hint and nothing else. Dropping the
entry would lose a favorite over a typo, and the file is hand-editable.
