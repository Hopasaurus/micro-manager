# T-0133 — Broker: publish per-column events from a per-file diff; detail-body edits fire nothing

## Context

`research-app-fllicker.md` §2 sources 4 and 5, §3 C. Today the broker publishes
`board`, `status`, and `check` together on **any** fingerprint change — so a
detail-body edit (the most common write) refetches the whole board for no
visible change, and a change to one item re-renders every region including a
full validation pass.

Using T-0132's per-file stamps, the poller can say which region a change can
affect and publish only that.

## Requirements

- Diff per-file stamps between ticks and publish region events:
  - `backlog.md` → `column:ready`, `column:blocked`, `column:someday`, `status`
  - `working.NN.md` → `column:working`, `status`
  - `done.md` / `done-YYYY.md` → `column:done`, `status`
  - `details/` listing change (add/remove) → the column(s) where that item's
    card lives (`data-has-detail` changed)
  - `details/<ID>.md` content change → **nothing**. This is the prize: the most
    common write stops touching the board entirely.
- Keep `board` as a coarse fallback event so a full refresh remains expressible
  (the 30 s backstop still converges even if an event is missed).
- Keep the `theme` path exactly as it is (theme stamp, separate from data).
- Update `architecture.md` §4.5: the "small closed set — `board`, `status`,
  `check`, `theme`" grows with `column:*`.
- Update `sse_test.go`: assert the new events arrive for the file that changed
  and — critically — that a detail-body edit publishes no board/column event.
- Fragment routes to consume these events are T-0134; until they land, columns
  can keep the `board` trigger and the events go unused.

## Open questions

- Whether `status` remains a single event or becomes per-column counts.
- The item-level event (`sse:item-T-0042`) that per-card routing would need —
  defer to T-0134's decision.
