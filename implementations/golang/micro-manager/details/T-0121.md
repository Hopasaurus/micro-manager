# T-0121 — Spec: reserve git conflict-marker lines (§5.1)

Spec change task following the T-0101 spike. The spike's findings and
decisions are in `implementations/golang/project/plan-git-support.md`; this
task lands the one normative change it proposes. **The format spec is
normative: the validators (T-0122) cannot reject markers until this task
defines the rule.**

## Why

Probe (T-0101): a git conflict block inside `backlog.md` —

```
<<<<<<< HEAD
- [ ] [X-003] Local edit | created:2026-08-01
=======
- [ ] [X-003] Remote edit | created:2026-08-01
>>>>>>> theirs
```

— is accepted by **both** validators. §5.1 says non-item prose "MAY appear
anywhere and MUST be ignored by readers", so the three marker lines are legal
prose and the item lines inside the block parse as real items. When a
conflict's two sides carry different IDs, the markers pass with zero findings
and a half-resolved merge is indistinguishable from valid prose. A reader that
swallows a merge marker is doing the opposite of the format's job.

## What to change in spec-file-format.md

§5.1's prose rule gains a reserved-shape carve-out: a line whose first
non-blank characters are exactly `<<<<<<<`, `=======`, or `>>>>>>>` is invalid
in every data file (`backlog.md`, `working.NN.md`, `done.md`), and a
conforming reader MUST refuse it loudly — report the file and line — never
ignore it. Keep the carve-out narrow: these are the three shapes git writes,
nothing else is reserved; ordinary prose that merely contains `<` or `>` is
unaffected.

Place the rule where readers find it: §5.1's "Non-item content" paragraph,
with a forward reference from §4.1 frontmatter (a marker line inside
frontmatter is a violation of §4.1 line grammar already, but state it once in
§5.1 and let both apply).

## Verify

A reader of the spec can state the rule without ambiguity: three reserved line
shapes, any file, refused loudly with the line number; every other line is
unaffected. T-0122 then enforces it in check.sh and the Go validator, and the
T-0070-style audit of the spec's own examples finds no accidental use of the
three shapes.

## Referenced by

T-0122 (validators reject markers), T-0123 (`mm fix` refuses to run while
markers remain, which this rule makes a load-time fact).
