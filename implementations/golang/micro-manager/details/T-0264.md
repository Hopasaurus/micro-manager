# T-0264 — Update structure.md

## Context

The checked-in `micro-manager/structure.md` is still the long version-1 guide:
it describes `backlog.md`, `working.NN.md`, fixed Ready/Blocked/Someday
sections, and the retired invariants I4/I10. This board is version 2 and uses
`board.md`, item `stage:` fields, configurable stages and per-stage WIP caps.
The Go initializer already emits a shorter version-2 structure document from
`mm/init.go`, but that generated text is still longer than a quick orientation
page and does not yet establish the intended relationship with `mm --help`.

`structure.md` is optional human documentation under format §5.5. It is not
board state, is not part of the fingerprint, and is not validated. The first
prose paragraph is also the board description read by status and written by
the future `--describe` operation, so it cannot simply be treated as wholly
immutable without qualifying what “read only” means.

## Goal

Make `structure.md` a concise, accurate orientation page for humans and coding
agents. It should explain what may be read or edited directly, direct command
users to `mm --help`, and direct readers who need normative detail to the
repository specifications. The file and CLI help should complement each other
instead of duplicating full operation documentation.

## Decided direction

Refreshing an existing `structure.md` will be an **explicit operation**, not an
automatic side effect of `--migrate`. Use the command shape:

```text
mm --refresh-structure [--dry-run]
```

`--migrate` continues to migrate board data only. It may report that the
documentation appears older than the board version and suggest
`mm --refresh-structure`, but it must not rewrite free-form documentation.

### Refresh ownership marker

Every `structure.md` created by `--init` or `--refresh-structure` contains this
literal control near the top:

```markdown
- [x] Allow `mm --refresh-structure` to update generated documentation.
```

The checked form is the opt-in and is emitted by default. Refresh behavior is:

- **File missing:** updatable. Create a fresh current guide with the checkbox
  checked and an empty user-notes area.
- **Checked marker present exactly once:** updatable. Refresh only the generated
  regions and preserve the user-notes payload byte-for-byte.
- **Marker unchecked (`- [ ]`), deleted, malformed, or duplicated:** protected.
  Stop before writing and explain that the file opted out or cannot be safely
  classified. The command must leave it byte-identical.

Deletion is intentionally protective rather than permissive: an arbitrary or
older hand-written `structure.md` does not become tool-owned merely because it
lacks a marker. A user who wants to keep such a file and regenerate the
conventional guide can rename or move it; the now-missing `structure.md` is
then safely recreated on the next explicit refresh.

### User-owned area

Generated guides contain one explicitly delimited payload:

```markdown
<!-- mm:user-notes:begin -->
## User notes

Add board-specific notes here. `mm --refresh-structure` preserves everything
between these markers exactly.
<!-- mm:user-notes:end -->
```

The boundary comments are reserved literals. Refresh owns everything outside
them and may replace those generated regions wholesale. It preserves every byte
strictly between the begin and end marker lines, including headings, blank
lines, Markdown, and trailing spaces. Missing, reversed, nested, or duplicated
boundaries make an existing file unclassifiable and therefore protected: stop
without writing. The empty generated section above is the default for new or
newly recreated files.

## Proposed information split

- **`structure.md`:** stable concepts visible from the directory—what each
  file is, the item-line shape, the few invariants a manual editor must not
  violate, and where authoritative/help material lives.
- **`mm --help`:** current command syntax, modifiers, examples, shell quoting,
  and operational behavior. Add a short pointer back to `structure.md` for the
  on-disk model and safe manual-editing rules.
- **Repository specs:** normative and exhaustive format/tool behavior. Link to
  `project/spec-file-format.md` and `project/spec-tools.md` using the chosen
  canonical repository URL, while noting that a local checkout may be easier
  to consult.
- **Optional agent file:** only add a separate LLM-oriented file if it contains
  durable instructions not already covered by `structure.md`, repository
  `AGENTS.md`, or `mm --help`. Avoid maintaining a second copy of the format.

## Work items

1. **Define the audience and authority statement.** Open with a compact note
   that the directory is plain Markdown, `structure.md` is orientation rather
   than the normative spec, and the board data remains usable without this
   document.
2. **Replace version-1 content.** Remove all guidance about `backlog.md`,
   `working.NN.md`, fixed backlog sections, `blocked:`, slot-file WIP limits,
   and the retired invariant list. Describe version 2 only: `board.md`,
   `done.md`, `details/`, optional archives/audit, `stage:`, and `wip.<stage>`.
3. **Cut to a quick-reference size.** Target roughly 80–140 lines and prefer
   one representative item line, a compact file table, a short “safe manual
   edits” list, and pointers over repeated field/operation catalogs.
4. **State the read-only boundary precisely.** Explain that reading the files
   directly is always safe and that `structure.md` itself is documentation,
   not authoritative board state. If “read only” is intended for agents, say
   whether agents must use `mm` for mutations or may edit Markdown manually
   while preserving invariants. Do not contradict `--describe`, which is
   designed to update the first prose paragraph.
5. **Add navigation in both directions.** `structure.md` should name
   `mm --help` and `mm --help --OPERATION`; general CLI help should point to
   `structure.md` for storage layout and manual-editing constraints.
6. **Point to deeper documentation.** Include the repository location and
   direct pointers to the format and tool specs. Clearly label those specs as

7. **Make it agent-friendly without duplicating content.** Use explicit
   headings such as “Authority,” “Files,” “Safe edits,” and “More help”; state
   the non-negotiable rules in literal terms (one home per ID, `next_id` only

   Decide whether that is sufficient before creating another file.
8. **Update the initializer source.** Keep `renderInitStructureV2` aligned so a

   `--migrate`.
10. **Preserve user-owned content safely.** Retain the first prose paragraph

    silently discard text merely because it differs from the generated

11. **Add migration guidance without mutation.** When migration can determine
    that `structure.md` declares an older version than the resulting board, it
    may emit a non-fatal suggestion to run `--refresh-structure`. Absence or
    arbitrary free-form content remains valid and must not block migration.
12. **Decide fixture scope.** Update only fixtures whose exact structure output

## Suggested outline

```text
# <project name>
<board description / concise default paragraph>

## Authority
## Files
## Item lines
## Safe manual edits
## Commands and more help
```

The “Safe manual edits” section should be short enough to scan and include only
the failure-prone rules. Full field grammar, every operation, archive mechanics,
and implementation notes belong in the linked specs or CLI help.

## Resolved decisions

1. “Read-only” describes `structure.md` as non-authoritative documentation;
   careful direct edits to board data remain supported, with `mm` recommended
   for preserving invariants.
2. The public repository URL is
   `https://github.com/Hopasaurus/micro-manager`, accompanied by paths to the
   format and tools specs within a checkout.
3. Initialization and refresh use one canonical generated template. The
   checked-in guide uses that template with its own project, description, and
   date.
4. No second LLM-oriented file is generated. Explicit headings and concise
   invariant language make `structure.md` useful to both humans and agents.
5. The resulting guide is 69 lines: short enough to scan without omitting the
   ownership marker, user-notes area, file model, safety rules, or navigation.

## Acceptance criteria

- The guide accurately describes version 2 and contains no active guidance for
  retired version-1 files or operations.
- A reader can identify the files, understand the item-line/stage model, and
  find both CLI and normative help without reading a full embedded spec.
- The read-only statement is unambiguous and does not conflict with the chosen
  manual-editing policy or `--describe` semantics.
- New-board output and the checked-in guide follow the chosen canonical model.
- Existing documentation changes only through `--refresh-structure`; migration
  never rewrites it implicitly.
- Refresh preserves the board description and never silently destroys other
  user-authored content.
- Every generated guide opts in with the checked refresh marker and includes
  the delimited user-notes area. Unchecking or deleting the marker protects an
  existing file; a missing file is created.
- Protected or structurally ambiguous files fail before mutation and remain
  byte-identical.
- Help and initializer tests prevent the two documents from drifting apart.
