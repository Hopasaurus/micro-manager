# T-0261 — Vet live updates and conflict handling in the UI item detail view

## Context

The open item detail view can become stale when either `details/T-NNNN.md` or the item line in `board.md` changes through another CLI session, UI session, or editor. Reloading must not silently discard unsaved local edits.

## Investigation

- Map the current detail-view load/save flow, broker/SSE events, file stamps or revision data, and the sources of board-line versus detail-body state.
- Define the user-visible states for clean external updates, dirty-local plus external updates, deletions/moves, and repeated changes.
- Evaluate the proposed phases: (1) detect and offer reload when clean, (2) warn and prevent loss when dirty, (3) three-way merge/conflict resolution.
- Identify an appropriate merge base and whether phase 3 is justified versus simpler explicit choices.
- Specify testable behavior, accessibility requirements, fallback behavior, and interactions with existing flicker/change-detection work.

## Done when

Record a go/no-go recommendation for each phase, an event/revision design, UX states, risks, dependencies on existing tasks, and separate follow-up implementation tasks for approved phases.

## Findings (2026-09-05)

### Recommendation

- **Phase 1 — GO:** detect item-specific external changes and offer reload while
  the open form is clean.
- **Phase 2 — GO:** track local dirtiness, prevent stale saves, and require an
  explicit resolution before either version can be discarded.
- **Phase 3 — NO-GO for now:** do not build a three-way merge editor until
  phases 1 and 2 provide evidence that conflicts are frequent enough to justify
  it. Preserve the original snapshot in the phase-2 design so merge can be
  added later without changing the concurrency contract.

No owner clarification is required for these recommendations. The originating
request already fixes the key UX policy: notify and offer reload; never silently
replace local edits.

## Current behavior and architecture

### Panel load

`GET /p/:projectId/item/:itemId` calls `Store.Get`, then separately reads the
detail through `Store.Detail`. The panel renders editable title, priority, tags,
reason, tickler controls, and detail body. Stage and other board-line state are
rendered in the panel heading, metadata, actions, and board behind it.

The panel carries no revision, ETag, file stamp, or original-value payload.

### Change notification

The broker has one poller per open project. It polls `Store.Fingerprint`, whose
input includes `board.md`, `done.md`, archives, working files, and every detail
file. A change publishes generic `board`, `status`, and `check` SSE events.

The board and status regions listen and morph-refresh themselves. The panel is
outside the board DOM in `#item-panel-root`, has no SSE trigger, and is not
refetched. Consequently:

- a `board.md` edit refreshes the card behind the panel but not the form;
- a detail-file edit changes the project fingerprint but still leaves the form
  stale;
- the SSE-down polling fallback only polls self-described morph regions, and
  the panel is not one of them.

The generic project fingerprint is suitable as a wake-up signal but not as an
item revision: unrelated item, archive, or detail changes also change it.

### Save and conflict behavior

The HTML edit handler starts a fresh `Store.Update` when Save arrives, then
starts a separate `AttachDetail` or `SetDetailBody` transaction. Each
transaction records size and mtime when it begins and detects a writer racing
that short transaction.

That does **not** detect a change made after the panel was rendered but before
Save was pressed. The fresh transaction reads the external version as its own
baseline and can overwrite it with stale form values. The existing
`dialog-conflict` therefore handles only a narrow commit-time race, not the
view-lifetime conflict this task concerns.

Because fields and detail are saved in separate transactions, the field update
can also commit before a detail conflict or error. Phase 2 cannot be made safe
by a preflight check followed by these same two calls; another writer can enter
between the check and either commit.

## Proposed revision and event design

### Item revision

Add a library value representing the exact editable snapshot:

```text
ItemRevision = SHA-256(
  rendered item line + NUL +
  detail-file existence + NUL + exact detail bytes
)
```

The token should include the whole item line, not only fields currently shown
in the form, because stage, custom fields, ticklers, timestamps, and detail
linkage affect the truth and actions shown by the panel. Exact detail bytes
include frontmatter changes such as a synchronized title. Hash content rather
than size/mtime so a same-size edit cannot compare equal.

The panel stores the opaque token in `data-revision` and submits it as
`expectedRevision`. Clients compare tokens only; the hash composition remains a
library detail.

### Notification path

The existing project fingerprint remains the cheap broker signal. On any data
change, publish an `item` notification in addition to the existing region
events. It need not contain an ID: external-editor changes are discovered as a
project fingerprint delta, so the broker does not know which item changed.

The open panel responds by querying a small internal item-freshness route with
its item ID and baseline token. The route recomputes only that item's revision:

- unchanged: no UI update;
- changed: return current revision and state;
- missing: report deletion;
- temporarily invalid/unreadable: report unavailable without replacing input.

This avoids full panel morphs for unrelated project changes and fits the
existing SSE-down fallback: the freshness probe becomes a self-described
pollable region while the stream is down. Events remain notifications rather
than content, matching the broker architecture.

### Save precondition

Add a single library transaction that accepts the editable fields, optional
detail-body action, and `ExpectedRevision`. Under the store lock it must:

1. load the item and detail;
2. compare the current item revision with `ExpectedRevision`;
3. return `ErrConcurrent` before mutation if they differ;
4. apply the field and detail changes to one transaction;
5. validate and atomically commit the complete write set.

The HTML and JSON edit endpoints should use this operation. A web-only check is
insufficient, and sequential `Update` plus `SetDetailBody` must not remain the
panel save path.

## UX state model

### Clean form, external change

Show an inline warning with `role="status"`/`aria-live="polite"`: “This item
changed elsewhere.” Offer **Reload item** and keep the current form visible
until selected. Reload replaces the panel from its normal route and updates the
baseline revision. Do not steal focus merely because the notification arrived.

### Dirty form, no external change

Save normally with the baseline revision. Successful save dismisses the panel
as it does today. Client-side dirty state is an aid, not the concurrency guard;
the server precondition is authoritative.

### Dirty form, external change

Show a persistent warning with `role="alert"`. Keep local inputs intact. Offer:

- **Review changes** — show original, local, and current values side by side;
- **Reload and discard mine** — guarded by explicit confirmation;
- **Keep editing** — dismisses no warning and does not authorize overwrite.

Save remains available only as a preconditioned save. If pressed, the server
returns `Concurrent` and the existing conflict dialog opens. There is no blind
“save mine anyway” action.

Phase 2's comparison may be field-level and a plain text diff for the detail;
it need not merge. Non-overlapping differences can be copied manually.

### Repeated external changes

Keep the form's original revision as the merge base and separately update the
latest observed revision/current snapshot. Coalesce notifications into one
warning; do not stack dialogs or reset local inputs. A resolved reload promotes
the latest snapshot to the new base.

### Item moved or finished

These are ordinary revision changes. Reload re-renders the new stage/state and
available actions. A stale save is refused exactly like any other conflict.

### Item removed

Show “This item was removed elsewhere,” disable Save, and offer **Close panel**
and **Reload board**. Never recreate the item from stale form data.

### Detail added, detached, or deleted

All change the item revision. A missing detail file that violates the board is
reported as unavailable/conflicted; the local textarea is preserved for manual
recovery.

## Phase boundaries

### Phase 1: detection and clean reload

- Library item-revision function.
- Revision on rendered panels.
- Generic `item` SSE notification plus SSE-down freshness polling.
- Item-specific freshness endpoint.
- Clean-state notification and explicit reload.
- Missing/unavailable states.
- No automatic form replacement.

Phase 1 can initially treat any input/change event as dirty and hand that state
to phase 2 behavior, ensuring it never destroys edits even before the full
comparison UI exists.

### Phase 2: loss prevention and explicit resolution

- Stable form-dirty tracking based on the rendered original values.
- Expected-revision submission on every edit.
- One atomic library operation for item fields plus detail body.
- `Concurrent` response on any view-lifetime mismatch.
- Dirty conflict warning/dialog, comparison view, guarded discard/reload.
- Repeated-change coalescing and deleted/moved/finished cases.

### Phase 3: merge, deferred

A future merge can use three snapshots already defined by phase 2:

- base: panel snapshot originally loaded;
- local: current form values;
- remote: latest server snapshot.

Structured fields can merge per field. Detail Markdown needs a diff3 algorithm
and a conflict editor. Adding that now creates substantial accessibility,
testing, and data-loss surface without evidence that comparison plus manual
resolution is inadequate. Revisit only after observing real phase-2 conflicts.

## Testing and accessibility requirements

- Server tests for revisions changing on board-line edits, detail edits,
  attachment/detachment, moves, finish, removal, and no-op writes.
- Transaction tests proving a stale expected revision writes neither
  `board.md` nor the detail file, and a valid combined edit commits both.
- SSE tests proving detail-only and board-only changes wake the panel probe.
- JavaScript tests for clean, dirty, repeated, missing, and unavailable states;
  inputs and focus must survive notifications.
- End-to-end tests with two panels plus an external file write.
- The warning must not rely on color; controls require stable labels and focus
  order. Conflict dialogs retain the existing focus trap and Reload-only
  no-blind-overwrite rule from spec-gui.md §5.10.
- SSE-down mode must converge through polling without refreshing an unchanged
  panel.

## Risks and dependencies

- The combined save operation is the highest-risk change because it replaces a
  currently non-atomic two-operation workflow. It belongs in `mm/`, not only in
  the web handler.
- A project fingerprint event may be noisy; the item-specific revision probe is
  what prevents unrelated changes from disturbing the form.
- Morphing the panel itself can overwrite live controls. The notification path
  must update only its dedicated status region until the user chooses reload.
- The existing echo-suppression window applies to board/status refreshes, not
  the panel. A successful save dismisses the panel, while note/action responses
  should not generate a stale warning in a surviving panel.
- T-0132/T-0133/T-0134 were cancelled because broad per-column file diffing did
  not justify its cost. This plan does not revive them: it retains the coarse
  broker signal and performs one targeted item comparison only when a panel is
  open.

## Follow-up tasks

Create two implementation tasks:

1. **T-0265, Phase 1** — item revisions, panel freshness notification, explicit
   clean reload, and SSE-down fallback.
2. **T-0266, Phase 2** — atomic preconditioned panel save, dirty/conflict state,
   comparison, and guarded discard/reload.

Do not create a phase-3 implementation task yet. Its gate is evidence from the
phase-2 conflict flow that manual resolution is insufficient.
