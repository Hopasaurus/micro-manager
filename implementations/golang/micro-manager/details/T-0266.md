# T-0266 — Phase 2: prevent stale item-panel saves and resolve conflicts

## Context

Follow-up from T-0261 and dependent on its phase-1 item revision. The current panel starts a fresh field transaction and then a separate detail transaction at Save time, so it neither detects changes since render nor commits the two editable sources atomically.

## Requirements

- Add one library transaction for editable item fields plus optional detail-body action.
- Accept the panel baseline as an expected revision and return Concurrent before mutation when current state differs.
- Commit board and detail changes atomically; a failure must write neither.
- Make both HTML and JSON edit paths use the preconditioned operation.
- Track dirty state from original rendered values without treating programmatic initialization as user editing.
- Preserve local inputs on external changes and repeated notifications.
- Provide an accessible comparison of base, local, and current values.
- Offer guarded Reload and discard mine plus Keep editing; never offer blind overwrite.
- Disable stale saves only as UI guidance; the server precondition remains authoritative.
- Handle moved, finished, removed, attached/detached detail, and temporarily invalid state.

## Verification

Test two-panel and external-editor races, stale and current revisions, atomic multi-file failure, repeated changes, field-level comparison, detail text diff, focus, keyboard flow, and conflict-dialog behavior.

## Dependency

Implement after the phase-1 follow-up from T-0261. Preserve the base/local/remote model so a future three-way merge can be added without changing the concurrency contract.
