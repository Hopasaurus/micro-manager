# T-0070 — Audit the templates against the testid, property and route indexes

## Context

`spec-gui.md` §12 says a conforming implementation renders every required
`data-testid`, exposes every CSS custom property, and serves every route — and
that the external suite locates elements *exclusively* by those names. That
suite is not written and is not a Go test. Until it exists, nothing here catches
a renamed testid, and after it exists, a Go test that fails in two seconds is
still cheaper than a browser run.

The three appendices of the spec are literal indexes. They can be read as data.

## Requirements

1. A Go test that parses Appendix A (testids), Appendix B (custom properties)
   and Appendix C (routes) **from the spec file itself**, rather than from a
   copy. A copied list drifts, and the drift is invisible.
2. Testids: render every view against a fixture and assert each required id is
   present. Interpolated forms — `item-<ID>`, `board-column-slot-<NN>`,
   `toast-<n>` — become patterns; the fixture must contain an item, a slot and a
   done item so the concrete forms actually appear.
3. Routes: assert the Echo route table contains every path in Appendix C, and —
   the half that matters more — that **no route shadows one in the list**
   (§4, "MUST NOT add a route that shadows one below").
4. Custom properties: assert the app-root style block defines every name in
   Appendix B, and that `mm.css` contains no literal colour outside the built-in
   fallback definitions (§8.4).
5. Fragment parity: for every partial, render it standalone and inside its page
   and assert the markup is identical. htmx swaps fragments in, and a fragment
   that differs from its first-render form breaks the external suite in a way
   that only shows up after an interaction
   (`project/architecture.md` §4.3).
6. Failure output names the missing id, property or route. "Appendix A item 37
   not found" is not usable; `board-column-slot-01` is.
7. When the spec is edited, this test is what tells us the implementation
   drifted. That makes it the closest thing this module has to the conformance
   suite, so it runs in the default `go test ./...` and is not tagged or
   skipped.

## Open questions

- Whether the fixture used here is one of the existing `testdata/` directories
  or a new one built for full DOM coverage. `clean-full` may already have the
  shape; check before adding another.
