# T-0247 — Regroup board.md by stage on every write, blank-line separated

Reported live: "Blocked doesn't appear to be orderable." Reordering within
Blocked actually worked fine at the data layer (verified directly via the
CLI before implementing anything) — the real problem was that board.md is a
flat, insertion-order list (spec-file-format.md §5.1.6), so items from
different stages end up physically interleaved in the file. Reading the
raw file (or anything that shows it), Blocked's items never appear as a
contiguous, inspectable sequence, which is what actually looked like "no
order."

§5.1.6 explicitly permits the fix: "a writer MAY still group items
physically by stage for a human reading the raw file." Asked the user
which operations should trigger it (every mutation / just move / a
separate explicit command) — chose every mutation, so the file stays
continuously tidy rather than only right after a drag.

## Implementation

`mm/board.go`'s new `regroupBoard(b *boardFile, e *fileEdit)` rewrites
board.md's item lines into contiguous blocks in `stages:` declared order,
one blank line between each non-empty group. Hooked into ONE central
place, `tx.go`'s `stage()` (guarded on `name == "board.md" && t.model.board
!= nil`), rather than added to each of the ~10 v2 operations that write
board.md — every future v2 operation gets it automatically, nothing to
remember per op.

- Content between the frontmatter and the first item (the board's own
  heading and any introductory prose) is preserved verbatim.
- Content interspersed among or after the items is NOT preserved — regroup
  fully replaces everything from the first item's current line to the end
  of the file. Nothing today writes such content there, and §5.1.6
  requires only that a reader ignore non-item content, not that a writer
  preserve its position. Documented as a deliberate, known limitation
  rather than something silently different from before.
- An item whose `stage:` is not among the declared `stages:` (a
  pre-existing I4 violation, not something this may introduce) is NOT
  dropped — it survives at the end of the file. This matters because §7's
  own discipline is "preserve or fix a pre-existing problem, never make it
  worse by deleting data."
- Only runs when board.md is already dirty for a real reason (`tx.stage`'s
  existing `e.Dirty()` gate, unchanged) — a genuine no-op write still
  writes nothing (`TestV2NoOpMoveWritesNothing`, unaffected).

New tests in `mm/board_test.go`: `TestMoveRegroupsBoardByStage` (a fixture
whose file order does NOT match `stages:` order gets fully re-laid-out by
a single move, validates cleanly afterward),
`TestRegroupSkipsEmptyStagesCleanly` (no orphaned blank lines when a
stage empties out), `TestRegroupPreservesAnItemOnAnUndeclaredStage` (the
data-loss guard above, proven directly).

Verified live end to end, not just via unit tests: added a second Blocked
item through the real running GUI (new-item panel, Stage: Blocked) against
a fixture whose original file order was someday/ready/ready/blocked/
working/review with no blank lines at all — the write landed the new item
in board.md's blocked group, correctly separated from ready and working by
blank lines, and the board's Blocked column rendered both items normally.

`go build`, `go vet`, `gofmt -l`, and the full `go test ./...` (mm,
internal/cli, internal/web including the jstest node suite) are all green
with no other test changes needed — existing coverage checks logical
`Stage`/`StageItems()` properties, not raw physical file layout, so it was
insensitive to this change everywhere except the new tests written to
specifically prove it.

## Notes

board.md now regroups by stage on every mutation via a single hook in tx.go's stage(), preserving pre-existing violations rather than silently dropping items. Verified live through the GUI. See details/T-0247.md.
