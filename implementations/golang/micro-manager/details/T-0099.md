# T-0099 — broker.Subscribe: gate wg.Add behind a closed flag so shutdown cannot race Wait (F7)

Finding **F7** of `project/code-review-006.md` (PLAUSIBLE — not reproduced).

## The bug

`internal/web/broker.go`:

- `Subscribe` (line ~74) calls `b.wg.Add(1)` under `b.mu`.
- `close()` (line ~124) calls `b.rootCancel()` then `b.wg.Wait()` — without
  taking `b.mu` and with no `closed` flag to gate new subscriptions.

`Server.Start` returns → `broker.close()` cancels `rootCtx` and blocks in
`Wait()`. An in-flight `GET /api/v1/events` reaches `Subscribe`, finds no
existing subscriber for its project, and calls `Add(1)`. If the last poller
has already exited so the counter is 0 while `Wait` is blocked, the runtime
panics with `sync: WaitGroup misuse: Add called concurrently with Wait` and
takes the process down during shutdown.

Narrow interleaving, never reproduced — but nothing in the code prevents it.

## Fix direction

A `closed bool` checked under `b.mu`: `close()` sets it (and cancels the root
context) before `Wait()`, and `Subscribe` returns an already-closed channel
when it is set, so no `Add` can land after `Wait` begins.

## Verify

- Hard to hit naturally; the fix should be provable by inspection and, if
  practical, a stress test that hammers Subscribe/close concurrently under
  `-race`.
- Normal subscribe/unsubscribe/poll behavior must be unchanged.

## Notes

**2026-07-31** — closed bool set by close() under mu before rootCancel/Wait; Subscribe checks it under the same lock it already holds and returns an already-closed channel, so no Add can land after Wait begins. close() is now idempotent. The SSE handler already exits on a closed channel, so a refused subscription ends the stream cleanly rather than blocking. Observed failure mode of the unfixed code under the stress test is a livelock (close never returns, because new pollers keep being added while Wait blocks) rather than the panic - same root cause, Add after Wait began.

TestBrokerCloseDoesNotRaceSubscribe added: 8 goroutines subscribing straight through close, -count=5 under -race. Verified it catches the regression (443s hang, FAIL).
