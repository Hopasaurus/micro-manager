# T-0245 — Dragging a fresh working item into a needs_reason stage refused with the dialog stuck open

Reported live against a real project (`simple-signage`, a v2 board with
`needs_reason: blocked`): dragging a working item with no existing `reason:`
into a needs-reason stage opened dialog-block as expected, but typing a
reason and clicking Block produced a toast, left the item in `working`, and
the dialog stayed open.

## Root cause

`dialog-block`'s form (`internal/web/templates/partials/dialogs.html`) is a
single submission: it asks for the reason, then posts to `/pause` with both
`stage` and `reason`. But `pauseV2` (`mm/board_ops.go`) never accepts a new
reason at pause time — it only checks whether the item **already** carries
one for a needs_reason destination (a deliberate v1/v2 decoupling, "research
decision 18": v1's `blocked:` travels with the move, v2's `reason:` does
not). Both web mutation handlers read the submitted `stage` field but never
threaded the submitted `reason` into anything the library would see:

- `internal/web/item.go`'s "pause" case set `req.Stage` but had no
  `PauseRequest.Reason` field to put the reason in (it doesn't exist -
  `PauseRequest` only has version 1's `Blocked string`).
- `internal/web/api/items.go`'s generic mutation dispatch had the identical
  shape, independently.

So for a "fresh" item (no `reason:` yet), `pauseV2` always refused with
"needs a reason", regardless of what the dialog's form carried — the
dialog's own submitted text was silently discarded before it ever reached
the library. This exact gap was found and deliberately deferred during
T-0236 (spawned as its own follow-up task then), and is now fixed directly
since a live user hit it.

## Fix

Both handlers now set the item's `reason:` field via `store.Update(id,
UpdateRequest{Blocked: &reason}, ...)` **before** calling `Pause`, when a
stage and a non-empty reason arrive together — chaining the two library
calls within one HTTP round trip so the dialog's single submission works
end to end, matching what a user reasonably expects from a form that asks
"what is it waiting on?" and has one "Block" button. `updateInternal`
already generalizes `UpdateRequest.Blocked` to `it.Reason` for a version-2
item (`op_update.go`), so no library change was needed - only the two web
handlers had to actually use it.

`internal/web/dragdrop_test.go`'s `TestWorkingToBlockedPromptsAndPauses`
previously asserted the bug's behavior as correct (refuse, then a two-step
edit-then-pause workaround); rewritten to assert the single-submission
success it now is. Added a new case to
`internal/web/api_handlers_test.go`'s `TestAPIOperations` covering the
JSON route's identical fix.

`go build`, `go vet`, `gofmt -l`, and the full `go test ./...` are all
green.

## Notes
