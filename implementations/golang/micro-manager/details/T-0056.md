# T-0056 — Render the board with columns, item cards and query filters

## As built

`internal/web/board.go`, `templates/board.html`,
`templates/partials/item-card.html`.

**One template renders every card.** `item-card.html` is the single place a
card's markup exists — the board, a search result, an htmx swap after a mutation
and eventually the report all reach that one definition. That is what makes the
DOM contract holdable rather than something to remember in five templates.

**Column order is fixed and asserted positionally**: ready, blocked, someday,
one per working file in slot order, then done (§5.5).

**`data-position` is 1-based within its column**, recomputed on every render. It
is how a test asserts ordering without reading text, and it is what a rejected
drag has to restore (§7.1).

**Action legality is computed once, on the server**, by `actionsFor`, and shared
by the card menu and the item panel. Illegal actions are rendered **present and
disabled with `data-reason`** naming the error code — the same code the server
would return if the operation were attempted, so the client's early disable and
the server's refusal cannot disagree (§2.1, §5.5).

**A free-text query goes through the library's search**, so the board's `?q=`,
the CLI's `--search` and the API agree about what matches. `SearchItems`
collapses hits to distinct items, because the board renders cards and one card
per matching line would be a different view of the same project.

## The spelling boundary

`mm.Section` values are **capitalised** — `Ready`, because they name the
`## Ready` heading in the file — while the DOM contract fixes them **lowercase**:
`data-section="ready"`, `board-column-ready`. Rendering the library's spelling
straight into the markup produced `board-column-Ready` and every §5.5 testid was
wrong.

`sectionKey` and `parseSection` are the one boundary between the two spellings.
Nothing else in the web layer may write a section into markup directly.
