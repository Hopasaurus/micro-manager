# T-0253 — Optional time on created/started/updated; opt-in audit.md action log

Two requests bundled together:

1. `created`, `started` and `updated` MAY carry an ISO 8601 time (the
   existing `TIMESTAMP` token), not just a bare `DATE`. Still optional — a
   plain date stays valid, and nothing starts requiring a clock.
2. A new opt-in `audit.md`, enabled by a line in `board.md`, recording a
   timestamped (date+time) machine-parsable entry per changed field: task
   id, field name, new value (blank for a detail-file body change, unless
   something else reads better). GUI gets a toggle to enable it and a page
   to view it.

## Design decisions

- **Round-trip, not rewrite.** `created`/`started` stay `Date` internally
  (everything that computes cycle time, flight time, report grouping etc.
  keeps working on the calendar day, untouched) plus a new sibling string
  field carrying the optional `THH:MM:SSZ`/`±HH:MM` suffix verbatim. This
  avoids threading a new type through every consumer — nothing but
  itemline.go's parse/render needs to know the suffix exists.
- **`updated` needed no struct change** — it was never actually validated
  as a DATE anywhere (`fm.Get`/`fm.Set` on a raw frontmatter string); it
  only gets an added shape check (DATE or TIMESTAMP, when present) so
  "keep it in ISO 8601 format" is actually enforced instead of accepting
  anything.
- **The tool's own writes stay date-only by default.** "Optional" means
  accepted, not required or auto-upgraded — `touchUpdated` keeps writing a
  bare date so no existing test asserting `updated: 2026-08-26` breaks.
  A time only appears where a human (or a future feature) put one there by
  hand, and it survives untouched through every operation that doesn't
  touch that specific file. The dedicated `--created`/`--started` CLI
  flags and JSON API fields stay date-only backfill conveniences; the full
  form is reachable through `--edit --set created:VALUE` / the JSON `set`
  array, mirroring how `--set` is already the general "any field, any
  value" escape hatch elsewhere.
- **Audit reuses the existing `Change`/`t.record` machinery** already
  populated by every v2 operation (`board_ops.go`) for dry-run reporting.
  Each `Change` carries a full rendered before/after item line; a generic
  differ (reusing the item-line field splitter) finds which `key:value`
  pairs actually differ and emits one audit line per changed field — no
  per-operation instrumentation needed for the common paths. `ChangeCreated`
  (no before) logs every field on the new line; `ChangeDeleted` (no after)
  logs one `field:removed` line with a blank value; a pure reorder (no
  field diff) logs nothing, which is correct — no field changed. A
  detail-file touch (any `File` that isn't `board.md`/`done.md`) logs one
  `field:detail` line with a blank value, its creation/removal included.
  A `Change` with no `ID` (a board-level config edit, e.g. a WIP limit or
  the `audit` key itself) is not an item action and is never logged.
- **Found and fixed while wiring this up:** `moveV2` mutated `started:`/
  `reason:`/`tickler:` on the item BEFORE taking its `Before` snapshot for
  the `Change` record, so those fields were invisible to the differ — only
  `stage` (set later, via `InsertItem`) ever showed. Moved the snapshot to
  the top of the function, before any mutation. Also: `writeItemLine`
  (used by `--note` and `--edit --detail` to attach a new `detail:` field
  to an existing item) stages the write but records no `Change` of its
  own; `op_note.go` and `AttachDetail` (`op_detail.go`) now snapshot
  before/after around it themselves, the same shape `updateInternal`
  already used for `--edit`. Caught by writing the tests below, not
  invented in the abstract.
- **v2 only**, per the request ("a line in board.md"): gated on
  `t.model.board != nil && stageCfg.AuditEnabled`.
- **Timestamp source:** a `Store.clock func() time.Time` (default
  `time.Now`, overridable in tests — mirrors `internal/web`'s existing
  `registry.now` pattern), read once at `tx.commit()`.
- **Audit format** (plain, greppable, matching the rest of this format's
  `key:value` convention rather than introducing JSON):
  `TIMESTAMP | id:ID | field:NAME | value:VALUE`
  One line per changed field. Never validated (like an archive) — it is a
  log, not board state.
- **Known, accepted limitation:** the rarer administrative operations
  (`--fix`, `--archive`, `--migrate`) were not individually audited for
  complete before/after field coverage the way the everyday lifecycle
  operations (add, start, pause, finish, block/unblock via move, edit,
  note, remove) were — some of their `Change` records may log a bare
  `field:detail`/incomplete entry rather than the precise field that
  changed. Documented here rather than in the normative spec, since it's
  an implementation gap in this build, not a format allowance.

## Tests

`mm/item_test.go`: `TestParseDateOrStamp` (bare date, three valid TIMESTAMP
forms with round-trip, seven rejected shapes). `mm/itemline_test.go`:
round-trip case with timestamped `created:`/`started:`, a rejection case
(no offset). `mm/board_test.go`: `TestParseBoardValidatesUpdatedShape`.
`mm/audit_test.go`: pure-function tests for `auditFieldChanges` (creation,
move, pure-reorder-is-empty, delete, detail-touch) and `appendAuditEntries`
(skips no-ID changes, writes the header once); integration tests against a
real `Store` — disabled-by-default, add+start logging, dry-run writes
nothing, `SetAudit` toggling and its version-1 refusal, the moveV2
reason/started regression, and the note-as-blank-detail-value case (which
caught the `writeItemLine` gap above). `internal/web/settings_test.go`:
`TestProjectSettingsAuditToggle` (v1 has no toggle; v2 toggles on/off,
correctly re-renders `settings-audit-view`). `internal/web/audit_view_test.go`:
unavailable-on-v1, disabled-by-default, empty-when-enabled, and
entries-render-newest-first. `internal/web/audit_test.go` (the Appendix A
contract audit): extended to exercise every new state and pattern.

Verified live: enabled audit via the Settings checkbox in a running
browser, confirmed `board.md` gained `audit: true`, moved an item with
`--reason` and confirmed both `field:stage` and `field:reason` lines
appeared (this is what caught the moveV2 ordering bug above), and viewed
the populated table on `/p/:id/audit` sorted newest first.

`go build`, `go vet`, `gofmt -l`, and the full `go test ./...` (mm,
internal/cli, internal/web including the jstest node suite) are all green.

## Notes

Both features shipped: created/started/updated accept an optional ISO8601 time (round-tripped, never required), and audit.md is a new opt-in per-field action log wired through the existing Change-recording machinery, with a Settings toggle and a viewer page. Found and fixed two pre-existing Change-recording gaps (moveV2's snapshot ordering, writeItemLine's missing Change) while testing it end to end.
