# T-0249 — Allow reordering within working (drag + spec)

Follow-up from a direct question during T-0248's investigation: "which
stages are forbidden from reordering?" Answer at the time: only `working`,
via one hardcoded line in `mm.js`'s `legality()`. Asked to remove it, and
fix the spec if needed — it was needed: `spec-gui.md` §7.2's own Legal
Transitions table explicitly marked `working → working` **illegal**, which
actually *contradicted* `spec-tools.md` §5.1.7's own text ("Moving into
`working` or out of `working` is legal here too"). The library
(`moveV2`) already had no restriction on a same-stage move within
`working` — this was a client-only rule with no library rule behind it,
and a spec self-contradiction underneath that.

## Why it was ever forbidden

Version 1 modeled `working` as N separate slot files (`working.NN.md`),
each holding at most one item with no shared order across slots — there
was no "position" concept to rearrange. Version 2's `working` is an
ordinary declared stage with its own flat, ordered run
(`spec-file-format.md` §5.1.6), exactly like `ready`/`blocked`/`someday`/
any custom stage — the old restriction just never got revisited when v2
generalized `working` into a real stage.

## What changed

**Spec** (`project/spec-gui.md` §7.2): row 1 broadened from "any
non-`working`, non-done column" to "any non-done column" (working
included); the `working | working` row flipped from illegal to
`--move --position N`, cross-referenced against `--start`'s own,
unrelated `Conflict` (starting an item already on `working` is still
illegal — a reorder is not a re-`--start`). `project/spec-tools.md` §6.3's
`Conflict` example was also corrected: "moving an already-`working` item
into `working`" was ambiguous with, and read as forbidding, exactly the
reorder this task legalized; reworded to name `--start` specifically and
state the `--move` case explicitly.

**Code** (`internal/web/static/mm.js`): deleted the one line
(`if (from === 'working' && to === 'working') return conflict`) — `legality()`'s
very next line, `if (from === to) return { allowed: true, op: 'move' }`,
already handles every other stage's reorder identically, so removing the
exclusion was the entire fix. Nothing else needed to change: `moveV2`
already skips the WIP check when `to === from`, and never re-stamps
`started:` on an item that already has one.

## Tests

`internal/web/jstest/mm.test.js`: a new "reordering within working is
legal" case (two working items, drag one past the other, confirms
`data-drop-allowed="true"` and a plain `move` posts with `stage` set, no
`section`). The pre-existing "an illegal drop issues no request" case
used working→working as its example of something refused — since that's
no longer true, rewritten to use reopening a done item instead (still
illegal, unrelated to this change). `internal/web/dragdrop_test.go`'s
`TestIllegalTransitionsAreRefused` split into a "starting an
already-working item" case (unchanged behavior, corrected wording) and a
new v2-level "reordering within working" case proving the real HTTP round
trip succeeds and lands the new order — the old subtest ran against a
version-1 fixture and so only "passed" because version 1 refuses all
mutations outright (T-0236), never because of any working-specific rule;
that coincidence is now replaced with a test that actually proves what it
claims. `mm.js`'s line-count architecture guard raised 990→1010 with the
usual per-change justification.

Verified live: dragged one working item above another in a running
browser (real `DragEvent`s), confirmed `data-drop-allowed="true"` during
the hover, and the two items' order swapped correctly in `board.md`.

`go build`, `go vet`, `gofmt -l`, and the full `go test ./...` (mm,
internal/cli, internal/web including the jstest node suite) are all
green.
