# T-0242 — Make item detail resizable.

Add a drag thing so that item detail is resizable.  Start at minimum of 33% view width.

## Notes

**2026-08-21** — Shipped. The item panel (spec-gui.md §5.6, `item-panel.html`,
`.mm-panel`) is a fixed right-side overlay that was a hard-coded
`width: min(32rem, 100%)`. Added a thin drag handle along its left edge
(`x-item-panel-resize-handle` — `x`-prefixed per §5.1, since resizing is a
client affordance the spec's testid list doesn't name) and pointer-based
resize logic in `mm.js`.

Width is a client-only preference, never sent to or persisted by the
server, stored in `localStorage` as a percentage of the viewport width
(`mm:item-panel-width-vw`) rather than a raw pixel count so it stays
sensible across a resized browser window. 33vw is both the default and the
floor — the panel can never be dragged (or loaded) narrower than a third of
the viewport, matching the task's own ask; 90vw is the ceiling, left as a
reasonable choice (not specified) so a sliver of the board always stays
visible. The stored width is applied on every render the panel can appear
in — a fresh `/item/:id` load, the new-item panel, and "save and add
another" reopening a copy (T-0080) — the same "born correct, never applied
a frame late" shape T-0150's collapse-state fix and T-0240's generalization
of it already established for the board's own column-collapse preference,
reused here for a second, unrelated client preference.

Not done, and deliberately out of scope: keyboard resizing. The codebase's
own accessibility rule (§6.2: every drag has a non-drag equivalent) is
about reachability of real operations — start/pause/move/finish — not
cosmetic sizing that never blocks any task if left at its default; the
panel is fully usable and every field reachable at 33vw. Worth adding later
if it turns out to matter in practice, but the task asked for a drag
affordance specifically and nothing here should stop a keyboard-only path
from being added on top without touching this shipped shape.

New coverage: `internal/web/item_test.go`'s `TestItemPanel` asserts the
handle's testid renders; four new `internal/web/jstest/mm.test.js` cases
cover the drag math (floor/ceiling clamping, a mid-range drag honoured
exactly), that a released drag stops listening to further pointer moves,
and the load-time restore (including clamping an out-of-range stored
value, not trusting it verbatim). `dragdrop_test.go`'s
`TestDragAttributesArePresentInTheClient` line-count ceiling (§4.6 of the
architecture: keep `mm.js` small) moved 900→960, with the same
per-change justification comment every prior bump used.

Verified live in a browser (isolated config-home): dragging the handle to
the browser's exact horizontal midpoint set the panel to precisely 50vw
and wrote `50` to `localStorage`; reopening the panel (a fresh page
navigation, not just a re-render) restored 50vw immediately with no
flash of the old default.

`go build`, `go vet`, `gofmt -l`, and the full `go test ./...` (mm,
internal/cli, internal/web including the 40-test `jstest` node suite) are
all green.

Added a drag handle to the item panel's left edge and pointer-based resize logic in mm.js; width defaults to and floors at 33vw, ceilings at 90vw, persisted client-side and applied before paint on every render. See details/T-0242.md for the full breakdown.
