# T-0267 — Create a versioning system

## Problem

Product-version strings currently drift between components:

- the Go CLI reports `0.2.0`;
- the Go UI reports `0.1.0-dev`;
- the local TypeScript scaffold uses `0.0.0`, but the entire implementation is
  intentionally git-ignored and has no committed executable version surface;
- the pi plugin package uses `0.1.0`;
- the specifications expose only their independent integer compatibility
  versions (currently version 2).

There is no canonical product version or repeatable bump operation. A release
can therefore publish tools that implement the same overall micro-manager
release while reporting unrelated versions.

## Goal

Establish one repository-wide semantic product version, provide a script that
validates and bumps it, and make every implemented CLI/UI plus the top-level
specification metadata report that same value. Exercise the mechanism by
bumping the current product version one patch level.

The product version is release identity. It remains separate from format,
tools, GUI, TUI, configuration-schema, and JSON-schema compatibility versions;
those integers change only when their respective contracts become incompatible.

## Recommended design

Use a root `VERSION` file containing one bare SemVer value (no `v` prefix and
one terminating newline) as the canonical source for repository tooling and
human readers. Compiled programs cannot reliably locate repository files at
runtime, so builds should inject or generate their version from this source;
development fallbacks must be explicit and must not become a second release
version.

Add a repository-root script with a narrow interface, for example:

```text
./version.sh current
./version.sh check
./version.sh bump patch
```

`current` prints the canonical value. `check` is read-only and fails if a
committed mirror or program-reported value disagrees. `bump patch` computes the
next version, validates the complete prospective edit, then updates all
committed mirrors together. Reject malformed SemVer, unknown bump kinds, a
dirty/inconsistent version state, and any partial update. Do not create a git
commit, tag, release, or publish artifacts.

Prefer build-time injection for Go (`-ldflags -X`) with a clearly named
development fallback, and keep local `go run`/`go test` useful. JavaScript
package manifests still need synchronized literal versions because package
tooling reads them without executing project code. The bump/check script is
the enforcement boundary across languages.

## Scope

1. Add the canonical product-version source and bump/check script at the
   repository root.
2. Make the root build/install recipes inject the canonical version into both
   Go binaries. Direct development builds retain a documented fallback.
3. Make `mm --version`, `mm-ui --version`, the UI About view, health response,
   and `mm --help --json` report the same product version.
4. Add a product/release version field to the metadata block of each normative
   specification without changing its existing spec-version field or meaning.
5. Require future implemented non-Go CLIs/UIs to consume the root `VERSION`.
   Do not modify ignored local scaffolds or invent executable version surfaces
   for placeholders that have not reached the repository.
6. Keep the pi plugin on its own package lifecycle. Document that exclusion;
   `version.sh check` must not compare or rewrite its package version.
7. Update user-facing version examples that assert the repository's actual
   version. Leave deliberately arbitrary fixture values such as `1.4.0` and
   `9.9.9` unchanged.
8. Run the bump operation for one patch increment and verify a second `check`
   is a no-op.

## Safety and behavior

- Parse SemVer rather than incrementing text with an unanchored substitution.
- Preserve unrelated content and formatting in every touched file.
- Validate that every expected old value occurs exactly where intended before
  writing anything; ambiguity or drift must abort without a partial bump.
- Write replacements atomically or stage all validated temporary files before
  replacing originals.
- `check` must work in CI and identify each mismatching file/value.
- The script must be independent of the `mm` binary so it can repair or build a
  checkout whose binary is absent.
- Running a patch bump on stable `X.Y.Z` produces `X.Y.(Z+1)`. A prerelease
  promotes its existing core version to stable rather than incrementing it.
- Supported prerelease spellings are valid SemVer forms such as `-beta`,
  `-beta.1` (release-candidate sequence), or `-beta.<git-hash>`. The optional
  suffix is explicit input; the ordinary patch command does not manufacture a
  timestamp, counter, or hash.

## Acceptance criteria

- One documented source names the repository product version.
- A clean checkout passes `./version.sh check`.
- The patch bump changes exactly the intended version-bearing files and a
  second check confirms that all mirrors agree.
- Both freshly built Go binaries report the new product version; CLI JSON,
  health, and About agree with them.
- Each normative spec clearly distinguishes product version from its own
  compatibility/spec version.
- Relevant Go and repository-level tests cover version reporting, bumps,
  prerelease promotion, and drift detection; all existing build, test, vet,
  and board-validation suites pass.
- No tag, commit, release, or publication is created by the bump script.

## Likely files

- `VERSION`, `version.sh`, root `Makefile`
- `implementations/golang/internal/cli/cli.go`
- `implementations/golang/internal/web/version.go`
- `implementations/golang/cmd/mm-ui/main.go` and About/health tests
- future non-Go implementation manifests once those implementations are
  committed and expose a CLI or UI
- `plugins/pi-mm/package.json` is explicitly excluded because the plugin has an
  independent package lifecycle
- `project/spec-*.md` metadata blocks

## Resolved decisions

1. The canonical baseline is `0.2.0`; exercising the patch bump produces
   `0.2.1`.
2. The pi plugin retains its independent package version and is outside the
   repository product-version bump.
3. Supported Makefile/release builds inject the canonical `VERSION`. A direct
   `go build` uses an unmistakable development fallback rather than requiring
   generated source to be committed.
4. Prereleases use `-beta`, optionally followed by a release-candidate number
   or git hash (`-beta.1`, `-beta.<hash>`). Promoting a prerelease removes the
   suffix without incrementing its core patch number.
