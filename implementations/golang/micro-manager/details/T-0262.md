# T-0262 — Vet changing an existing board ID prefix from the CLI

## Context

`mm --init --prefix P` already selects the ID prefix for a new board, but there is no flag for changing the prefix of an existing board. Because the prefix is embedded in every item ID, `next_id`, detail frontmatter and filenames, references, and possibly archives, this is a board-wide migration rather than a simple setting edit.

## Investigation

- Clarify the user workflow and command shape: extend a settings/edit operation, add a dedicated migration flag, or explicitly keep prefixes immutable after initialization.
- Inventory every location that must change, including active and done items, `next_id`, detail files and headings, structured refs, audit/history data, and archives.
- Decide how free-form text that mentions IDs should be treated.
- Define collision handling, atomicity, rollback, dry-run preview, validation, and JSON/porcelain output.
- Evaluate compatibility with I1, I2, I9, discovery, external links, and concurrent writers.

## Done when

Record a go/no-go recommendation, preferred CLI contract, exact migration semantics and safety checks, affected specs/components, and scoped follow-up implementation tasks if approved.

## Source

Requested while reviewing the feature ideas in `xfer/working-with-mm.md`; related existing behavior is `mm --init --prefix P`.

## Recommendation

**No-go for changing `id_prefix` on an existing board in the current format.**
Keep `--prefix P` scoped to `--init`; do not add it to `--edit`, project
settings, or a generic frontmatter setter.

This is not merely an implementation-risk judgment. `spec-tools.md` §5.1.1
already says the prefix is a grammar decision a board cannot re-make later,
and format §3.3.2 requires one grammar for every ID in the directory. More
importantly, I2 says IDs are never reused or renumbered. Changing `T-0042` to
`GO-0042` changes the item's identity even though the numeric suffix survives.
A tool cannot call that a conforming edit without first changing the format
contract and the meaning of I2.

The user-facing rule should therefore stay simple:

- `mm --init --prefix GO` chooses a new board's permanent ID namespace.
- `mm --edit --prefix GO` and a standalone `mm --prefix GO` remain invalid
  combinations rather than looking like a cheap setting change.
- A board that needs a different prefix today should create a new board and
  move/copy work deliberately, preserving the old IDs as provenance in prose
  or an extension field if needed. There is no automated identity-preserving
  move in the current spec.

No unresolved product question is required to reach this recommendation.

## Migration blast radius

A hypothetical rekey is a whole-board, and partly tree-wide, migration. It
would have to account for all of the following:

1. `board.md`: every active item ID, `next_id`, `id_prefix`, local structured
   fields whose values contain IDs, and `updated`.
2. `done.md`: every completed item ID and each live detail path.
3. `details/<ID>.md`: filename, `id` frontmatter, canonical title heading, and
   any structured references. Detail prose is unstructured Markdown.
4. `done-YYYY.md` and `details-YYYY/<ID>.md`: archived IDs, paths, filenames,
   and detail frontmatter/headings. Archives are deliberately outside
   validation, so omitting one can silently create duplicates or broken links.
5. Other discovered boards: `refs:<board-slug>:<ID>` values targeting this
   board. These are advisory and tree-relative, so no operation confined to
   one directory can find every inbound reference.
6. `audit.md`: historical `id:` values. It is append-only and MUST NOT be
   rewritten, so changing them would violate the log contract; leaving them
   unchanged would require a permanent old-to-new identity record for audit
   interpretation.
7. External links, scripts, issue references, shell history, bookmarks, and
   prose anywhere else are unknowable and cannot be migrated safely.

Free-form text must never be search-and-replaced. A token resembling an ID in
a title, reason, note, detail paragraph, `structure.md`, unregistered field, or
external document may be an example, a historical reference, or an ID from a
different board. Only grammar-defined structured locations could be rewritten.

## Safety analysis

- **Collisions:** changing only the prefix is one-to-one among the board's
  current IDs, but target detail filenames can already exist as orphans, and
  archives can contain IDs invisible to normal validation. Inbound references
  may also become ambiguous across discovery roots.
- **I1/I2/I9:** a partial rewrite creates mixed grammars, duplicate identities,
  dangling detail paths, or detail frontmatter drift. A completed rewrite still
  violates current I2 because all IDs changed.
- **Atomicity:** the transaction layer can preflight stamps before its first
  write, but POSIX cannot atomically rename an arbitrary set of board, detail,
  archive, audit, and foreign-board files. Crash recovery would require a
  durable migration manifest and an idempotent resume/rollback protocol.
- **Concurrency:** every owned source and destination must be stamped before
  commit, including non-existent target filenames. Any change aborts before the
  first write. Tree-wide inbound refs cannot share that guarantee unless every
  participating board is locked into one coordinated transaction.
- **Discovery/project identity:** the GUI `projectId` is path-derived and the
  cross-board `board` slug is independent, so neither changes automatically.
  The rekey nevertheless invalidates every link containing the old item IDs.
- **Output:** a credible operation needs a complete old-to-new mapping and file
  plan in normal, JSON, and porcelain modes. `--dry-run` must perform every
  parse, collision, reference, archive, and stamp preflight without writing.

## If the format is deliberately revised later

Use a dedicated, conspicuously migratory operation—not a settings flag:

```text
mm --rekey-prefix GO [--include-archives] [--update-refs ROOT] --dry-run
mm --rekey-prefix GO [--include-archives] [--update-refs ROOT] --yes
```

The future spec would first need to define whether identity survives a rekey,
supersede I2 accordingly, define an immutable old-to-new alias ledger, decide
whether archives are mandatory, and state the boundary for inbound-reference
updates. Execution should require a successful dry-run plan (or an explicit
confirmation showing the same mapping), reject all collisions and malformed
structured data, never rewrite prose, and use a durable recovery manifest.

If that policy is approved, split implementation into scoped follow-ups:

1. Revise the format/tools specs: identity semantics, alias ledger, archive and
   audit treatment, recovery rules, and CLI/output contract.
2. Add a read-only rekey planner returning the complete mapping, affected-file
   inventory, collisions, unresolved inbound refs, and dry-run renderings.
3. Add the single-board transactional executor plus crash-resume/rollback and
   fault-injection tests.
4. Add optional discovery-root inbound-ref rewriting as a separate coordinated
   operation; never imply it found links outside the declared root.
5. Add CLI JSON/porcelain rendering, confirmation UX, validator fixtures, and
   end-to-end tests spanning live items, done items, details, archives, audit,
   collisions, and concurrent writers.

Until those format decisions are intentionally made, implementing any portion
would create a tool that can silently invalidate identity and history. No Go
implementation task should be opened from this spike's current no-go result.
