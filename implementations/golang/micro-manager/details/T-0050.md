# T-0050 — Enforce loopback binding with Host, Origin and CSP guards

## Context

`spec-gui.md` §9.6. The service has unauthenticated read and write access to the
user's files, the specification defines no authentication, and so it requires
the service to be unreachable from the network. This is not hardening on top of
a working service — it is the thing that stands in for authentication, which is
why it landed before there was anything worth reaching.

## As built

`internal/web/guards.go`, wired in `New` and as the first middleware.

**The refusal happens in `New`, not in `Start`.** A misconfiguration is then a
startup error, and can never be a service that came up on an address the user
did not intend and only failed later.

**A hostname must resolve entirely to loopback.** `localhost` is fine;
a name resolving to both `127.0.0.1` and a routable address is refused, because
checking only the first answer would pass a name that then listens on the
second.

**`0.0.0.0` and `::` are named separately** in the refusal even though the
loopback check would catch them, because §9.6 rule 3 makes the point that
binding every interface is never the accidental outcome of a default — and the
message a user sees should say that.

**Every refusal names what to do about it.** A guard whose message a user cannot
act on is a guard they turn off. The bind refusal names the address, says what
the service can reach, and names `server.allowRemote` as the deliberate way
through. A test asserts the address appears in the message.

**Host is checked before anything else runs.** This is DNS-rebinding defence:
loopback binding alone does not help, because any page the user visits can issue
requests to `localhost`, and a hostname the browser already trusts can be
repointed at `127.0.0.1`. Anything but `localhost`, a loopback literal, or a
configured hostname is 421.

**Origin is checked only on state-changing methods**, and an absent Origin is
allowed — curl and a script send none, and a browser always sends one for the
requests this rule is about. A foreign Origin on a `GET` is not this rule's
business; the Host check is what protects reads.

**Security headers are set before the guards run**, so a 421 or 403 carries them
too. A refusal that leaked CORS headers would be a hole with a tidy status code,
and a test asserts on exactly that response.

**No CORS header is ever sent.** Not `*`, not a reflected origin. A test walks
every response header looking for the request's origin echoed back, which is the
failure mode a naive CORS implementation has.

## The one deliberate loosening

`style-src` carries `'unsafe-inline'`. §8.7 requires the theme's custom
properties to be inlined in the served HTML — that is what makes a project
switch free of a flash of the previous theme — and an inline `<style>` block
needs either this or a per-request nonce. A nonce is stricter and is the obvious
upgrade if that block ever carries anything but tokens; it is not free, because
the nonce has to reach every template that renders the app root.
