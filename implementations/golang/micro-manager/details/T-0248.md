# T-0248 — Custom v2 stages (e.g. review) were entirely undraggable, then rejected once fixed

Reported live against `simple-signage`'s real board (`stages:
someday,ready,blocked,working,review`): unable to rearrange items within
the Review column, and unable to drop items into it at all. Two separate
bugs, found one after fixing the other.

## Bug 1: `legality()` only recognized the four version-1 stage names

`internal/web/static/mm.js`'s client-side transition table (§7.2's replica,
kept only for instant hover feedback — the server stays authoritative)
special-cased `ready`/`blocked`/`someday`/`working`/`done` and refused
**everything else by default**, including any custom stage a v2 board
declares. `startV2`/`pauseV2` (`mm/board_ops.go`) place no restriction on
the other side of a start/pause; the refusal was purely a client artifact
of a table that never learned about custom stages.

Generalized: `to === 'working'`/`from === 'working'` now trigger
start/pause regardless of the other stage (matching the library's own lack
of restriction); `block`/`unblock` stay gated on the literal `blocked` name
(the dialog that prompts for a reason is hardcoded to it — see the
follow-up below); everything else — any stage-to-stage pair not otherwise
named — now defaults to a plain `move` instead of `Conflict`, since the
server is the real authority and a plain `move` is legal to or from any
declared stage (spec-tools.md §5.1.7).

**Known remaining gap, not fixed here**: dragging into a needs_reason stage
*other than* the literal `blocked` still refuses server-side ("needs a
reason") with no dialog to collect one, because `dialog-block`
(`internal/web/templates/partials/dialogs.html`) is hardcoded to that one
stage rather than parameterized by destination. Not reachable on the
reported board (its only needs_reason stage is `blocked`), so left as a
follow-up rather than generalizing the dialog itself in this pass.

## Bug 2: fixing bug 1 exposed a second, pre-existing one

With `legality()` fixed, dragging into or within Review still failed —
every request came back `400 "review" is not a section`. `commitMove()`
sends both `section` and `stage` on a move/pause (a T-0243 fix, so the
server can read whichever field its version needs) — but `section` isn't a
free-form slug like `stage` is: `internal/web/item.go`'s "move"/"pause"
cases call `mm.ParseSection`, which only recognizes `ready`/`blocked`/
`someday`, and refuse immediately on anything else — before the `stage`
field is ever read. "review" was never a reachable destination in
`commitMove()` before T-0243 either; sending both fields unconditionally
had simply never been exercised against a custom stage until `legality()`
stopped blocking the drag client-side.

Fixed by hoisting the `backlog()` name-check `legality()` already had into
shared module scope and using it to decide whether `section` is included
at all: `values.stage = to` always; `values.section = to` only when `to`
is one of the three names `mm.ParseSection` actually recognizes. A custom
stage now sends `stage` alone, which is exactly what version 2 needs and
what version 1 would simply have nothing to do with anyway.

## Tests

`internal/web/jstest/mm.test.js`: three new cases against a `REVIEW_HTML`
fixture — a drop from elsewhere lands in review with `stage` set and no
`section` field at all, reordering within review is legal, and start/pause
work between a custom stage and working. `mm.js`'s line-count architecture
guard (`internal/web/dragdrop_test.go`) raised 960→990 with the usual
per-change justification. `internal/web/dragdrop_test.go` also gained
`TestMoveToACustomStageWithNoSection`, a real end-to-end HTTP round trip
against `clean-v2-full`'s own declared "review" stage, proving the server
side independently of the client-side JS suite.

Verified live end to end against a copy of the actual reported shape
(clean-v2-full, which already declares `review`): dispatched real
`DragEvent`s in a running browser tab against the fixed build - reordering
two items within Review, and dragging a Ready item into Review - both
landed correctly in `board.md`.

`go build`, `go vet`, `gofmt -l`, and the full `go test ./...` (mm,
internal/cli, internal/web including the jstest node suite) are all
green.

## Notes

Generalized mm.js's drag legality table past the four v1 stage names, then fixed a second bug that fix exposed (section sent unconditionally, rejected by ParseSection for any custom stage). Verified live with real DragEvents against a copy of the reported board shape. See details/T-0248.md.
