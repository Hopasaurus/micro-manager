# T-0250 — Fix drop position lost + pre-populate reason in the block dialog

Reported live: dropping a task into Blocked at the bottom or middle of the
list moved it to the top once the reason was entered. Also requested:
pre-populate the reason input with the item's existing reason, if it has
one, when the dialog opens.

## Root cause of the position bug

Dropping into Blocked opens `dialog-block` (spec-gui.md §7.2 — blocking
must prompt for a reason). The drop's own index was computed correctly by
`hoverTarget` during the drag, but `commitMove()`'s dialog-opening branch
only ever passed `?item=<id>` to the dialog fetch — the position was
discarded the moment the dialog opened, and the dialog's own `<form>`
carried nothing to recover it. Once submitted, whichever endpoint handled
it fell back to its own default position:

- A **working** item's drag posted to `/pause` (T-0245's fix), whose
  library call (`pauseV2`) defaults an unpositioned pause to **the top**
  — matching "seemed to go to the top" exactly.
- A **non-working** item's drag posted to `/block` (`Store.Move`), whose
  default with no selector is **append at the end**.

Two different silent defaults, same root cause: nothing ever threaded the
drop position through the dialog round trip.

## Fix

Rather than adding position support to two separate paths, unified
`dialog-block` to always post to `/block` (`internal/web/item.go`'s
`Store.Move`-based handler), for a working item too — `moveV2` places no
restriction on the item's current stage, so there was never a real reason
to keep a separate `/pause` path for this dialog specifically (only
historical: `legality()` used to compute a `pause` op for any drag out of
working, and the dialog inherited that op name). This also drops the
dialog template's `{{if $working}}...{{end}}` branch entirely — `/block`
already hardcodes `section`/`stage` server-side, so no hidden input needs
to carry them, simplifying the template alongside the actual fix.

- `mm.js`'s `commitMove()` now appends `&position=<1-based index>` to the
  dialog fetch when opening `dialog-block` specifically (`finish` has no
  equivalent — the done column has no position to preserve).
- `dialogs.go` reads that query param and passes it (plus the item's
  current `Reason`) into the dialog's view data.
- `dialogs.html`'s `dialog-block` form carries a hidden `position` input
  when one was supplied, and the reason `<input>`'s `value` is now the
  item's existing reason (empty for a fresh item — the second half of
  this task, and a natural fit once the dialog was already being
  rewritten).
- `item.go`'s `/block` handler reads the `position` field onto
  `MoveRequest.Position`, which `resolveIndexV2` already knows how to
  honour precisely (absent still defaults to append, exactly right for
  the item-menu's own "Block" button, which has no drop to preserve).

## Tests

`internal/web/dragdrop_test.go`: `TestWorkingToBlockedPromptsAndPauses`
renamed to `TestWorkingToBlockedPromptsAndBlocks` and updated for the
unified `/block` endpoint; new `TestBlockHonoursTheDropPosition` (a
three-item Blocked column, dropping at position 1 lands above both
existing occupants) and `TestBlockDialogPrefillsAnExistingReason` (an
already-blocked item's dialog carries its reason; a fresh item's is
empty). `internal/web/jstest/mm.test.js` gained "dragging into blocked
prompts the block dialog with the drop position", asserting the exact
fetch URL carries `&position=N`.

Verified live end to end: dropped a working item into the middle of a
three-item Blocked column in a running browser (real `DragEvent`s),
confirmed the dialog fetch carried `position=2`, submitted a reason, and
the item landed exactly between the two existing occupants in `board.md`
— not at the top or the bottom. Separately confirmed the dialog opens
pre-filled with an already-blocked item's existing reason, and empty for
a reason-less one.

`go build`, `go vet`, `gofmt -l`, and the full `go test ./...` (mm,
internal/cli, internal/web including the jstest node suite) are all
green.
