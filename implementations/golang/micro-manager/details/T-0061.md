# T-0061 — Render the check view and the status bar violation count

## As built

`internal/web/check.go`, `templates/check.html`. The status bar half already
existed — §5.2 requires `status-check` on *every* route, so it shipped with the
app shell in T-0055 — and this item is the view plus the proof that the two
agree.

**One call, three consumers.** The view runs `Store.Validate` and nothing else:
the same call the CLI's `--check` makes, and the same one every mutation runs
before it commits. The view, the command line and the tool's own pre-commit
guard therefore cannot disagree about what is wrong with a directory. A test
compares the view's findings against the library's directly.

**Violations are results, not errors.** A directory with violations answers
200 with the findings listed (`spec-tools.md` §5.1.12). A non-200 would mean the
directory could not be read at all — and refusing to show a broken directory
removes the tool exactly when it is needed.

**`data-invariant` carries the I1–I10 identifier**, which is what lets a suite
assert *which* rule broke. Message text is deliberately free to vary between
implementations; the identifier is not, so it is the thing to match on.

**`check-run` swaps the section, not the page.** Re-running exists precisely to
pick up a change made outside the UI — by the CLI, or by an editor — and a test
writes an orphan detail file behind the service's back and asserts the re-run
sees it.
