# T-0161 — Morph the board-targeting mutation swaps again (T-0138 reversal)

[[T-0148]] (spike, 2026-08-04) found that the /new and /item "still flicker"
report is the whole-board outerHTML rebuild on every panel save. T-0138 made
every board-targeting mutation swap outerHTML for exactly one reason — a morph
swap aimed at the board from elsewhere re-registered the board's `every 30s`
poll and leaked a second chain per mutation. T-0139 removed every `every`
clause from the templates (the backstop is now a JS interval in mm.js, not an
htmx poll; grep: no `every Ns` trigger remains in templates/ or static/).

The leak mechanism is gone, so the outerHTML swaps are now pure cost: a full
teardown-and-rebuild of every column and card (the research report's flicker
source 2; 31,825 bytes in the clean-full fixture alone) on the very page whose
main interaction is the panel save. This is the /new and /item flicker — and
the /board dialogs flicker the same way.

Verified in headless Chromium (playwright-core, chromium-1234) against the
running service, with the item edit form flipped to `hx-swap="morph"` +
`hx-ext="morph"`:

- the save lands, the panel dismisses, and the board element is PRESERVED
  (morph) — no teardown;
- zero board/status fetches in the 12 s after the morph save with the SSE
  stream up — no poll chain returns. (T-0138's post-mutation expectation was
  TWO 30 s chains.)

## The eight swap sites to flip outerHTML → morph

- `templates/partials/item-panel.html` — :34 (the item edit/new form), :109
  (the action buttons), :122 (the note form); all already carry
  `hx-target="[data-testid='board']"`;
- `templates/partials/dialogs.html` — :38 (block), :64 (finish), :83
  (confirm-remove);
- `static/mm.js` — :297 (card-menu start/pause/finish/…), :547 (drag commit).

The mm.js `htmx.ajax` calls pass an explicit source, which T-0129 verified
resolves "morph" from the app root's hx-ext. The native form submits need
`hx-ext="morph"` declared on the form element itself — that is the pairing
`TestMorphSwapsDeclareOwnExtension` enforces, and the one combination proven
reliable in the vendored htmx (sse_test.go).

## Tests to update

- `TestMorphOnlyOnSelfRefreshingRegions` (sse_test.go) pins "no
  `hx-swap=\"morph\"` may carry an `hx-target`" — the pin's purpose (the
  T-0138 leak) is gone. Re-scope it to whatever the reversal leaves true; the
  point of the test is to fail loudly if a swap that causes the old leak
  comes back, and the old leak is impossible while no `every` clause exists.
- `TestBoardMutationsSwapOuterHTML` pins the board-targeting swaps exist and
  are outerHTML; it must now pin them as morph while keeping the "must exist"
  half, so the swaps cannot silently disappear.
- The mm.js line-ceiling guard (780): the two `swap: 'outerHTML'` → `'morph'`
  edits do not change the line count; verify the guard still passes and run
  the jsdom suite (T-0111) — card-menu and drag tests must stay green.

## Browser verification (repeat the T-0138 methodology)

The leak was only observable in a browser; the reversal must be verified the
same way: load a board, run four real mutations through the card menu and the
panel, and confirm with the SSE stream up that board/status fetch ZERO times
over ~8 minutes (T-0139's idle budget — no `every` chains to leak). With the
stream down, the mm.js interval polls 3 regions × 12/min; a mutation must not
add a second interval per region — the fetch cadence stays exactly 5 s.

## In scope, small

- The app-status OOB swap on every mutation (board.html:39) is outerHTML. No
  chain (event trigger only), but for consistency it can morph too via
  `hx-swap-oob="morph:[data-testid='app-status']"` with the footer's own
  hx-ext. Optional: it is a one-line footer, so the visual win is negligible.
- `check.html:23` (the Run button) re-runs the check region outerHTML on an
  explicit user action — leave it.
