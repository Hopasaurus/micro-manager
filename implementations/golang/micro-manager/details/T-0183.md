# T-0183 — Context injection and configuration

From [[project/spec-pi-mm-plugin.md]]. Spec §6 + §9: before_agent_start appends a <=8-line board block (data only: wip, per-section counts, in-work, top of Ready), refreshes after any plugin mutation, injects nothing when no board or untrusted. Config files ~/.pi/agent/mm-plugin.json (global) and .pi/mm-plugin.json (only when ctx.isProjectTrusted()) with keys board, context, contextLines, timeoutMs, confirmRemove. Context MAY include the one-line board description after the path (spec §3.4).

## As built

`src/context.ts` (the block, its cache) and `src/config.ts` (§9's two files),
wired into `before_agent_start` and `session_start`.

**"Refresh after any plugin mutation" is implemented from `mm`'s own change
set.** Nothing in the plugin has to know which operations mutate: `operate()`
calls `markBoardChanged(envelope)` after every run, and the cache is
invalidated when `changes` is non-empty. That is the one source that cannot be
wrong about it — and it covers the awkward case too, a mutation that failed
*after* writing something, because the failure envelope reports what it touched
as well.

**Injection refuses in five ways, and each returns nothing rather than a
guess**: injection switched off (config or `/mm context off`), no `mm`, no
pinned board, an untrusted project, or a `--status` read that failed. §6 is
explicit that an empty injection beats a false one, and a stale block is a
false one.

**It does not resolve a board.** §6 says inject nothing when no board is
resolved — not "go and find one". Resolution changes which board the session
operates on, and a turn boundary must not make that decision on the user's
behalf.

**Truncation is explicit.** A board that overflows the line budget ends with a
bare `…`, so the agent can tell a short board from a clipped one; otherwise it
would reason about work it cannot see. `contextLines` can lower the budget but
never raise it past §6's eight.

**No commentary, and a test that says so.** Behaviour guidance lives in the
tools' `promptGuidelines`, attached to the tool it is about. Prose in this block
would be re-read every single turn.

## Configuration, and the one filesystem exemption

§9's project file is read **only** when `ctx.isProjectTrusted()` — an untrusted
project pointing the plugin at a board is what pi's trust model exists to stop.
Everything is best-effort: a wrong-typed key is named and dropped rather than
coerced (`timeoutMs: "30s"` is a mistake worth hearing about), an unknown key is
reported because it is usually a typo for a real one, and unreadable JSON leaves
the defaults standing with a warning. A config that appears to work and does
nothing is the worst outcome.

This is also the first module that must touch the filesystem, which the §8.1
conformance test had banned outright. The ban is now an **exemption with a
receipt**: `config.ts` may import `node:fs`, and the test additionally asserts
that every path it BUILDS ends in `CONFIG_FILENAME`. An exemption nobody checks
is just a hole. (The check is line-wise rather than paren-matched — a nested
`homedir()` ends a naive match early, and that bug cost one iteration.)

`config.board` is applied after the branch pin is reconstructed, per §7: the
file is the standing instruction, the branch is where this session had got to.

## Verification

`src/context.test.ts` asserts mostly what the block must NOT contain and when
it must NOT appear — a rule broken here is broken thousands of times over. It
pins the exact §6 layout, the absence of done items and prose, explicit
truncation, the 8-line ceiling, all five refusals, and the cache being
invalidated by a change set but not by a read.

`src/config.test.ts` builds real files in a temp home and project: the trust
gate both ways, key-by-key override, wrong types named and dropped,
`contextLines` clamped, unknown keys reported, and broken JSON surviving as
defaults.

139 tests: all pass with `mm` on PATH, 133 pass and 6 skip without.
`tsc --noEmit` clean, and `pi --list-models -e ./src/index.ts` still loads the
extension.

## §10 conformance

With this, the plugin meets §10's **minimally conforming** list: §2.1, §3.2,
§3.3, §4.1–§4.3, the required tool set, §6, §8.1, §8.3, and §9's global config.
It also has §4.2's full required set, §8.2's guarded `mm_remove`, §5's command
surface and §7's branching state — the **fully conforming** list — with only the
recommended tools of **T-0184** outstanding.
