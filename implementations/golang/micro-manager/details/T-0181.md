# T-0181 — mm_remove with the double guard

From [[project/spec-pi-mm-plugin.md]]. Spec §8.2: requires confirmed:true in the schema (default false), prompts with ctx.ui.confirm naming item and home when ctx.hasUI, and only then passes --force — the CLI's own guard is the third line. Headless modes skip the prompt; explicit confirmation is the whole guard. confirmRemove config switch.

## As built

`plugins/pi-mm/src/tools-remove.ts`. Three locks, in order, each a different
party asserting the same thing:

1. **`confirmed: true`, defaulting to false** — the MODEL asserting it has the
   user's go-ahead. An unconfirmed call is refused before anything is spawned,
   not even the read.
2. **`ctx.ui.confirm` when there is a UI** — the USER, answering for
   themselves, with the item and its home named.
3. **`--force`** — the CLI's own guard, reached only on the far side of both.

Headless skips step 2 and the explicit `confirmed` is the whole guard: there is
nobody to ask, and inventing an answer would be worse than either refusing
everything or trusting a flag the model set deliberately.

**Every refusal names `mm_finish --outcome cancelled`.** A refusal that does not
name the alternative just gets retried with the flag flipped, which is the
failure mode the guard exists to prevent. Removal is for a typo, a duplicate, an
item added to the wrong board; abandoning work keeps the record.

**Declining is not an error.** The user answered the question they were asked
and the answer was no, so the result is an ordinary one carrying
`declined: true` — an `isError` would read as "something went wrong" and invite
a retry.

## The one place this bends §4.1

The prompt must name "the item and its home" (§8.2 step 2), which means reading
the item before asking about it — a second subprocess in a tool that §4.1 says
is one operation.

That rule is about chaining MUTATIONS: "start and finish is two tool calls",
because a chain hides which step failed. A pre-flight read hides nothing — if
it fails, nothing was removed and the error is the read's — and a confirmation
prompt that could not say what it was about would be a worse guard than none.
The plugin already makes a second call for board resolution (§3.2 requires it),
so "one subprocess" was never literally the rule; "one mutation" is.

## `confirmRemove`

§9's switch is wired as `ToolDeps.confirmRemove`, defaulting to on. It governs
the DIALOG only: with the prompt off, an unconfirmed call is still refused. The
config reader that supplies the value is **T-0183**.

## Verification

`src/tools-remove.test.ts` has a test per way of getting past a lock you should
not, and each asserts that **nothing ran** — a guard that lets the subprocess
through and regrets it afterwards is not a guard. It also pins the schema
default, the exact argv (`--remove ID --force`, and no `--with-detail`, a switch
§4.2 does not give this tool), and that the orphaned-detail warning `mm` emits
is carried rather than swallowed.

`src/mm-contract.test.ts` then runs all three states against a **real board**:
unconfirmed refusal → the item is still listed; declined prompt → still listed;
both guards satisfied → really gone, and `mm_check` still clean, because
`--force` is a guard rather than a bypass of the transaction envelope.

99 tests: all pass with `mm` on PATH, 94 pass and 5 skip without. `tsc --noEmit`
clean.

## The required surface is complete

§4.2's required set is now all present: `mm_init`, `mm_find`, `mm_status`,
`mm_next`, `mm_list`, `mm_show`, `mm_board`, `mm_describe`, `mm_add`,
`mm_edit`, `mm_move`, `mm_note`, `mm_start`, `mm_pause`, `mm_finish`,
`mm_remove`, `mm_check`. What remains for §10's "fully conforming" is the `/mm`
command surface (**T-0182**) and §7's branching state, which T-0177 built —
plus context injection (**T-0183**) for the minimal conformance §10 also names.
