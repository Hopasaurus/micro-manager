# T-0238 — Columns: settings page + report page generalized to version 2

Split out from T-0230 (Columns M4) once M4's own plan checklist
(notes/add-columns-plan.md#m4) was fully satisfied — CLI, the board view,
the item panel, TUI (no-op, unimplemented), and the cross-directory
decisions are all done, and VersionMismatch enforcement is its own tracked
task (T-0236). This is TestAuditTestids' remaining failure, for two GUI
surfaces the plan checklist never actually named: the settings page and the
report page. Both are still entirely version-1-shaped.

## The gap

**Settings page** (spec-gui.md §5.9, `internal/web/templates/settings.html`):
the WIP section is a single fixed `settings-wip-limit` input (one
directory-wide number), not the per-stage `settings-wip-row-<slug>` /
`settings-wip-limit-<slug>` pairs spec-gui.md now requires — "one row per
declared stage; a stage with no wip.<slug> key renders its input empty,
meaning uncapped". There is also no `settings-migrate` section at all: per
spec, it renders (with `hidden` removed) only when the open board is a
version-1 directory, and its `settings-migrate-run` button calls the
migrate action (spec-tools.md §5.3.4), re-fetching and re-rendering the
whole view afterward since every testid and config key changes shape the
moment migration lands. Note this visibility check is just `dir.Version < 2`
— a plain field read, NOT gated on T-0236's VersionMismatch enforcement
actually existing; the two are unrelated despite the shared vocabulary.

**Report page** (spec-gui.md §5.7, `internal/web/templates/report.html`):
`report-include-wip` (a checkbox) exists; `report-include-stage` (a
`multiple` select of the directory's declared stages) does not. The library
side of this already shipped this session (mm/report.go's
`ReportOptions.IncludeStages` / `Report.StageIncluded`, wired through the
CLI's own `--include-stage`) — this task is purely the GUI form control and
wiring it into the request the report handler already builds.

## Shape of the work

Both pieces follow the same pattern already used for the board and item
panel: a Go-side view-model field computed from `dir.Version`/`StageCfg`
(mirroring `stageOptionsFor` in `internal/web/board.go`), a template branch
or generalized loop, and a v1/v2 pair of tests. Neither should need library
changes beyond what --include-stage already added — SetStageWipLimit
(op_wip.go) and Store.Migrate already exist and are exercised by the CLI's
own tests.

## Notes

**2026-08-21** — Shipped both pieces; `TestAuditTestids` (and the full
suite) is green.

**Report page** (`internal/web/report.go`, `templates/report.html`):
`reportControls` gained `IncludeStages []string` (the `<select multiple
name="include-stage">`'s selected values, read straight off
`url.Values["include-stage"]` — a multi-select submits one value per
selection under the same name, no extra parsing needed) and `StageOptions
[]stageOption` (populated only for `dir.Version == 2`, so the control is
omitted entirely on a version-1 project rather than rendered with nothing
to choose from — same pattern the item panel's `tickler-dest` already
established). `reportData` gained `StageIncluded []reportStageGroupData`,
populated from `mm.Report.StageIncluded` the same way `Wip` already is
(`itemView`-wrapped); the template renders one `report-group-stage-<slug>`
section per non-empty group, dropping empty ones — the same "empty groups
train the reader to skip it" rule the CLI's own Markdown rendering already
follows. Added a template helper, `includes`, since Go's `html/template`
has no built-in slice-membership test for marking the selected `<option>`s
on reload.

**Settings page** (`internal/web/settings.go`, `templates/settings.html`):
`wipSettingsData` gained `Version2 bool` and `Rows []wipStageRow` (one
`settings-wip-row-<slug>`/`settings-wip-limit-<slug>` pair per declared
stage, in `stages:` order); an uncapped stage's `Limit` is the empty
string, not `"0"`, so its input renders empty per spec ("absent means
unlimited"). `saveSettingsProject`'s single if/else became a
`switch` on the `action` field: `clear_theme` (existing),
`migrate` (new — calls `Store.MigrateVersion`, NOT `op_migrate.go`'s older
unversioned repair, despite the similar name; the two are unrelated
mechanisms that happen to share a spec section number's neighborhood), and
the default save path, which now loops every declared stage's own
`wip-<slug>` field on a v2 project instead of reading the single `wipLimit`
field. `settingsData` gained `NeedsMigration bool` (`dir.Version < 2`) which
gates `settings-migrate`'s `hidden` attribute — a plain field read, **not**
gated on T-0236's VersionMismatch enforcement despite the shared
vocabulary; `MigrateVersion` and `SetStageWipLimit` both already existed
and needed no library changes.

Verified live in a browser (isolated config-home) end to end, not just via

(the report page, the settings page) and instance-table entries for
