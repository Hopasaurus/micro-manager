# T-0059 — Implement drag and drop and the keyboard move mode

## Context

`spec-gui.md` §7 is the one part of the GUI that server rendering cannot supply.
It requires accurate DOM attributes **on every pointer move**, not only on drop,
and a keyboard move mode that maintains the same attributes so one set of test
assertions covers both input paths.

`static/mm.js` is the only hand-written JavaScript in the project
(`project/architecture.md` §4.6). Keep it small and dependency-free; if it grows
past a few hundred lines, something belongs on the server that has drifted onto
the client.

## Requirements

1. Mid-gesture attributes, per §7.3: `data-dragging` on the card,
   `data-drag-source` on the app root, and on the hovered column
   `data-drop-target`, `data-drop-allowed`, `data-drop-index`, `data-drop-reason`.
   At most one column carries `data-drop-target="true"` at a time. A
   `drop-placeholder` element sits in the hovered column at the insertion point.
2. Keyboard move mode, §7.4: `Space`/`Enter` enters it and sets
   `data-move-mode="true"`; arrows change index and column; `Enter` commits;
   `Escape` cancels and restores focus and position. **One code path** with the
   pointer drag, so the attributes cannot drift apart.
3. The transition table of §7.2 is replicated client-side for instant hover
   feedback — the one deliberate duplication of a domain rule, permitted by
   §2.1 because the server's answer stays authoritative. Slot-to-slot and
   anything out of done are illegal: `data-drop-allowed="false"`, and the drop
   issues **no request**.
4. Drop maps to an operation: same column → `--move --position`; backlog → slot
   → `--start --slot`; slot → backlog → `--pause`; anything → done → `--finish`
   (prompt for outcome); to/from blocked → `--block`/`--unblock` (prompt for a
   reason; cancelling aborts).
5. The request goes through `htmx.ajax()` so the response flows through the same
   swap and out-of-band machinery as every other mutation. No parallel update
   path.
6. Rejection restores the pre-drag DOM **including `data-position` on every
   affected card**, keeps focus on the item, raises a `danger` toast carrying the
   error code, and for `WipLimitReached` opens `dialog-wip-limit` (§7.1, §7.5).
7. `data-busy` tracking lives here too, wired to `htmx:beforeRequest`,
   `htmx:afterSettle` and `htmx:responseError`. It is the quiescence signal the
   external suite waits on, so `false` must mean the view fully reflects server
   state (§5.1).
8. Announce drag start, target change and result through the board's
   `aria-live="polite"` region (§11 rule 4).
9. Favorites reordering on Home uses this same mechanism and the same attributes
   (§10 rule 3) — write it as a generic list-reorder, not a board special case.

## Open questions

- HTML5 drag-and-drop events versus pointer events. HTML5 DnD is what the spec's
  wording implies (`draggable="true"` in the §5.5 markup) but its synthetic
  events are notoriously awkward to drive from an automation harness. Pointer
  events are easier to test and would still satisfy every documented attribute.
  Check what the external suite can synthesize before committing.
