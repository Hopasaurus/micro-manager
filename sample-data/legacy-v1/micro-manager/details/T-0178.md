# T-0178 — Read tools: mm_status, mm_next, mm_list, mm_show, mm_board, mm_check, mm_find

From [[project/spec-pi-mm-plugin.md]]. The required read set of spec §4.2/Appendix A: one tool per op, formatted content for the model + parsed envelope in details. Includes mm_find (mm --find): every located board with path/project, the in-use board marked; an empty list is a valid result, never an error. mm_status and mm_board also surface the board description from the --status envelope (spec §3.4; the CLI side is T-0187). mm_list keeps on-disk order (never re-sort Ready), limit default 50 cap 200. mm_next empty is "nothing ready", not an error. mm_check surfaces violations path:line.

## As built

`plugins/pi-mm/src/tools-read.ts` (the seven tools) and `src/format.ts` (what a
result says). Every tool is one `operate()` call plus a formatter — the gates,
the `--dir`, the error mapping and the `details` shape are decided once.

**Two gates, in order, before any operation runs**: `mm` on PATH (§2.1), then a
resolved board (§3.2). A tool with neither returns an error naming the cause and
the remedy — never a fake empty board (§4.1). `mm_find` skips the second gate on
purpose: listing boards is exactly what you do when you have none.

**`details` carries the parsed envelope and the pin** on every result, which is
what makes §7's branch reconstruction work and what a `/mm` renderer will read.

The four places a plausible implementation goes wrong, each asserted directly:

- **`mm_next` on an empty Ready is a RESULT.** The CLI exits 3 so a script can
  stop; the tool turns that one case into "nothing ready." and leaves every
  other exit an error. A test pins both halves, including that exit 6 stays a
  failure.
- **`mm_list` never re-sorts.** On-disk order is the user's prioritisation, so
  the tool prints what it was handed. The limit defaults to 50 and is **clamped
  to 200 here** rather than trusted from the model: an unbounded list is a
  context bill the user pays.
- **`mm_find` with no boards is a result**, "no boards located. mm_init creates
  one." — never an error.
- **`mm_check` reports violations as a result too** (`spec-tools.md` §5.1.12:
  violations are results, the exit code is what a script gates on). Reporting
  them IS the tool's job, so an exit 1 carrying findings is rendered as
  `path:line: I1 message`, not as a failure the agent has to interpret.

**The board description** rides through `directory.description` when the
installed `mm` reports one and is simply absent otherwise — no CLI change
needed here, and an absent description is a valid state (§3.4).

## Verification

`src/tools-read.test.ts` drives a fake runner and asserts the **argv** each tool
builds, whether the result is an error, and what `details` carries — the
contract rather than the wording. `src/mm-contract.test.ts` then drives the same
tools against a **real board and a real `mm`**, which is what proves the two
halves fit: the argv they build is argv `mm` accepts, and the envelopes they
read are envelopes `mm` writes. It skips with a reason when `mm` is absent.

60 tests: all pass with `mm` on PATH, 58 pass and 2 skip without. `tsc --noEmit`
clean.
