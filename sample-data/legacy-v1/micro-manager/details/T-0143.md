# T-0143 — Name the compiled-in library themes in spec-gui.md §8.7

## Context

The Go implementation ships two themes compiled into `mm` (`BuiltinThemes()` in
`mm/theme.go`): the default, id `micro-manager`, and the light companion
`micro-manager-lite`. The spec's §8.7 resolution order named neither: step 5
said only "Built-in default", and §8.2's theme-library table listed only files.
The implementation comments recorded the two failure modes this left open:

- the default's id was once `mm-default`, "which nothing anywhere resolved by,
  so an exported builtin carried an id no listing offered and no import could
  match";
- `sample-one-dark` — an ILLUSTRATION id from §8.6/§8.2 of the spec — used to
  sit in the library listing, and selecting it "silently served the built-in".

## What the spec now says

A "Built-in themes" block in §8.7 (with one-line follow-throughs in §3.3, §8.2
and §8.8):

- **`micro-manager` is MUST** — the built-in default of step 5, defining every
  token in §8.3, which is what makes per-token fallback total. **The id is
  normative; the palette is not.** A theme is chosen by id in `config.json`,
  exported under its id, and listed by id — those are the cross-implementation
  contracts, and renaming the default would break all three.
- **`micro-manager-lite` is SHOULD**, not MUST: `appearance: light`, one
  palette, no `gui` group (typography, spacing, radii fall through to the
  default, exactly as `BuiltinLiteTheme` does). It is recommended so a config
  that names it means the same thing in every UI — but the palettes are
  presentation and a conforming TUI-only implementation ships no GUI at all.
- **A built-in resolves at the precedence position its id was named at**, not at
  step 5: a project naming `micro-manager-lite` still outranks a system
  `theme.json`. This is what `ResolveTheme`'s `builtinID` fallback already does,
  and what the code comment calls the reason "a project that names
  micro-manager-lite would not silently lose to a system theme.json it
  outranks".
- **A library file whose id matches a built-in shadows it**: the file is read,
  the built-in ignored, the id listed once. The supported way to patch a shipped
  theme; matches `buildThemeLibrary`'s skip and `ResolveTheme` reading the file
  first.
- Built-ins appear in the theme library listing and are exportable — exporting
  one is how a user forks it.
- The document's illustration ids (`sample-one-dark`, `nord-dark`) are called
  out as not shipped; offering one in a picker is the "serves the default with
  no indication" failure mode.

## Decisions made here

- **SHOULD, not MUST, for `micro-manager-lite`**, despite it shipping in mm.
  §8.7's rules for a built-in apply to every compiled-in theme; a
  MAY-compile-more rule covers the general case. Requiring the palette would
  force every implementation to duplicate a specific colour list the spec has
  never fixed.
- **Silent continuation is specified, not a warning.** A named id with no file
  and no built-in resolves to the next candidate (rule 4), and the code does
  exactly that. The spec calls out the picker as the place the mistake is made —
  a picker MUST only offer ids that resolve — rather than inventing a new
  warning channel the implementation would then have to build.
- **spec-tui.md:458 fixed too**: `:theme sample-one-dark` → `:theme
  micro-manager-lite`. The TUI's own example must not commit the failure mode
  §8.7 now describes.
- **§8.8 import collision**: a built-in id collides like any other; overwriting
  writes a shadowing library file, not a replacement — the built-in is still
  there when the file is removed.

## Not done

No code change was needed: `mm/theme.go`, `internal/web/theme.go` and their
tests already behave as the new text prescribes, and the existing web tests
already assert the built-in listing and export that §8.7 rule 1 requires.
