# T-0166 — Spec: say what coverage archiving costs — a stranded detail file breaks I9, and §10.5 names only I1/I2

stranded details should be moved into a directory: "details-YYYY/" and loading an item from the archive should be able to find the detail.   The ID pool then needs to be unique within the year plus the time that items from a previous year are not yet archived (and ideally just plain unique all together)

The time when an archive is run should be able to be specified for a number of days after the end of a month or be manual.  Examples: "Archive a month 15 days after it ends" or 30 or 60 days or even 0.

## Decided (2026-08-04)

Option 2 of the four `T-0043.md` weighed — the detail file travels with its
item — which is what the requirement above asks for. T-0043 shipped option 1
(strand and report) explicitly deferring the choice here; making the library
follow the spec is **T-0168**.

### spec-file-format.md

New **§5.6 Archives: `done-YYYY.md` and `details-YYYY/`**, six rules: an archive
file has `done.md`'s schema; archives are not validated; a detail file travels
with its item and the archived `detail:` field is rewritten to
`details-YYYY/<ID>.md`; restoring is the same move backwards; archiving never
recycles an ID; when to archive is a tool's policy, not the format's.

The layout needs **no validator change at all**, which is the argument that
settled it: I8 and I9 name `details/` exactly, so `details-2025/` is already
invisible to `check.sh` and to the Go checker. Verified by reading both — the
reference validator globs `"$dir"/details/*.md` and `mm/store.go` reads
`filepath.Join(dir, "details")`.

T-0043's objection to option 2 was that a hand-restore then silently breaks I8.
It is not silent: the restored line IS validated, so I8 reports either a
`detail` that is not `details/<ID>.md` or one that is and names a file that is
not there. Half a restore is caught, which is strictly better than option 1,
where a whole archive silently strands files (51 of them on this board).

Also: §1's file table gains the two archive rows (otherwise "any other file is
outside this specification" contradicts §5.6), §5.3 and §5.4 point at it, the
`detail` row of §6 notes the archived form, a line under I9 scopes I8/I9 to the
live files, and **§10.5 is rewritten** — it now says the detail files do not
become orphans *because* they moved out of reach, which is the same
invisibility rather than an exemption from it. Appendix A gains two informative
patterns, marked as never validated.

### spec-tools.md

New **§5.3.1 `--archive` in detail**: `--before YYYY-MM` and `--age DAYS` as
mutually exclusive spellings of one month-granular cutoff (`--age` is the
requirement above — "archive a month 15 days after it ends", `--age 0` for
every complete month); detail files move and fields are rewritten, and doing one
without the other is non-conforming; `next_id` untouched; **nothing archives on
its own initiative** — a scheduled run needs configuration that names the
policy. Also the `--include-archives` note (follow the archived `detail` field,
do not assume `details/`) and the Appendix A row, which now names I9 as the
invariant a bad archive breaks.

### The ID question

Answered by I2 rather than by a new rule: `next_id` rises monotonically and an
archive MUST NOT change it, so IDs stay unique across the whole directory,
archived or not — "plain unique all together", not merely per year. The hazard
is only for a tool that *derives* `next_id` from what it can see; §5.6 rule 5
makes reading the archives its obligation, because no checker will catch the
collision it would otherwise create.

### Not done here

Front-end policy: no config key and no UI control for `--age`. The CLI has no
`--archive` switch at all (**T-0167**), so there is nothing yet for a schedule
to drive.

`structure.md` in every data directory carried a one-sentence version of the old
rule ("cut trailing months into `done-YYYY.md`"); all six copies now mention the
detail half, since a hand-editor following the old sentence would strand files.
