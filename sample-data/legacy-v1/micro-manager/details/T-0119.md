# T-0119 — Spike: digit widths supported without special libraries

What ID digit widths can an implementation honor using only the language's
native integer machinery — no third-party bignum library? The answer becomes
the shared cap the format's readers agree on.

## Why now

- T-0113 made `id_width` "one or more ASCII digits" (3–6 RECOMMENDED, warn
  outside) and generalised the counter-space cap to `10^W − 1` — with no upper
  bound on W. Every implementation must therefore refuse loudly (never
  silently misparse) a grammar it cannot honor.
- T-0116 found the edge while cross-checking the two validators: Go rejects a
  20-digit `id_width` (`strconv.Atoi` overflows int64 → a format violation)
  while mawk accepts it and then demands 20-digit IDs, so the validators
  diverge exactly where the declared width outruns the checker's native
  integer. The spike's answer becomes the shared rule that removes the
  divergence.

## What to explore, per language

For each of **golang, typescript, clojure, java, python**, record the native
range and how a width beyond it fails:

- **golang**: `int64` — `10^19 − 1`; `Atoi` on a longer width is an error, so
  a too-wide declaration already fails loudly.
- **typescript**: `number` is a float64, exact only to `2^53` (~9e15, so
  roughly 15–16 digits); `BigInt` is built in, no library — decide whether it
  counts as "native" for this spike.
- **clojure**: arbitrary-precision integers natively — any width, no library.
- **java**: `long` is `int64`; `java.math.BigInteger` ships in the JDK — decide
  whether the standard library counts as "special" or is fair game.
- **python**: arbitrary-precision ints natively — any width, no library.

Also decide where the counter arithmetic matters, not just parsing:
`next_id` increments and the I2 comparison (`Num(id) >= Num(next_id)`) must
stay exact at the supported widths.

## Decisions this task must make and write down

1. The largest `id_width` every checker must accept and compare exactly — pick
   a number every native implementation agrees on (the narrowest native range
   above, or a deliberate bound below it for headroom).
2. Whether widths beyond that cap are a format violation everywhere (Go's
   behavior today) — the rule that makes the validators agree.
3. Whether "without special libraries" means "no third-party dependency" (so
   JS `BigInt`, Python/Clojure native ints and `java.math.BigInteger` all
   count) — or something stricter.
4. What the spec change is: bound `id_width` in §3.3.2, or leave it open and
   state the shared cap as a reader rule.

## Deliverable

Save the findings and decision to `implementations/golang/project/plan-id-widths.md`,
then the spec change lands as its own task (like T-0113 did for T-0112).
