# T-0122 — Validators: reject git conflict-marker lines

Enforcement task following T-0121's spec rule: a line whose first non-blank
characters are `<<<<<<<`, `=======`, or `>>>>>>>` is invalid in every data
file. **Gated on T-0121** — the rule must exist in the spec before the
validators enforce it.

## Why

T-0101 probed both validators with a git conflict block inside `backlog.md`:
both silently absorbed the markers (spec §5.1 prose rule) and parsed the item
lines inside the block, surfacing only the incidental duplicate ID. With
different IDs on the two sides the markers pass with zero findings — a
half-resolved merge renders garbage and nothing notices. Closing that hole is
the whole point; T-0116's lockstep discipline applies here too (both
validators must agree, or the oracle test fails).

## What to do

- **check.sh**: in each data-file pass (backlog, working files, done), a line
  matching `^<<<<<<<`, `^=======`, or `^>>>>>>>` (after the usual trim) is a
  violation naming the file and line. This joins the format-level findings the
  checker already emits (like the grammar violations of T-0116), not an
  I1-I10 number.
- **Go validator** (`mm/`): the same rule at parse time — a marker line in any
  data file is a parse-level format violation, so an unmerged file cannot even
  load cleanly. Decide whether this surfaces in `Open`/`Validate` the way the
  grammar violations do, and keep the two packages' behavior identical.
- **Fixture corpus**: a `broken-marker` fixture (one marker block, IDs
  different on the two sides so the markers are the *only* finding) joins
  `testdata/`; register it in `brokenInvariants` as `"format"` so the oracle
  test runs it through both validators and asserts the finding sets match.
- The reading battery (byte-unchanged reads over the clean fixtures) must stay
  green — rejecting markers must not touch what valid files parse to.

## Verify

check.sh and the Go validator report the same (file, line) finding on the
marker fixture; the fixture corpus's clean directories still parse
byte-identically; `go test ./...` and `./check.sh --all` pass.

## Referenced by

T-0123 (`mm fix` refuses to run while markers remain — with this task, that is
just "the directory must be loadable", which the library already guarantees
for every mutation).

## Update (post-ship)

Enforced in both validators, with the fixture proving lockstep:

- **check.sh** — a rule right after `FNR == 1` in the main awk walk (covers
  `backlog.md`, `working.NN.md`, `done.md`, frontmatter and body): a line
  whose first non-blank characters are exactly `<<<<<<<`, `=======`, or
  `>>>>>>>` is a `git conflict-marker line` finding with the file and line.
- **Go** — `isConflictMarker` (in `itemline.go`, beside `looksLikeItemLine`)
  and `markerViolations`, called first in `parseBacklog`, `parseDoneG`, and
  `parseWorkingG`, so every data file's lines are walked exactly once and a
  half-merged file is refused loudly whatever else is in it. Markers surface
  as `format` violations, the same class as the grammar rejections.
- **Fixture `broken-marker`** — the T-0101 probe scenario: a conflict block
  in `Someday` whose two sides carry DIFFERENT IDs (X-002 / X-003, both below
  `next_id`), so the three marker lines are the directory's ONLY findings.
  Before this task it passed both validators with zero findings; now both
  report `backlog.md:21/23/25` and the oracle test asserts lockstep.
- **Tests** — `TestConflictMarkersAreRefused` (backlog body, done body,
  working body, working frontmatter — each yields exactly 3 `format`
  findings), `TestBrokenMarkerFixtureHasOnlyMarkerFindings`, and
  `TestConflictMarkersBlockMutations` (reads still work, but the transaction
  envelope refuses every mutation — the loadability guarantee T-0123 builds
  on).

Known limit, matching both validators' existing posture: `details/` bodies
are never walked (I8/I9 read only frontmatter), so a marker in a detail
body is outside what the validators can cheaply see — same class of limit as
the unvalidated `done-YYYY.md` archives. Detail *frontmatter* markers are
also silent in both, keeping the two validators identical by construction.
Empirically confirmed: markers in `done.md` and `working.NN.md` bodies are
caught by check.sh's one rule.
