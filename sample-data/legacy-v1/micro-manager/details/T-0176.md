# T-0176 — mm runner: subprocess with --json, --dir pin, timeout, exit-code mapping

From [[project/spec-pi-mm-plugin.md]]. The shared runner of spec §4.1 and Appendix C: one mm subprocess per tool, always --json, --dir once pinned, bounded timeout (default 30s, config timeoutMs), exit codes 0-6 mapped to typed tool errors with remedies surfaced (WIP slots on 4, re-read instruction on 5, "operation not in this mm build" on 2). Never retry a failed mutation automatically.

## As built

`plugins/pi-mm/src/runner.ts` — `run({ args, dir?, timeoutMs?, signal?, command? })`
returning a `RunOutcome` that is either the parsed envelope or a typed failure.
It never throws for anything `mm` does: every caller is a tool that has to
report rather than crash.

- **`buildArgs`** is exported and tested on its own, because the argv is a
  contract: §10 says the plugin MUST NOT run `mm` with a switch the spec does
  not name, and a test that reads the array is how that stays true. It appends
  `--json` always and `--dir` once a board is pinned, and it **throws** if a
  caller passes either itself — that is a plugin bug, not a user error, and two
  `--dir`s would mean two callers disagree about which board is being written.
- **Nine failure kinds**: the six exit codes, plus `spawn` (mm never started),
  `timeout` (never finished) and `envelope` (answered with something that is
  not §9.2's object). The last three are separate because their remedies are:
  install it, wait less, file a bug.
- **The CLI's own message always leads.** Where the spec asks for a sentence
  the CLI cannot know it appends one — exit 2 is the build's age rather than a
  plugin bug, exit 5 needs a re-read, exit 3 with `Ambiguous` needs a pin. Exit
  4 gets nothing added, because the CLI already names the remedy better than a
  copy of it would.
- **An unknown exit code maps to `io`, not to a new kind.** §4.3 says the
  plugin MUST NOT reinterpret the taxonomy; inventing a seventh code would be
  exactly that.
- **`AbortSignal`** kills the child, so a cancelled pi turn does not leave one
  running.
- **The environment passes through untouched**, `MM_DIR` included: it is step 2
  of §3.2's resolution order, and scrubbing it would quietly change which board
  a user's shell means.

## Verification

The unit tests drive shell shims rather than a mocked `spawn`, because the
interesting failures are the ones a mock cannot have — ENOENT, a non-zero exit,
a process that hangs. **The envelopes in them are real**, captured from the Go
`mm` while writing the runner, so the code agrees with the tool rather than
with a guess about it.

Two assertions worth naming:

- **One tool call is exactly one subprocess.** An absence of retry logic is
  invisible; a second spawn is not, so a counting shim is what makes §8.4's
  "never retry a failed mutation automatically" a checked property.
- **`src/mm-contract.test.ts` drives the real `mm`** — init, add, status, start,
  the WIP limit, an unknown id, an unknown switch — and skips with a reason when
  it is not on PATH, so the suite still runs on a machine that has never built
  the Go implementation. It logs what it covered, because a skip that looks like
  a pass is this repository's known failure mode.

32 tests: 31 pass and 1 skips without `mm`; all 32 with it. `tsc --noEmit`
clean.

## Found on the way

**`--init` reports the new board in `result`, not in `directory`.** Every other
operation carries the board's identity in the envelope's `directory` block, but
there is no directory to describe until `--init` has made one. `mm_init`
(T-0179) reads its path and project from `result`; the contract test pins it so
the surprise is discovered here rather than there.

## Not done

Board resolution and the pin (**T-0177**) — the runner takes `dir` as a
parameter and has no opinion about where it came from. Reading `timeoutMs` from
config is **T-0183**; until then the default is §9's 30s and callers may
override per call.
