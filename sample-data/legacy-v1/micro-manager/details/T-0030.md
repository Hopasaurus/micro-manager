# T-0030 — Build the CLI switch parser, one operation per invocation

## Context

`spec-tools.md` §3.2 requires the operation to be selected by a **switch**, not
a positional subcommand: `mm --add "…"`, never `mm add "…"`. Exactly one
operation switch per invocation; zero is a usage error, two or more is a usage
error naming both.

## Resolved: hand-rolled

`flag` cannot express the three things this specification is built on: repeated
accumulating switches, "exactly one of this set" across a namespace, and a
switch valid with or without a value. Every third-party parser that does handle
those is built around positional subcommands, which §3.2 explicitly rejects —
adopting one would mean fighting its model *and* taking a dependency. The
surface is flat by design, which is the case a hand-rolled parser handles well.
It came to roughly 300 lines with its own tests.

## The spec contradicts itself, and running it found out

`--wip` was listed **both** as an operation (§5.2, "set the WIP limit") **and**
as a modifier of `--init` (§5.1.1, "how many working files to create"). §3.2
says operation and modifier switches share one namespace precisely so that no
switch changes meaning depending on what preceded it — so a parser implementing
§3.2 literally reads `mm --init --project P --wip 2` as two operations and
refuses it. Which is exactly what happened on the first smoke test.

Resolved by renaming the `--init` modifier to `--slots`, and the spec was
updated in the same change with the reason recorded, per the rule in
`../../AGENTS.md`. The alternative — making `--wip` mean different things after
different operations — is the context-sensitivity §3.2 exists to prevent.

**Two more collisions of the same kind remain** in the spec, both in §5.2
operations that are not implemented yet:

- `--note ID TEXT` (operation) against `--finish --note TEXT` (modifier)
- `--detail ID` (operation) against `--add --detail` (modifier)

They must be resolved the same way when those operations are built. They are
noted in the spec at §5.1.1.

## Two more found by the tests

- **`--help` and `--version` are modifiers, not operations.** §3.4 lists them
  under "valid with every operation", and §3.4 also requires `--help` with an
  operation to print that operation's usage — impossible if `--help` is itself
  an operation, since two operations is an error. Modelling them as operations
  made `mm --help --start` a usage error.
- **`mm --add -- text`** took `--` as the title. An operation that consumes the
  next argument as its subject must never consume `--`, which ends switch
  parsing.
