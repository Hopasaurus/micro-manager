# T-0147 — Move to top / move to bottom in the card menu

Add "Move to top" and "Move to bottom" to the card context menu (and, because
the item panel shares the same action list, to the panel).

## Design

The library and the CLI already have this vocabulary: `--move` accepts
`--top` / `--end` (spec-tools.md §5.1.7), and `mm.MoveRequest` already carries
`Top` and `End`. The GUI work is wiring, not new semantics:

- Two new ops, `move-top` ("Move to top") and `move-end` ("Move to bottom"),
  registered as POST routes exactly like the other mutations
  (`/p/:projectId/items/:itemId/move-top`, `.../move-end`). Both map to
  `mm.MoveRequest{Top: true}` / `{End: true}` with **no section**: reordering
  never changes section, so the destination is the item's own.
- `actionsFor` adds both to the action list: **enabled for backlog items**
  (like `move`), **disabled with `Conflict` for working and done items**
  (also like `move` — only backlog items can be moved).
- No `mm.js` change: the card menu's generic click handler already posts
  `data-op` to `/p/…/items/…/<op>` for anything that is not
  remove/block/finish/edit/move/note, and the panel's generic `hx-post`
  branch does the same. Both surfaces pick the new ops up from the shared
  `Actions` list automatically.
- The two entries stay **enabled at the boundary**. "Move to top" on the
  item already at the top is a legal no-op — the library no-ops a
  same-position move rather than refusing it, exactly as `mm --move --top`
  on the top item does. Disabling there would need a reason code that does
  not exist in the error vocabulary, and would make the menu's answer depend
  on a position computation the server does not otherwise need for the menu.

## Files

- `internal/web/board.go` — `actionsFor`: `move-top`/`move-end` entries in
  every state case.
- `internal/web/item.go` — `operate`: the two new cases; the "nine routes"
  comment.
- `internal/web/routes.go` — the two ops join the mutation route list.
- `internal/web/audit_test.go` — the Appendix A audit's op enumeration gains
  the two ops, so the conformance pass also asserts they render.
- `internal/web/item_test.go` — `TestMoveTopAndBottomActions`: ready items
  have both enabled, working items have both disabled with `Conflict`, and
  the POSTs reorder the Ready section in both directions.

## Spec note

No spec change. §5.5 fixes a *floor* — one entry per legal operation, testid
`item-<ID>-action-<operation>` — and the two new entries fit the existing
pattern. §6.1's parity table is about drag reachability; these are
accelerators over `--move --top/--end`, which §6.1 already lists (`--move`
via `item-*-action-move`).
