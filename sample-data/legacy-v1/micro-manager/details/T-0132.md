# T-0132 — Library: expose per-file stamps for region-level change detection

## Context

`research-app-fllicker.md` §3 C. The broker cannot say *what* changed because
the fingerprint (`mm/fingerprint.go`) is one SHA-256 over the listing plus
per-file `name\0size\0mtime` — deliberately coarse, and by design not
decomposable. To publish region events the broker needs the per-file stamps the
hash is built from.

The owned-file set is a **library** rule (what counts as a data file, what is
ignored), so the helper belongs in `mm/`, not a re-stat in `internal/web`.

The spec's `Fingerprint` (§2.4 of spec-tools.md) stays exactly as defined: one
value, served over the API. This is an addition, not a change.

## Requirements

- A small exported helper — e.g. `FileStamps()` on `Store` — returning per-file
  name, size, and mtime for exactly the files `Fingerprint()` hashes.
- It MUST distinguish the `details/` **listing** (a file appearing or
  disappearing — that is what changes `data-has-detail` on a card) from the
  details/ **content** (size/mtime of an existing file — nothing a card
  renders). Callers need both facts separately.
- Same discipline as the rest of `mm/`: no environment access, no printing, no
  `os.Exit`, zero new dependencies.
- Tests against the real fixture directories: stamps change when and only when
  the corresponding files change, and the details-listing vs content split is
  asserted (touch a detail body → content changes, listing does not; add a
  detail file → listing changes).
- Nothing else: the broker-side diff and event naming are T-0133.

## Open questions

- Return shape: a sorted slice of entries vs a map keyed by name. The broker
  diffs two snapshots; whichever makes that diff trivial.
- Whether to reuse `stampOf`/`isOwnedFile` internals or expose a fresh walk.
