# T-0205 — Tickler: log scheduled items and next fire on every pass

From T-0204: the tickler ran for weeks without ever moving the due items and nothing in any log said what was scheduled. Add the audit listing to tickHeld (internal/web/tickler.go): before Store.Tick, call store.Ticklers(today) and log one line per scheduled item — ID, schedule, tickled (last fire), next fire — and a line when nothing is scheduled, so absence is visible too. The fires already log; the scheduled set is the missing half. Tests in internal/web/tickler_test.go. See details/T-0204.md.

## Done (2026-08-07)

- `mm.Tickler` gained a library-computed `Due` field: `Ticklers` reports the
  run's own due test (`Schedule.Due(now, tickled, created)`), so the log and
  the next `Tick` agree by construction — including the backdated one-shot,
  which logs `next=none due=true` ("overdue, fire now", spec-tools §5.3.3).
- `tickHeld` now calls `logScheduled` before each board's `Tick`: one Info
  line per scheduled item (`directory, item, schedule, tickled, next, due`),
  and one `count=0` line when nothing is scheduled — absence is visible too.
- Tests: `TestTicklersDue` (library, incl. the backdated case),
  `TestTicklerLogsScheduled` (order: scheduled lines then the fire; due=true
  for the backdated add), `TestTicklerLogsNothingScheduled` (count=0, no
  fires). A `recordsHandler` captures slog records for assertions.
- Full `go test ./...` green; library purity grep and `check.sh` clean.
