# T-0142 — Theme editor: edit the dark palette (colorDark) alongside the light

Follow-up from T-0137.

## Context

The editor (T-0137) has live preview, a built-in lite theme, and palette
generation from a base colour. What it still cannot do is EDIT the dark
palette: the form carries one `token_*` field per `color.*` token and none for
`colorDark.*`, the appearance preview shows the RESOLVED dark values, and the
save handler preserves the previous `colorDark` rather than writing anything
the user changed. A theme with `appearance: auto` (the built-in default is
auto) therefore has half its colours invisible to the editor.

The palette generator produces both halves (`/settings/theme/palette` returns
`light` and `dark`), and the client stores the generated dark for preview only
— it cannot be saved. That is the gap this task closes.

## What to build

- A palette switcher in the editor (Light / Dark) that swaps which set of
  inputs the form edits, so `token_*` fields target `color` or `colorDark`
  depending on the active tab. The save handler already reads
  `token_<path>` into `theme.Color`; the dark tab's fields need the same
  treatment into `theme.ColorDark` (§8.2: `auto` REQUIRES both sets, so an
  auto theme must be able to edit both in one place).
- The preview already works for both palettes; keep it.

## Verify

An `appearance: auto` theme whose dark palette is edited in the editor round
trips through save with the new `colorDark`, and the appearance preview shows
it. The palette generator's dark half lands in the dark tab's fields.

## Constraints

- Every `color` token is REQUIRED in both sets when `appearance` is auto
  (§8.2); the dark tab must default a missing value to the resolved one, the
  same per-token fallback the rest of the editor relies on.
- Unknown keys and `tui`/`extra` survive a save untouched (§8.2) — the save
  handler starts from the resolved theme, so keep that.

## Resolution (2026-08-05)

Implemented. The editor now carries two colour grids — light fields post as
`token_<path>`, dark as `tokenDark_<path>` — under a Light/Dark tab switcher
(`x-palette-tab-light`/`x-palette-tab-dark`, not contract testids). The tabs
only swap which grid is visible; both stay in the DOM, so one save posts both
sets and the handler reads whichever the user touched.

- `buildThemeEditor` renders `DarkColors` from the RESOLVED dark values (the
  per-token fallback is visible before typing); `DarkTab` picks the initial
  tab (dark only for `appearance: dark`). The server renders the initial
  hidden state; the JS syncs `aria-selected`.
- `saveThemeEditor` reads `tokenDark_<path>` into `theme.ColorDark`; an empty
  field is skipped, keeping the resolved value. Dark tokens render onto the
  SAME custom properties as light, so the JS previews a dark edit by updating
  the `data-dark-tokens` document and rebuilding the forced-dark block rather
  than using the light fields' inline override.
- The palette generator now fills both grids, not just light + preview JSON.
- The save handler was ALSO rebuilt to satisfy the §8.2 constraint, which the
  old code quietly violated: it based on `mm.BuiltinTheme()` (empty `raw`),
  dropping a library theme's unknown keys and `tui`/`extra` on save. It now
  bases on the resolved theme's own file (`resolved.Path`) when there is one,
  then fills every gap from the resolved values — so unknown keys survive AND
  every token stays present. The gui fields were dropped on save too (the form
  rendered them with live preview but the handler never read them); they are
  read now.
- A correctness trap: `ResolveTheme` hands back the SHARED built-in maps when
  no theme file exists, so writing dark edits had to go through the fresh
  built-in copy, never the resolved reference.

Tests: editor carries both palettes (initial tab + hidden state + resolved
values), the auto round trip (dark edit lands, light preserved, both sets
complete), empty-field fallback, unknown-key/tui/extra preservation, built-in
pollution guard, and gui-token save. All existing theme, audit and a11y tests
pass; gofmt/vet/test clean; `check.sh --all` 8/8.
