# T-0180 — Workflow tools: mm_start, mm_pause, mm_finish

From [[project/spec-pi-mm-plugin.md]]. Spec §4.2/§4.3: start surfaces the WIP-limit error with current slots so the agent can act; finish carries outcome + closing-note. No chaining — "start and finish" is two tool calls.

## As built

`plugins/pi-mm/src/tools-workflow.ts`. Three tools, each one operation, each
reporting where the item landed: `started T-0001 alpha → slot 01`,
`paused … → ready #1`, `finished … → done.md (shipped)`.

**The WIP limit needed no code.** `mm` already composes the remedy §4.3 asks
for:

```
wip limit reached (1/1)
  slot 01  T-0001  one
finish one, pause one, or raise the limit with --wip
```

The runner passes that through verbatim, so re-deriving a slot listing from the
envelope would be a worse copy of something already correct. What the plugin
adds is the *guideline* — "when mm_start reports the WIP limit, do not retry it:
finish or pause one of the items it names" — because the thing an agent gets
wrong here is retrying, and §8.4 says the plugin must never retry for it.

**`mm_finish` passes `--closing-note`, never `--note`.** `--note` is the
operation that adds one (`spec-tools.md` §5.1.10); passing it here would be a
second operation rather than a modifier. It also does NOT pass `--outcome` when
the caller omits one: the default is the CLI's, and repeating it here would be a
second place to change if it ever moved.

## The §8.1 guard, narrowed for the third time

The conformance grep fired on `tools-workflow.ts` for the string `done.md` — in
`landed()`, which builds the sentence "this item is in done.md now", and in
`mm_finish`'s description. It had already fired on a parameter description
saying `working.NN.md` (T-0179) and on this file's own header (T-0175).

Three false positives is the rule being wrong. **Naming a board file is how you
talk about a board; opening one is the thing that must never happen.** So the
test now asserts the mechanism rather than the vocabulary:

1. no plugin module imports `node:fs` — the load-bearing rule, since a board
   cannot be read or written without it, and the only thing the plugin spawns
   is `mm`, whose argv the runner's tests pin;
2. no board filename appears as a **path** — a bare literal (`"backlog.md"`) or
   one after a separator (`"details/T-0042.md"`). A filename inside a sentence
   is prose.

Narrowing it immediately caught its own bug: the needle `details` had been
matching `message["details"]` in board.ts — pi's word for a tool result's
payload, nothing to do with the board's `details/`. The needles now carry their
directory.

## Verification

`src/tools-workflow.test.ts` pins the argv, the landing text, and the WIP-limit
case — that the slot listing reaches the model, that the exit code and error
code reach `details`, and that exactly one `--start` was attempted.
`src/mm-contract.test.ts` then runs the whole lifecycle against a **real board
with one slot**: start, a real WIP limit with its real remedy, pause, start the
other, finish with a closing note, and confirm the note landed in the detail
file — two tool calls where a chain would have been one, as §4.1 requires.

87 tests: all pass with `mm` on PATH, 83 pass and 4 skip without. `tsc --noEmit`
clean.
