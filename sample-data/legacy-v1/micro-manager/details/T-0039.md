# T-0039 — Integrate EDITOR and VISUAL for detail editing

## Why this is wrapper territory by definition

`$EDITOR` is process environment and launching a child that takes over the
terminal is precisely what a UI service must never inherit. The library creates
the detail file; only `internal/cli` decides whether a human is shown it.

`VISUAL` wins where both are set (§3.5). The distinction is historical but real:
`EDITOR` may be a line editor for a dumb terminal, `VISUAL` is the full-screen
one, and this is a full-screen job.

## The editor is not run through a shell

`EDITOR="code --wait"` is common and has to work, so the value is split on
whitespace into a program and arguments. It is **not** passed to `sh -c`, which
would make a semicolon in the variable run arbitrary commands with the user's
file as an argument. A test asserts that `EDITOR="myeditor --wait; rm -rf /"`
arrives as inert argv rather than as shell syntax.

## Five ways to say no

Each is a case where handing over the terminal would be *wrong*, not merely
unwanted:

- `--no-edit` and `--quiet` — asked for explicitly;
- `--json` and `--porcelain` — a machine is reading stdout, and an editor would
  seize the terminal in the middle of a pipeline;
- `--dry-run` — nothing was written, so there is no file to open;
- **no terminal** — the same reason one level down. A CI job with `EDITOR` set
  would otherwise hang forever waiting for a human. `cmd/mm` decides this by
  checking that stdin and stdout are both character devices.

## A failed launch is not a failed operation

The item and its detail file are written and validated before the editor is
considered. If the launch fails, the failure is reported on stderr and the exit
code stays 0 — losing a recorded item because `$EDITOR` was misconfigured would
be the tool destroying good work over a preference.
