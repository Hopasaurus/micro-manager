# T-0130 — Suppress refresh echoes in mm.js: own mutations and in-flight drags

## Context

`research-app-fllicker.md` §2 sources 3 and 6, and §3 E.

**Mutation echo.** A mutation swaps the board from its POST response; within 5 s
the broker's next poll sees the new fingerprint and publishes `board`; the
client fetches and swaps the *identical* board again. Morph (T-0129) makes the
second swap invisible, but it is still a round trip and it keeps `data-busy`
true through both requests — the quiescence signal the external suite waits on.
The client can distinguish its own mutation from an external write: the service
cannot (the broker sees only a fingerprint change), but the tab that issued the
request can.

**Drag interruption.** A refresh mid-gesture replaces the dragged card (morph
strips the client-only `data-dragging` / `data-move-mode` attributes the server
never emits) and kills the move. `mm.js` already knows a move is in flight — its
`move` variable.

## Requirements

- Record the time the last mutation response settled (an `htmx:afterSettle`
  after a request this tab issued), and skip an `sse:board` / `sse:status`
  event that arrives within ~1–2 s of it. The POST response already carried the
  fresh region; the fetch would return identical bytes.
- Suppress region refreshes entirely while a drag is in flight (`move !== null`).
- Suppression is **per-tab** and only covers the tab that made the request: tab
  A's mutation must still refresh tab B through the same SSE event. Do not
  suppress in a way that reads shared state.
- Keep the `data-busy` accounting correct — a suppressed event must not be
  counted as an in-flight request, and an unsuppressed one must not be lost.
- With morph in place this is an optimisation (the echo is already invisible);
  its measurable value is fewer fetches and a shorter busy window. Without morph
  it is a correctness-adjacent fix for the visible double-swap. Both land in
  Phase 1.

## Open questions

- Window size: 1–2 s is the guess; tune so a real external write arriving
  within the window still wins (the next poll, ≤5 s later, catches it).
- Whether to suppress the `sse:check` echo too, or only board/status.
