# T-0012 — Implement the transaction envelope: read, modify, validate, write

## Context

`spec-tools.md` §7. Every operation is a transaction over one directory and must
be all-or-nothing. `--start` touches two files; `--edit --title` touches an item
file and possibly a detail file. A partial application of either leaves the
directory invalid.

## Requirements

1. Read, modify in memory, **validate**, then write. Never mutate a file
   incrementally.
2. Validation runs before every commit. If the resulting model violates any
   invariant, return `ErrInvariantViolation` with the list and write nothing.
   This is what makes it impossible for the tool to produce a directory its own
   checker rejects.
3. Write each file atomically: temp file in the same directory, `fsync`, then
   `os.Rename`.
4. Order multi-file writes so that a crash between them fails validation loudly
   rather than losing data.
5. Record size and mtime at read; if they differ at write, return
   `ErrConcurrent` without writing.
6. Every mutation accepts a dry-run flag and returns its `[]Change` without
   writing.

## Write ordering

| Operation | Write first | Then | Crash between leaves |
|---|---|---|---|
| start | working file | remove backlog line | duplicate ID — I1 catches it |
| pause | backlog line | reset working file | duplicate ID — I1 catches it |
| finish | done.md line | reset working file | duplicate ID — I1 catches it |
| edit title | item file | detail frontmatter | title drift — I9 catches it |

The rule in every row: **write the copy before removing the original.** A
duplicate is a reported violation; a deletion is gone.

## Open questions

- Advisory locking is RECOMMENDED but not required. Defer until the UI service
  exists; concurrent detection (rule 5) covers the CLI-plus-editor case.
