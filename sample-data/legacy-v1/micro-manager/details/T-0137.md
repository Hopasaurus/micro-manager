# T-0137 — Theme preview in theme editor

The theme editor should have a live preview so the user can see what the theme will look like.

Also add a lite mode theme that is built in.

Also add a feature to do automatic color complementing or whatever it is called where a user can pick a color and other colors and shades are selected that look nice with that color and it is somehow based on a color wheel.

## Update (post-ship)

All three features shipped, with the colour math in the library and the client
kept thin.

### 1. Live preview

`spec-gui.md` §8.7 already required it ("Editing a theme MUST apply live to the
current view, so the editor is a preview"); the editor was a form with a save
button that revealed the result afterwards. Now every token input carries
`data-token-path`, and `static/theme-editor.js` maps the path to its custom
property and overrides it on the app root as the user types — so the page
itself (header, nav, editor, status bar) re-themes live. The appearance select
previews the dark palette too: the server serialises the resolved `colorDark`
into `data-dark-tokens` on the editor container, and choosing dark/auto forces
those values on even when the OS is light. The preview is ephemeral by design
(§2.1): the server stays authoritative, a reload drops it, and Save posts the
form values the server validates.

The script is a separate file because the shell's `mm.js` has a 700-line guard
(dragdrop_test.go): the editor's behaviour is page-specific and loads only on
`/settings/theme`.

### 2. Lite theme

`micro-manager-lite`, the second built-in: a desaturated, low-chrome, light
theme (near-monochrome palette, muted borders, no shadows beyond the tokens).
Details:

- `mm.BuiltinThemes()` is the registry — default first (it is the bottom of
  §8.7), then lite. `BuiltinLibraryTheme(id)` resolves a compiled-in entry, and
  the web listings (theme library, settings select, JSON API) and exports all
  derive from the registry, so they cannot drift.
- Resolution: a config that names a built-in library theme resolves it at the
  SAME precedence position as a library file (step 2 for a project-named id,
  step 4 for a system-named id), via a `builtinID` fallback on the candidate
  list. A project that names lite beats a system theme.json; a project
  theme.json beats the project's own naming of lite.
- The lite theme carries no `gui` tokens: it inherits the default's per-token
  fallback, so it changes the colour story, not the typography. It exports and
  re-imports like any theme.
- The settings theme select now offers both built-ins PLUS library-file themes,
  which previously were not selectable through the UI at all.

### 3. Palette from a colour

`mm/palette.go`: `HexToHSL`/`HSLToHex` (standard RGB-model wheel) and
`HarmonizedPalette(base, dark)`, which derives the complete 30-token colour set
from one base. The scheme: semantic hues stay at their meaning (blocked red,
working yellow, done green, ready blue) so a "done" state keeps meaning when
the brand colour changes; the base supplies the saturation (a grey base yields
a deliberately monochrome palette); the base itself is `accent.base`; its
complement (180° away) tints `border.focus` and `selection.bg`; and
`accent.fg` is chosen by luminance so the accent pair always clears WCAG AA.

The editor has a "Palette from a colour" box: type a hex, Generate fetches
`GET /settings/theme/palette?base=…` (an internal route, like `/p/:id/shell` —
not in the spec's route table), and the client fills every colour input, which
fires the same input listener the typing preview uses. The derivation lives in
the library so a future TUI theme editor derives the same tokens from the same
base; the endpoint is how the web editor reaches it without duplicating the
math in JS.

### Shipped alongside

- `saveThemeEditor` starts from the RESOLVED theme rather than the default, so
  editing a library theme no longer silently replaces its `colorDark` with the
  default's (the editor has no dark fields — see T-0142).
- The project settings page now highlights the PROJECT's chosen theme, not the
  system config's, and the source badge is read off `ResolveTheme`'s answer
  instead of file existence.
- A file theme whose id shadows a built-in (e.g. an imported
  `micro-manager-lite.json`) is listed once and cannot be confused with the
  built-in.

### Follow-ups registered

- **T-0142** — the editor still cannot EDIT `colorDark`; the preview shows it
  and palette generation fills it, but only for preview. This is the largest
  remaining gap.
- **T-0143** — spec-gui.md §8.7 defines the theme library as files; mm now
  resolves compiled-in entries at the same precedence. The spec should name
  the built-in library themes.

### Test discipline

All of it in Go, library-side where possible: HSL round trips, palette
completeness/determinism/contrast, grey-base monochrome, lite completeness +
AA + export round trip, registry, and precedence (project-named lite beats
system theme.json, project theme.json beats named lite). Web-side: the editor
carries the preview hooks, the lite theme appears in every surface, the palette
endpoint returns complete sets and rejects a bad base, and the save preserves
the dark palette. The JS itself is untestable here — that is the standing gap
of T-0111 (JS test runner).
