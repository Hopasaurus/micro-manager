# T-0194 — detect multiple mm directories in the same directory

for instance micro-manager & .micro-manager

error on this and have the user fix

## What was already true

Resolution refused before this task: two candidates at the resolving step is
the ambiguity of `spec-tools.md` §4, and `mm --status` in such a directory
already failed with both paths listed.

The gap was the command a user runs to ask *is anything wrong here*:
`--check` said **both boards are clean**. A situation that splits a project's
history in two was invisible to the tool whose job is reporting exactly that.

## The rule

One parent directory holds at most one micro-manager directory
(`spec-file-format.md` Appendix B, "Two boards in one place"). It is a mistake
because **nothing joins them**: no shared `next_id`, so both start at `T-0001`
and the same ID means two different items; a report covers one of them; and
someone adding an item today cannot tell which board yesterday's went into.

## Decisions

**It is not an invariant, and not I11.** I1–I10 are properties of one
directory's *files*, and a conforming reader must be able to validate a board
it was handed without reading the directory above it. Making this an invariant
would oblige every reader to walk upward, which nothing else in the format
requires — and would put it inside `Store.Validate`, which runs before every
mutation. So it lives in the checker front ends, which already look at the
parent: `internal/cli`'s `collisionFindings` and `check.sh`'s own copy.

**Reported against each colliding directory, not once against the parent.**
Two reasons. A person working in `./micro-manager` who never runs `--all` has
to be told, and `--check --dir X` is how they would ask. And the per-directory
result array is what `--json` and `--porcelain` carry — a finding attached to
the parent would have no place in the envelope, and the pi plugin's `mm_check`
would print "clean: no violations" for a run that exited 1.

**A write is still allowed.** The collision does not block `--add` or any other
mutation: the library's validator never looks at the parent, so the user can
keep working in whichever board they meant while they sort it out. Search-based
resolution still refuses, so they will be passing `--dir` until it is fixed —
which is the pressure the task asked for, without a hostage.

**A sibling that is not a board is not a collision.** The emptiness test comes
first: an empty `.micro-manager` beside a real board is that test's business,
and reporting it as a rival board would send someone to fix the wrong thing.

**`--find` warns rather than hides.** Both directories stay in the listing —
hiding one would pick a winner, the one thing the format never does with
ambiguity — and a stderr line names the parent.

## The trap this turned up

The first version of the `check.sh` half probed `"$parent/$name"` for each of
the six recognized names. That is wrong on a normalization-insensitive
filesystem: APFS resolves `µmanager` (U+00B5) and `μmanager` (U+03BC) to the
same directory, so `sample-data/symbol/µmanager` reported a rival named
`μmanager` that does not exist — a false positive on this repository's own
fixtures, caught by running `./check.sh --all`.

Both implementations now enumerate the parent's **entries** and compare names
as strings. The Go side never had the bug, because `os.ReadDir` returns what is
actually there; the two implementations disagreeing is what exposed it.
`TestCollidingSiblingsDoesNotInventAUnicodeTwin` pins it.
