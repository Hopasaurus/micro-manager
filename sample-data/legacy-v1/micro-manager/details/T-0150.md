# T-0150 — Flicker follow up

There is still some flicker. In part this is caused when there is a full
refresh and the someday column is collapsed: all the items render briefly in
their positions as if the column was not collapsed, then jump to the right
position.

## Root cause

The someday collapse state (§5.5) is a **client preference**, kept in
`localStorage` under `mm:someday-collapsed:<project>`. The server never
persists it, so every board render the server produced emitted the someday
column **expanded** (`data-collapsed` absent). When htmx morphed in a fresh
board — the SSE/poll refresh of §2.3, or a mutation's `board-swap` — the
column expanded for a frame, and `restoreSomedayState()` on
`htmx:afterSettle` collapsed it a beat later. htmx's settle phase runs
after the swap asynchronously, so the browser paints the expanded board in
between: items render briefly in their un-collapsed positions, then jump.
That is the reported flicker.

Reproduced in headless Chromium (probe in `/tmp/ssetest/flicker-probe.mjs`):
with the pre-fix code a forced full refresh took the someday column through
`data-collapsed: true → (absent) → true` — one frame expanded.

## Fix

1. **Server renders the collapse state (the real fix).** The client sends the
   state on every htmx request as `X-Someday-Collapsed: true|false`
   (`htmx:configRequest` in `mm.js`). `buildBoard` reads it and marks the
   someday column; the board partial emits `data-collapsed="true"` and a `v`
   toggle when collapsed, `data-collapsed="false"` and `>` otherwise (matching
   the canonical §5.5 markup). A swap is therefore **born collapsed** — the
   morph never expands it, so there is no frame to paint.
2. **Client fixup moves from `afterSettle` to `afterSwap`.** The fallback for
   a load or swap that never carried the header now lands in the same task as
   the swap, before the browser paints, instead of after htmx's settle delay.
   `DOMContentLoaded` still covers the initial full page load.

The header is sent by every htmx request (SSE refresh, 30s poll, mutation
POSTs), so all three board-refresh paths — the ones the flicker-fix phase
(T-0128…T-0131, T-0138) routes through `buildBoard` — render collapsed.

## Files

- `internal/web/static/mm.js` — `somedayCollapsed()` helper, the
  `htmx:configRequest` header, `restoreSomedayState` on `afterSwap`.
- `internal/web/board.go` — `columnData.Collapsed`, `somedayCollapsed(c)`
  reading the header in `buildBoard`.
- `internal/web/templates/partials/board.html` — emits `data-collapsed` and
  the toggle glyph from `$c.Collapsed`.
- `internal/web/board_test.go` — `TestSomedayCollapseRenderedFromHeader`:
  the fragment is born `data-collapsed="true"` / toggle `v` with the header,
  `false` / `>` without it, and the state never leaks onto other columns.
- `internal/web/dragdrop_test.go` — the mm.js size guard raised 700 → 720
  with a reason (the header plumbing is client-side by necessity, §2.1).

## Verification

- `go -C implementations/golang test ./...` — all packages pass.
- `./check.sh --all` — 8 directories clean.
- Browser probe (headless Chromium, `flicker-probe.mjs`): collapse the column,
  arm a `MutationObserver` on `data-collapsed`, force the full refresh
  (`sse:board` on body). Result: the refresh request carried
  `X-Someday-Collapsed: true`, the response was born collapsed, and the
  attribute never left `true` — no expanded frame. The same probe against the
  pre-fix build (HEAD worktree) caught `true → absent → true`, proving both
  the bug and the probe's sensitivity.
