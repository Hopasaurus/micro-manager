# T-0117 — GUI: non-default prefix and width end to end

Fifth task of the T-0112 spike. Depends on T-0113/T-0114.

## Today

- The web package interpolates rendered IDs everywhere (routes
  `/p/:projectId/item/:itemId`, card testids `item-{{.ID}}`, details links,
  search), so most of it should adapt to any ID shape automatically.
- The JSON API reports `projectId` (a hash) and item IDs as strings — shape is
  fine, but the API's `nextId` and any item-path construction must not assume
  `T-`/4.

## What to change

- Audit for hardcoded `T-`/4-digit assumptions: routes, the API item paths,
  test fixtures, the audit-testid families (they interpolate, but the spec
  examples in spec-gui.md may repeat the `T-0042` form and need reconciling).
- Serve a non-default fixture (from the T-0116 corpus) through the GUI test
  server and verify add/edit/remove/search/SSE round trips with `X-003`-style
  IDs.

## Verify

Browser or harness-level: a directory with `id_prefix: X` / `id_width: 3`
renders, opens panels, saves, and reports status with its own ID shape; the
existing `T-` corpus is byte-unchanged.

## Update (post-ship)

Every ID argument a front end accepts is now parsed against the directory's
**declared** grammar, never the default shape. The one place that had hardcoded
the default was the parse gate: `mm.ParseID` (default `T`/4) stood in front of
the panel, every mutation, the dialogs and the API's `:itemId`, so a valid
`X-001` was refused as "not a T-#### id" the moment it left the board.

Landed:

- **`Store.Grammar()`** (`mm/store.go`) — the typed accessor for the declared
  grammar, the same information `Directory()` already carried as
  `IDPrefix`/`IDWidth`; both web packages parse through it.
- **HTML views** (`internal/web/item.go`, `dialogs.go`) — `parseID`/`itemID`
  resolve the route parameter and the dialog's `?item=` in the store's grammar.
- **JSON API** (`internal/web/api`) — `itemID` takes the store; the move
  operation's `before`/`after` parse in the grammar too.
- **API init** — `POST /api/v1/projects` accepts `idPrefix`/`idWidth`, mirroring
  the CLI's `--init --prefix/--id-width` (T-0115), so a script can create a
  non-default board over HTTP.
- **Spec**: spec-gui.md needed no edit — §3.2 and §5.1 already say an ID
  appears verbatim and name `T-0042` as the *default* grammar; the examples
  are illustrations, and the T-0070 audit resolves Appendix A patterns
  (`item-<ID>`) against the fixture rather than a fixed shape.

Tests (`internal/web/grammar_test.go`, plus `TestStoreGrammar` in `mm/`):
serve `testdata/clean-id-grammar` (X/3, from the T-0116 corpus) through the
harness and drive the board, panel, dialogs, every mutation, search, status,
the JSON API (list/show/add/edit/remove/move/start/finish/note/detail/init)
and SSE with X-IDs; a foreign-shape ID is refused with the declared grammar in
the error; and a read battery over both `clean-id-grammar` and `clean-full`
leaves every file byte-unchanged. The real binary (`cmd/mm-ui`) was also
smoke-tested against a copied X/3 directory: board, panel, nextId `X-005`,
allocation, and a clean `check.sh` after mutations.
