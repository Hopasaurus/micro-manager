# T-0035 — Implement dry-run across every mutation

## What was already true

Every library mutation took a dry-run flag from the start (T-0012's transaction
envelope runs read → modify → **validate** → write, and the dry-run return sits
*after* validation), and the CLI passed `--dry-run` through to all nine of them.
So this item was not about adding a capability. It was about proving one.

## How it is proven

`internal/cli/dryrun_test.go` runs each of **21 scenarios twice** against two
identical directories — once dry, once for real — and requires the two to agree
on the exit code, on stdout and on stderr, after normalising the temp path and
the `would:` marker.

That shape was chosen over asserting on wording, which would only pin today's
phrasing. It tests the requirement that actually matters and is easiest to get
wrong: §3.4 says a dry run must return **the code the real run would have
returned**, so it can gate a script. Six of the scenarios are commands that
*fail* — the WIP limit, the remove guard, a wrong-state pause, an unknown id —
because a dry run that reports success for a command that would be refused is
worse than useless: it is a script that proceeds into a failure.

## One thing decided rather than implemented

**`--dry-run` on a read-only operation is accepted, not refused.** §3.4 lists it
under switches "valid with every operation", and a read computes no change and
writes nothing, so the requirement is already satisfied trivially. Making it a
usage error would have been defensible strictness but would contradict the spec.
A test pins that `--list --dry-run` is byte-identical to `--list`.

## Not reachable by a dry run

Concurrent-modification detection: the size and mtime comparison happens in the
write step, which a dry run does not perform, so `--dry-run` can never return
exit 5. That is inherent rather than a gap — there is nothing to conflict with
when nothing is written.
