# T-0177 — Board resolution, pinning, and session/branch state

From [[project/spec-pi-mm-plugin.md]]. Spec §3.2 + §7: resolve through mm only (pin > MM_DIR passthrough > mm's own discovery), read directory.path from the first envelope and pin it; every later call passes --dir. Ambiguity (exit 3) surfaces candidates and requires a pin, never guesses. Also §3.2.1: mm_find lists located boards (in-use marked; empty is a result, not an error) and the board in use is always knowable — mm_board no-args returns path+project+how it resolved, mm_status names the directory, and the TUI keeps a persistent ctx.ui.setStatus board line (set at session start, on pin change, cleared when none). mm_board no-path is the full 'show me this board' view: identity + description + live status summary (§3.4). Pin travels in tool-result details per pi's state-management pattern and is reconstructed on session_start; branches get their own pin.

## As built

`plugins/pi-mm/src/board.ts`. The plugin never scans directories: resolution is
one `mm --status` with **no `--dir` at all**, which is what lets `mm` apply
`MM_DIR` and then its own discovery — the "refuse rather than guess" rule is
its, and re-implementing it here would be a second answer to disagree with.

- **Pinned means pinned.** Once a board is resolved, `resolveBoard` returns it
  without running anything, and every later call passes `--dir <pinned>`. A test
  counts the subprocesses to prove it: mid-session re-resolution is exactly what
  flips boards when two are nearby.
- **Ambiguity refuses and lists.** Exit 3 carrying `Ambiguous` produces a
  failure with the `mm --find` candidates attached and "pin one" as the remedy.
  Nothing is pinned in that case — the plugin must not choose (§3.2).
- **How it resolved is inferred, and honestly.** `mm` does not report which rule
  fired, so `MM_DIR` is named as the source only when it names the very
  directory that came back. Saying "MM_DIR" whenever the variable is merely SET
  would be a guess, and wrong whenever discovery overrode nothing.
- **The pin lives in the branch, not in memory.** It travels in tool-result
  `details` under one key, and `session_start` rebuilds it by scanning the
  active branch for the last pin-bearing result (`mm_status`, `mm_board`,
  `mm_init`). The module-level value is a cache of what the branch says. The
  reconstruction reads defensively — a transcript can hold anything an older
  build wrote — and ignores a `details` payload that is not a pin.
- **The status line** follows the pin: set at session start, updated on every
  tool call that resolves, and reading "no board" rather than a stale name when
  nothing is resolved.

## A design fix the tests forced

`board.ts` first called the runner module directly, so the tool layer could not
inject one — and three read-tool tests failed with "no calls recorded" rather
than with a wrong answer. That was the tests catching a real coupling, not a
test problem: resolution IS a pair of `mm` calls, so a caller that cannot
substitute a runner cannot test the thing the module exists to do.
`ResolveOptions.run` now takes the runner, defaulting to the real one.
