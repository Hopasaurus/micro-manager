# T-0037 — Implement block, unblock and note

## Where each one lives

**`--block` and `--unblock` are CLI sugar over `--move`**, exactly as §5.2 says.
They call `Store.Move` with the section set rather than writing a `blocked:`
field themselves. A second path that set the field directly would be a second
implementation of I5, and two implementations of an invariant eventually
disagree. `--unblock` returns the item to the *top* of `## Ready`: something
that has just become possible is usually the next thing to pick up.

**`--note` needed a library operation.** There was nothing that could append to a
*working file's* `## Notes` — `AppendDetailSection` only reaches detail files —
and where a note lands is a rule, not a rendering choice, so it belongs in the
library where the UI service gets it too.

`Store.Note` routes by state: a working item's notes go in its slot, next to the
work, where `--pause` and `--finish` already know to preserve them. Anything
else goes to the detail file, created if absent, via the *same* `preserveNotes`
path those two use — so a note written before a pause and one written by the
pause end up in the same place in the same shape. A test pins that.

Entries are dated by default. Notes accumulate over days, and an undated pile of
them cannot be read back as a history.

## The second namespace collision, resolved

`--note ID TEXT` (§5.2, an operation) collided with `--finish --note TEXT`
(§5.1.10, a modifier) — the same defect as `--wip`, found by the same rule in
§3.2, and this time predicted in the correction note that T-0030 left at §5.1.1.

Resolved the same way and for the same reason: **the operation keeps the short
name** — §5.2 calls it the highest-frequency write in daily use — and the
modifier becomes `--closing-note`. The spec is corrected at §5.1.10 with the
reason recorded.

The collision was caught by this implementation's own tests the moment `--note`
became an operation: two existing tests using `--finish --note` started failing
with "--finish and --note are both operations". That is the parser enforcing
§3.2 on the spec, which is the point of implementing the rule literally.

**One collision is still open**: `--detail ID` (§5.2) against `--add --detail`
(§5.1.2). Neither is implemented as an operation yet.
