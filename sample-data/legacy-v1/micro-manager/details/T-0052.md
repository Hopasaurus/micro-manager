# T-0052 — Build the project registry and the discovery cache

## Context

Every route under `/p/:projectId` has to turn twelve hex characters into an open
`mm.Store`. Nothing else in the service may hold a path-to-store mapping, and
nothing may accept a filesystem path in a URI position (`spec-gui.md` §3.1).

The registry is also where the two caches live: open stores, and the discovery
result. `spec-gui.md` §9.5 is explicit that fingerprint polling detects change
*within* a known project and never a new project appearing, so discovery is
cached with an explicit rescan rather than re-walked per request.

## Requirements

1. `internal/web/registry.go`: `Resolve(projectId) (*mm.Store, error)`, backed by
   a map keyed by id. `ErrNotFound` for an unknown id — the handler renders the
   not-found view with **404, never a redirect to `/`** (§4.1 rule 4).
2. Population, in this order: `scan.roots` discovery, the favorites file, the
   recent file, and any path passed on the command line. A favorite on an
   unmounted drive resolves to an entry marked missing, not to nothing —
   `spec-gui.md` §10 rule 5 forbids silently dropping it.
3. `mm.Store` is already safe for concurrent use, so a store is opened once and
   shared. Opening is cheap (it stats, it does not read), so eviction is not
   worth designing; a bounded map with no eviction is fine for a single-user
   tool.
4. Discovery cache carries `scannedAt` and `partial`, both of which reach the
   DOM (`data-scanned-at`, `data-partial`) and the JSON of `GET /api/v1/scan`.
   `POST /api/v1/scan` and `projects-rescan` force a re-walk. `scan.rescanOnFocus`
   is a client-side trigger onto the same route.
5. Root expansion — `~` and environment variables — happens **here**, never in
   the library (`spec-tools.md` §2.2 rule 4, `spec-gui.md` §9.5 rule 2). The
   library receives absolute paths in `DiscoveryOptions`.
6. A root that does not exist is reported and skipped, never fatal (§9.5 rule 3).
   Empty `scan.roots` falls back to the service's start directory as a single
   root and surfaces a prompt to configure roots — never `$HOME`, never `/`
   (§9.5 final rule).
7. Opening a project updates the recent list: moved to the front, never
   duplicated, `lastOpened` refreshed (`spec-gui.md` §10 rule 1). That write is
   atomic and tolerant of a concurrent writer, because the TUI may be running.

## Open questions

- Whether a project reachable only through recent/favorites but outside every
  scan root should appear in `/projects`. §5.3 groups by scan root, which
  implies not — it needs a group of its own, or it is reachable from Home only.
  Decide when building `/projects`.

## As built

`internal/web/registry.go`.

**The open question is resolved.** A project reachable only through favorites or
`--dir`, outside every scan root, gets a group of its own in the `/projects`
view rather than vanishing. §5.3 groups by scan root and has no place for it;
dropping it would make an explicitly opened project invisible in the list of
projects, which is worse than an extra group.

**Path comparison canonicalises both sides.** Discovery returns resolved paths —
on macOS `/var/folders/...` comes back as `/private/var/folders/...` — while a
configured root is whatever the user typed. Comparing them raw filed *every*
project under "no root at all", which the grouping test caught.

**The first walk happens on the first request, not at startup.** A slow or
absent network mount then delays one request rather than the service coming up
at all.

**Stores are opened once and kept.** `mm.Store` is safe for concurrent use and
opening is cheap — it stats, it does not read — so a single-user tool needs no
eviction. A store whose directory has since vanished simply fails its next
operation, which is the honest answer.

**A missing directory is still addressable.** `rememberPath` derives the id even
when the path does not resolve, so a favorite on an unmounted drive can be
rendered with `data-missing="true"` and offered explicit removal (§10 rule 5).
Resolving it fails; knowing about it does not.

**`touch` re-reads before writing** through `mm.UpdateProjectList`, so a second
front end running at the same time loses one edit rather than the whole file.
