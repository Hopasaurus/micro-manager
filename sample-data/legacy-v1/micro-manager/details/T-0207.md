# T-0207 — Tickler: add a system-settings control for tickler.interval and document the drivers

From T-0204: the tickler silently never ran because it is opt-in with no UI
path — the only way to enable it was hand-editing
`~/.config/micro-manager/config.json` and restarting. Instead, put the control
in the UI. The service must apply a change without a restart.

## The control

- **Where:** the system settings view (`/settings`, `data-scope="system"`), as a
  new "Tickler" section. It MUST NOT appear in project settings
  (`/p/:projectId/settings`) — `tickler.interval` is system-scoped and a
  project config MUST NOT set it (spec-gui.md §9.2).
- **Shape:** an on/off control plus an interval field (a duration like `1m`,
  `30s`; empty = off). Pre-fill from the merged config. Show the current state
  (on with interval / off) so the section is honest about what the service is
  doing.
- **Testids:** `x-`-prefixed — e.g. `x-settings-tickler`, `x-settings-tickler-interval`,
  `x-settings-tickler-status` — because spec-gui.md §5.9 does not enumerate a
  tickler section and §5.1 requires added testids to carry the `x-` prefix. The
  section is an extension of the spec, not contract. If it should become
  contract, amend §5.9 (and §2.4) in the same change — recorded here, not done.
- **Validation:** the interval must parse as a Go duration before saving; a typo
  must not silently turn the service on or off (the same principle as
  config.go's applyConfig warning). Reuse `time.ParseDuration`.

## Persistence and live application (the core of this task)

The write path already exists: `saveSettingsSystem` (POST /settings) mutates the
system config via `cfgFile.Set(...)`, `Save`s it, and reloads the merged config
into `s.opts.Config`. Add `cfgFile.Set("tickler.interval", ...)` there, and do
the same on the API path `PUT /api/v1/config` (`putSystemConfig`), which
replaces the whole file.

The gap: `ticklerLoop` is started **once at startup** (server.go) with the
interval captured at that moment; reloading `s.opts.Config` does not touch it.
Introduce a tickler controller that owns the loop goroutine and exposes
`apply(interval)`: start the loop when turned on, stop it when turned off,
restart with the new duration when changed, and never leak a stopped loop. Call
it after every config reload — both POST /settings and PUT /api/v1/config —
and at startup. The loop keeps its existing semantics (one pass per interval
over held boards only, spec-gui.md §2.4); decide whether an enable takes one
interval before the first pass or ticks immediately, and record it.

T-0206 (warn at startup when disabled) stays complementary: the default stays
off, and a silent non-runner must still be impossible.

## Docs

Record, in SKILL.md and AGENTS.md, the three ways the tickler runs: the UI
service on `tickler.interval` (held boards only; now settable from system
settings), a cron running `mm --tick`, and the fact that the default is off.

## Verify

Without touching the config file by hand: open `/settings`, enable the tickler
at `1m`, and confirm the running mm-ui logs `tickler service on` (or the
controller's equivalent) and moves a due someday item without a manual `--tick`
or restart; then disable it via the control and confirm the loop stops.

T-0206 shipped the startup warning; its help text names the two enablement
paths that exist today (system-config interval, cron `mm --tick`). When the
settings control in this task ships, extend that help text to name the
settings control as the third path.

## Done (2026-08-07)

**The control.** New system-scope Tickler section in the settings view
(settings.html + settings.go): a checkbox (`ticklerEnabled`), an interval
field (`ticklerInterval`), and a status badge ("off" / "on · every 1m").
Testids `x-settings-tickler`, `x-settings-tickler-enabled`,
`x-settings-tickler-interval`, `x-settings-tickler-status` — `x-` prefixed per
§5.1, since §5.9 has no tickler section. Absent from project settings
(system-scoped, §9.2). Pre-filled from the merged config. Enabled needs an
interval that parses as a Go duration; a typo or an empty interval refuses the
whole save (400) and changes nothing. Disabling writes the documented
`null` value (§9.2).

**Live application.** A `tickler` controller (internal/web/tickler.go) owns the
loop goroutine: `apply(interval)` starts it, stops it (waiting for the old
goroutine to exit — no leaks), or restarts it with a new duration, and reports
whether the effective state changed so a config reload that did not touch the
tickler logs nothing. Start creates it and logs the state (T-0206's line, now
with the settings path in the help text). `SystemConfigReload` re-reads the
system config into the merged view and applies the tickler; both write paths
call it — the settings form (POST /settings) and `PUT /api/v1/config`
(api/files.go, system scope, non-dry). Startup logging is not double-logged.

**Scope guard.** The API's project-config write-refusal list gained `tickler`:
a project PUT setting it is now 400, matching the library's own refusal.

**Docs.** SKILL.md and implementations/golang/AGENTS.md record the three ways
the tickler runs (UI service on `tickler.interval` — settable from system
settings, held boards only — cron `mm --tick`, default off) and the
observability contract.

**Verified.** Tests: `TestTicklerSettingsSection` (render/pre-fill/save/typo-
refusal/off), `TestProjectConfigRefusesTickler`, `TestTicklerControllerApply`
(unit: start/no-op/stop/restart, no leaks), `TestTicklerSettingsAppliesLive`
(real Start + real API: enable at 10ms → due item moves without restart,
disable → loop stops, transition logs on/off). Full `go test ./...` green,
`-race` clean on the tickler tests, gofmt clean, `check.sh --all` 8/8. Built
`mm-ui` and ran it against a copy of this tracker: enabled via the API, a
backdated someday item moved to Ready in one tick, disabled cleanly.
