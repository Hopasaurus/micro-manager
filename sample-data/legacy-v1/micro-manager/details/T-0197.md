# T-0197 — GUI: the monthly Wake-up control cannot express last (spec-gui §5.6)

Found while wiring the Wake-up group in T-0173.

`spec-gui.md` §5.6's composition table says the monthly kind takes
`tickler-monthday` **"(required, `1`–`31` or `last`)"**, and the format's
`SCHEDULE` token has `last@08:00` — the last day of the month, which is the
whole reason the value exists. But the same section's DOM sketch fixes the
control as

```html
<input data-testid="tickler-monthday" type="number" min="1" max="31"
       name="tickler-monthday">
```

and a `type="number"` input cannot hold the string `last`. So a schedule the
format supports, the CLI accepts (`mm --add --tickler last@08:00`) and the
server's composer already handles is unreachable from the UI.

The server half is done and stays done: `composeTickler` passes `last` through
untouched and zero-pads everything else, and `prefillTickler` reads a `last`
schedule back into the control. Only the control cannot produce one.

## The decision to make

Whatever fixes this is a **spec change first** (§5.6's DOM sketch is the
contract a conformance suite reads), then a template change. Three shapes, none
obviously right:

1. Make `tickler-monthday` a `<select>` of 1–31 plus "last". One control, one
   testid, no new DOM — but it drops the number input the sketch names, and a
   31-option select is clumsy.
2. Keep the number input and add a sibling checkbox (`tickler-monthday-last`).
   A new testid in the contract, and two controls for one value.
3. Change the input to `type="text"` with a pattern. Keeps the testid and the
   shape, loses the browser's number affordances.

T-0173 shipped the spec's sketch verbatim rather than inventing DOM the
contract does not have; this item is where the choice gets made.

## Done (2026-08-07)

**The decision — Option 3: `type="text"` with a pattern.** `tickler-monthday`
is now a text input whose `pattern` is exactly the allowed token set,
`(0?[1-9]|[12][0-9]|3[01]|last)` — a day `1`–`31` (composed zero-padded) or
the sentinel `last`. Chosen because the value is already a plain token through
the whole pipeline (pre-fill writes `"5"`/`"last"`, the composer reads the
string and zero-pads anything that is not `last`), so one control, one testid
and one `name` survive — the conformance surface (testid + composed value) is
unchanged. The pattern makes the allowed set explicit and client-enforced;
the server still validates on write (§4.2), so a non-conforming client is
refused where it always was.

Rejected: Option 2 (number input + `tickler-monthday-last` checkbox) splits
one value across two controls and needs an "which wins" rule when both are
set — a worse contract for the same reach. Option 1 (a 1–31 + last `<select>`)
is the same closed set but makes typing a day clumsier than a text field and
deads the composer's zero-pad path; the group's other selects are small enums
(weekday 7, ordinal 5), not 32 values. The number spinner was never useful
for 1–31 and cannot hold `last` at all — that was the bug.

**Spec first, then the template.** `spec-gui.md` §5.6's sketch now renders the
text input with the pattern, and a new bullet explains it (a `type="number"`
input cannot hold `last`, which the format §3.3 `SCHEDULE`, the CLI and the
server composer all accept). The composition table was already right
(`1`–`31` or `last`) and is unchanged. The implementation follows the sketch:
`partials/tickler.html` and the JS test's DOM mock carry the same attributes.

**Verified.** `TestWakeUpComposition` gains the sharp case — form `monthday
last` composes to `tickler:last` on the item, and the rendered panel control
is `type="text"` with the pattern (the regression pin: this test fails if the
control ever goes back to `type="number"`). `TestWakeUpGroupPrefillShapes`
still proves `value="last"` pre-fills back. Full `go test ./...` green,
`go vet` clean, 32/32 JS tests, gofmt clean, `check.sh --all` 8/8. Built
`mm-ui` and ran it against a copy of this tracker: a real form POST with
`tickler-monthday=last` wrote `tickler:last@08:00` to the file.
